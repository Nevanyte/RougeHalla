# NPC continuity runner callsite assessment

This is a source-callsite assessment and result at base `76ea6b995d3f2d7f844c1ff65f9a0750094a68c7`. The actual `BotRunner`/`Brain` replay passed for the network-style profile and all four default-manager phases. No conclusion about a source defect or intended gameplay semantics is made here.

## Production call order and cadence

The normal network bot constructs `createBotRunner` with `vision: true`, `selfDelayMs: 0`, and `worldDelayMs: INTERP_DELAY_MS` (100 ms) in `packages/server/src/bots/BotClient.ts:321`. Each `onPatch` builds a `PerceptionInput` from that decoded room state and buffered FX, toasts, and private messages, clears those buffers, then calls `runner.frame(input)` (`BotClient.ts:325-349`). The network driver therefore presents every received state patch to the runner; this source path does not add the in-process simulated downlink.

The in-process `BotManager` is a separate driver. It defaults to `BOT_FRAME_EVERY_TICKS = 4` (5 Hz at 20 Hz) and phases seats across those four patches (`packages/server/src/bots/BotManager.ts:39-45, 177-183, 356-359, 402-437`). Skipped patches' FX batches are retained for the next frame. Its default simulated one-way latency/jitter is 30 ms/8 ms (`packages/server/src/bots/brain/types.ts:1236-1253`); its runner uses `selfDelayMs=30` and `worldDelayMs=INTERP_DELAY_MS+30=130` (`BotManager.ts:347-355`). Commands pass through an ordered simulated delay line (`BotManager.ts:362-390`). These values must not be conflated with the network bot's every-patch, 0/100 ms runner configuration.

For either driver, `createBotRunner.frame` updates BotVision, calls `perceive` with its `canSee` callback and previous minimap, stores the new minimap, pushes the frame, composes the delayed percept, applies `vision.filter`, and only then calls `brain.tick` (`packages/server/src/bots/brain/runner.ts:49-60`). Inside `Brain.tick`, `memory.observe(p)` runs before `BrainContext` is constructed and before modules, strategy, tactics, or command submission (`packages/server/src/bots/brain/brain.ts:285-300`). It runs on each `brain.tick` with a non-null composed percept; slower strategy/tactics clocks do not gate it (`brain.ts:316-335`).

## Visibility and minimap behavior

`BotVision.update` enables sight only for active, non-training state; it consumes optional private `vision` snapshots, applies `gatesLocked`, updates its local `VisionMemory` from the bot's current player row, and builds only self-owned, unexpired ward memories (`packages/server/src/bots/brain/vision.ts:20-56`). `BotVision.canSee` accepts points from the local trail or an owned ward (`:58-62`). After FrameRing composition, `BotVision.filter` can remove fighters, mobs, containers, projectiles, minimap mobs, events, fields, chests, and effects (`:64-85`). It does not change the minimap timestamp.

`perceive` repaints minimap dots on first use or when `MINIMAP_REFRESH_MS` has elapsed, and the repaint includes living mob/elite rows in sight (`packages/server/src/bots/brain/perception.ts:618-640`). Between repaints, it filters the previous dot list by current `canSee` but preserves the old `t` (`:639`). Memory folds dots only when `p.minimap.t` changes; a missing dot then marks a previously dotted mob dead, while a later dot does not revive a record whose `alive` flag is already false (`packages/server/src/bots/brain/memory.ts:561-585`). An off-repaint visibility filter can therefore hide a dot without immediately producing a new memory observation; the next changed repaint timestamp is the decisive input.

The server-side `canPlayerSee` is related but not the exact local pipeline: it checks gameplay/training, viewer existence/alive status, `getVisionMemory`, immediate `isInVision` at the current player origin, and self-owned ward sight (`packages/server/src/sim/vision.ts:49-63`). BotVision uses the same `VisionMemory` class, but refreshes it on runner calls, uses `Math.fround` player coordinates, can restore a private snapshot, and lacks the server helper's separate immediate `isInVision` check (`bots/brain/vision.ts:25-42,58-61`; `packages/shared/src/vision.ts:121-149`). BotVision also filters post-compose delayed data using its current local sight. The existing source-method witness's `bot.mts` instead passes `canPlayerSee(sourceWorld, viewerId, point)` to `perceive`, calls FrameRing and Memory directly, and does not run `BotVision.filter`; that limitation is disclosed in `docs/evidence/npc-continuity-source/README.md` under the bot adapter scope.

For the captured history, the source rows show active/non-training play, `gatesLocked=false`, an all-floor map, three living camp mobs, no ward owner/expiry, and the witnessed mob at 800/688/1504 units at initial-visible/return/hidden milestones (`parity/policy/npc-continuity/source.json`, `world.actualLifecycle` and `timeline[].sourceDiagnostic.camps`). Those conditions explain the broad sight agreement in the actual replay. The long hidden interval and return settling interval also span many 100 ms vision refresh windows. Local trail initialization, private snapshots, update phase, 5 Hz versus 20 Hz updates, delayed composition, and minimap timestamp transitions can still change the first omitted or re-admitted frame.

## Passive observation boundary

The replay uses the real `BotRunner` and `createBrain`, with exact captured decoded states and the captured FX batches (all null in this history). It does not call `Memory.observe` a second time, inject or edit memory entries, substitute a scripted/fake Brain, modify the Percept, or submit returned commands to the captured World. The V8 Inspector helper installs an unchanged `()=>memory.view` getter at the first original `brain.tick` entry, captures the getter only after the whole original tick returns, disconnects the Inspector, and reads the current Memory view after completed ticks. It does not pause between `memory.observe` and context creation or sample a mid-tick state. OFF/ON public trace equality and helper cleanup are recorded. The replay has no captured private messages or reconnect; the report labels the driver profiles as source-schedule models, not a network session or actual BotManager lifecycle. Any instrumentation that wraps/replaces Memory, calls `observe` independently, writes World/Brain state, or makes commands reach the World would no longer be passive evidence.

An open-loop replay must state which actual driver it represents. Replaying every captured state into `createBotRunner` is a network-style per-patch driver only if it preserves network-style 0/100 ms settings and actual private input; imposing the BotManager four-phase schedule instead represents its 5 Hz driver, not the network path. If commands are intentionally not applied to the World, label that boundary and do not claim a full gameplay run.

## Conditional owner decision

The actual caller result now supplies a concrete owner decision: should a missing mob minimap dot be treated as terminal death, or as “not currently observed” until a death/lifecycle signal is available? The current Brain marks the witnessed mob dead after omission and keeps it dead when a later post-filter Percept presents the living mob again. Its camp Memory also eventually reports `aliveSeen=0` and a `clearedAt` timestamp, while the source camp remains `alive=3`, idle, and without a ward. If the owner chooses nonterminal omission semantics, the minimal fair candidate is to separate visibility uncertainty from confirmed life/camp state: omission may stale or hide a last-known row, but alone should not mark a mob dead or infer the whole camp cleared; a later visible row may refresh that stale observation unless an authoritative death/respawn cue intervened. This is a candidate interpretation, not an implementation request or source-bug verdict. Root owns the decision.

The replay's source diagnostics show the mob and all three camp members remained alive and the published camp stayed idle with no owner/ward during this no-clear history. It does not establish behavior across actual death or camp clear. A full clear/respawn changes public alive/state/cleared/respawn/ward facts; death FX, elite announcements, locks/targets, HP, persistent effects, loot, home position, source ordering, and RNG may distinguish histories (`docs/evidence/npc-continuity-source/DECISION.md:7-15`). No hidden death/replacement pair was produced. No ID-only continuity rule or privacy conclusion follows; any future proposal still needs the full-clear/global-camp/lock/cue comparison under the applicable observation contract.
