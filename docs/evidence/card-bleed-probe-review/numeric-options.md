## Numeric closure in actual code

`systems/status/dot.rs:77–119` computes `value*50/1000`, then owner multiplier/critical and shares. Generic status validation (`status_runtime/mod.rs:240–268`) currently checks finite scalar/payload/shares, not safe products, aggregate cardinality or sum magnitude. Thus “all restored input floats finite” proves neither finite landed rows nor finite Card pair totals, as both real probes demonstrate.

`systems/ledger.rs:883–901` tests **pre-scaled** `amounts[j]>0`, then pushes `amounts[j]*landed_share` without a post-product check. `landed_share` at852–859 is nonnegative: either positive applied/positive total, or a max-with-zero expression. Therefore the admitted landed algebra has nonnegative finite/zero, +Infinity and potentially NaN; the positive precheck and nonnegative share exclude negative finite/-Infinity from this multiplication. In particular regular-NPC total+Infinity with finite applied damage uses `applied/total=0`, so an infinite positive member produces `Infinity*0=NaN`. This is a concrete code/algebra branch, **not an executed fourth probe or a claim that generic NPC restore already admits that setup**. The ledger does not provide the stronger global “only finite or +Infinity” invariant.

Source `cardHooks.ts:307–318` filters solely dot/no-ability/no-signature, inserts the first amount and does sequential `acc.amount += h.amount` on repeats. It does not reject NaN/infinity or require positive amounts. `flushBleeds:281–289` emits every stored row unchanged, without an amount predicate. Hence skipping NaN, capping infinity, changing order, or substituting an exact sum for the trusted fold would change that source behavior. Ordinary released finite witnesses remain unchanged under a faithful representation.

## A: arithmetic-safe restore admission

A scalar threshold such as `value<=MAX/50` repairs only the first demonstrated operation. It does not repair4096 finite rows, owner/critical/settlement/share products, restored pending contributions or accumulation over the retained500ms window. Rejecting by tag count alone wrongly rejects safe tiny rows and is not justified. Checking only the next step's current pair sum also does not prove closure under remaining live producer actions/factor changes or the already retained trusted totals.

A complete admission alternative must derive arithmetic-safe bounds from the actual accepted factor/shares/deferred/status domain and the entire retained pair window, preserving every state it claims safe, and keep that invariant through accepted live lifecycle/input producers. The two probes provide counterexamples to the current admission, not that complete proof. **No one-line targeted restore magnitude/count fix is a complete dispatchable numeric solution on present evidence.** An admission-policy change would also change which previously accepted checkpoints run and requires explicit Root identity/compatibility treatment. It should not be smuggled into the independent NPC domain repair.

## B: tagged trusted arithmetic (exploratory, not approved)

`Finite(nonnegative f64) | PositiveInfinity` alone is **not closed** over the actual landed multiplication. A canonical three-case Card amount **can close this narrow Card reporting algebra**: `Finite(nonnegative finite binary64) | PositiveInfinity | NotANumber`. Deserialize finite payloads strictly: reject negative/nonfinite values and invalid/ambiguous tags; represent NaN only by its payload-free tag and infinity only by its payload-free tag. Preserve source-observable finite bits, including signed zero if present; do not normalize values incidentally.

Insert/classify the actual first landed amount. For repeats execute the original ordered finite `+` once; finite overflow becomes PositiveInfinity. Infinity plus finite/infinity stays infinity; NaN is absorbing, including infinity+NaN. No negative-infinity case is needed under the positive-input/nonnegative-share invariant above; do not quietly assume that invariant for a different producer. This preserves source first-insertion order, sequential rounding, overflow and NaN classification without persisting an IEEE nonfinite float. It does **not** repair unrelated upstream World arithmetic, nor prove all large accepted generic trajectories safe outside the new Card report.

C-DET explicitly says no nonfinite serialized World float (`CONTRACTS.md:388`, ADR0007:37) because JSON writes it as null. A payload-free enum sentinel is finite serialized data, fully visible to the existing serde-derived hash/checkpoint layout; it need not violate that literal rule. The current Card design explicitly forbids installing tagged nonfinite state, however: Root would have to deliberately replace that planning decision and document the extended domain. This analysis does not grant the exception/decision. Checkpoint/replay/version/content work already planned must include strict new-tag validation and actual changed hash leaves; never rely on serde_json's nonfinite→null behavior.

Raw server-only `Event::CardBleedHit` must carry the **typed amount**, not decode the infinity/NaN tag back into an event f64. Preserve typed server diagnostic/fixture comparison and exclude the event exhaustively from stateless/public observation. No wire/public SeenEvent numeric extension follows. Existing source output tags are comparison encoding, not authorization to send special numbers to clients.

## Public arithmetic remains independent and viewer-local

Eligibility must be resolved from the settled tick **before any numeric failure can influence a viewer**, then source redacted before public grouping. Do not poison the entire sealed report/projector globally because one hidden raw pair is NaN/infinite or its exact sidecar cannot accumulate. Under B, derived per-raw-pair sidecar arithmetic must retain an explicit nonfinite/error classification alongside ExactSum rather than globally failing at producer/seal time. Skip unentitled pairs before inspecting that classification; combine only entitled, redacted public keys. Never use the trusted global pair total to seed public history or decide public failure.

Existing `fx_projector/exact.rs:18–20` rejects nonfinite/negative input, and `rounded:78–80` returns Overflow when a **sum of finite inputs** rounds past maximum finite. Both remain possible under B. Preserve the existing fail-closed public policy: an entitled invalid amount gives typed InvalidAmount; an eligible exact bucket whose final rounding overflows gives typed Overflow; `FxProjector::fail` clears staged output/buckets and disables that viewer until the normal rebind path. Do not emit NaN/infinity/null, clamp, silently omit one bad bucket or publish a prefix. An unrelated unentitled nonfinite pair must not alter that viewer's output/error. Card's exact coalescing/merge must carry these per-pair classifications through segment boundaries and apply the same eligible-before-error rule; finite exact sums still round only at their public flush.

**Decision recommendation:** B's three-tag extension is the smallest self-contained representation option for preserving the observed existing generic intake and source Card fold, provided Root explicitly accepts that domain and the viewer-local typed-error design. B's proposed two tags are insufficient. A remains an alternative only with its full retained-window arithmetic admission invariant, not an arbitrary new cap. Neither option is approved here; no production implementation is authorized.
