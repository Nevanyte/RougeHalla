## Why `mobKills` cannot be reconstructed from the event/result trail

The source counter is a precise run-local measure: `arena.ts:267-273` increments `PlayerRuntime.mobKills` and mirrors it to `PlayerState.mobKills` only for an unresolved owner; `world.ts:243-247` distinguishes it from player kills. The source starts the run counter at zero (`sim/step.ts:65`). The ordinary source `RunResult` retains reward breakdown, not that counter (`sim/arena.ts:356-379`).

The native simulation has the same distinction. `systems/mob_life.rs:463-498` increments `credit.mob_kills` for a credited, unresolved, non-training owner before applying the *capped* mob/elite GV reward. Therefore earned mob GV cannot be inverted to a kill count; reaching the cap loses count information. Player kills are a separate result field. The current `WireResult` exposes player kills and GV, not `credit.mob_kills`. Current owner reward-chest/trophy state is not a tally either: `WireRewardId::Kill` is a stat-gain option and `WireRewardChest` exposes current options/taken state (`crates/rh-protocol/src/state.rs:160-168,224-238`), not every credited mob kill; player-kill Trophy drops are a separate mechanic (`packages/server/src/sim/killAugments.ts:1`).

Death events are not a complete replacement history. `Event::Death` is visible only `IfSeen(victim)` (`crates/rh-sim/src/events.rs:208-218,252-260`); observation filters the event by victim visibility and separately removes an unseen `by` (`crates/rh-sim/src/observe.rs:414-417,522-541`). The wire event carries only raw `id` and optional `by`, without a mob/credit/count field (`crates/rh-protocol/src/lib.rs:601-608`; projection at `rh-policy/src/delivery/projection.rs:333-336`). Thus a victim death can be absent from an owner sample, and the event does not attest that the owner received mob-kill credit under the source's training/resolved/award rules. A stream of visible `Death` rows is at most evidence for some events; it is not an exact baseline-plus-every-credit history. A later `Result` cannot repair omitted events or recover the capped count.

Minimal closure if full source parity is required: provide an owner-scoped, run-bound exact counter (including a defined initial/reset boundary and update order), or prove a complete accepted history of *credited mob-kill increments* independent of victim visibility, with exact owner attribution and reset semantics. No such history/proof exists in the inspected protocol 14/16 contract. Any new owner provider still needs its own C-OBS review; this audit does not authorize publishing hidden state.

## Why Held(None) target identity cannot be inferred from command history

The authoritative legacy source has more than an explicit target command. `sim/targeting.ts:30-71` sets a lock for an accepted wand target action; `:88-118` also acquires targets from attack-move. The follow loop (`:145-174`) drops or resumes the lock as the target, weapon, state, visibility grace, and lockability change. `sim/weapons.ts:57-89,133-173,231-237` sets, clears, and resets the lock; attacks, swaps away from wand, weapon changes, disconnect/release, downing, and run end also affect it. Therefore the most recent target command is not an authoritative record of current target identity.

Native `OwnerCombatView` intentionally resolves a lock against the current staged visible actors before projection (`crates/rh-sim/src/owner_combat/public_bridge.rs:37-63`; wire conversion `crates/rh-policy/src/delivery/projection.rs:163-178`). A known visible target can be mapped from that same sample. When it is redacted, the public `Held(None)` has no actor ref to map. `NpcRef14` explicitly carries accepted-sample context and is not a cross-sample identity (`crates/rh-policy/src/delivery/frame.rs:144-156,187-195`; `fair_percept14.rs:107-110`). Even a previously observed NPC id cannot establish continuity into the current hidden lock. Player ids are stable within a match, but the current held identity is deliberately not supplied, and event/history uniqueness cannot prove that it was not changed or cleared and reacquired.

Brain-produced commands do not close this gap. `brain.ts:205-212` stamps each released command and calls `memory.noteSent` before returning it to the caller. That is source Brain release history, not proof the external adapter accepted or the server applied the command. Conversely, the server may acquire a lock through attack-move or change it through target/weapon/state transitions. Protocol snapshot `ack_input` does not echo a complete accepted lock command or target binding. A local history could therefore diverge from authoritative state even while the accepted frame correctly says Held(None).

Exact lock reconstruction would require an entitled current identity binding. Sending a hidden target id merely to make the source Brain's identity comparison possible would disclose information the current projection deliberately withholds. Without a new entitlement decision, a policy adapter must preserve Held(None) as unknown identity and gate any source consumer that requires an exact target; substituting Clear/null or inventing an id is unsound. This is a concrete source-equivalence gap, not a proposed privacy exception.

## Smallest useful native/source controls

These are recommendations for a later, separately authorized closure; none were executed here.

1. For `mobKills`, use an otherwise identical source/native pair around `0 -> 1` and the actual strategy/hunt thresholds, and assert that a missing owner count rejects before Brain mutation/RNG draws. A separate provider-control suite must prove run-start zero, credited increment, no increment for uncredited/training/resolved cases, and reset at the real run boundary. These controls cannot substitute for a producer/provider contract.
2. For lock identity, pair an entitled Held(Some target) sample with Held(None), and use a hidden-state twin where the hidden target differs but every accepted field is identical. The adapter must not convert Held(None) to Clear, map a historical NPC ref into it, or advance Brain with a fabricated target. Verify known visible Player and NPC mappings only within their accepted sample.
3. Once a provider/equivalence is independently admitted, run the source corpus against the exact converted owner values and add positive/negative controls for the distinctions above. A static review cannot claim this comparison passed.

**Disposition:** neither fact is closed by current accepted protocol 14 or the inspected primary protocol 16 additions. `mobKills` has no exact accepted scalar and visible death/result history is incomplete or lossy for its definition. Held(None) intentionally preserves held-ness but withholds the source target identity; command history cannot recover authoritative identity. Keep both existing F0 gates open pending a reviewed entitled provider or an explicitly scoped source-consumer equivalence. No code, tests, capture, wire, or status changes were made.
