## Concrete contract findings

### 1. `MobSeen.type` must remain optional

Legacy `MobSeen.type` is declared `type?: string` in `packages/server/src/bots/brain/types.ts`. The current `verify.mjs::percept()` validator includes `type` in the required field list for every mob row. This rejects a supported absent value and conflicts with the packet’s explicit missing/Undefined/Null preservation rule. Keep the encoded declaration able to distinguish omitted `type` from an own `type: undefined`; validate a present non-undefined value as a string. This is a strict-reader bug, not a request for an optional case campaign; one source witness can establish the optional path.

I notified `/root/bot_tactics_source`; the author says the reader will allow the absent field and add an absent/own-undefined witness. Do not regard this contract as closed until the changed validator and resulting source bytes are available for review and the ordinary native reader preserves the distinction.

### 2. Reached evidence cannot be a copied `covers` label

At initial inspection, `checks.mts::reachedChecks` only asserted `cases.length > 200` and returned each case's declared `covers` text. `capture.mts` placed that result under `coverage.reachedAssertions`. Those values do not show that a method branch, state transition, RNG draw, or callback was reached. The packet requires a reached behavior ledger binding each claim to a concrete operation and actual callback/status/draw evidence, plus meaningful source controls.

I notified `/root/bot_tactics_source`. The author confirmed this is a temporary first grammar-run scaffold and will replace it with operation/result/callback/draw predicates and concrete reached controls before any final capture or freeze. Until that implementation and receipts exist, case names, source-code V8 coverage, and `covers` prose are intent inventories only; they cannot support semantic reach claims.

## Inputs and traces already represented well

- **Actual method outputs, not answer injection:** `runCase` calls the imported source helper/module/registry methods directly. Each operation records its encoded declaration before invocation and generated result afterward. `resolvedInput` for a card definition is a source catalog resolution used by `costsSomething`; the helper itself still receives the declared ID. Learned bias entries and path denials are declared deterministic callback behavior, and callback outputs are computed from those descriptors at runtime.
- **Identity:** Each context token is constructed once per case and reused by operations for that token, giving the WeakMap the same real `cfg` object across a continuation. Distinct tokens produce distinct but value-equal configs. Cases are planned for interleaved identity checks across all four modules. ChestHunter is a separate actual instance with its own lifetime; its runtime own-property diagnostics must remain read-only and must never be copied back as case setup. The four module WeakMaps remain opaque and are evidenced only through subsequent source hooks/results.
- **Memory and Knowledge:** The runner uses actual `createMemory.observe`, `noteSent`, `recordChoice`, and `view`; it snapshots the actual eight-field `MemoryView`. A proxy logs real `whereabouts` calls while leaving the other actual Memory map/view reads intact. Knowledge is constructed by real `createKnowledge`, and its exposed methods record actual arguments/results. The separate Knowledge-constructor RNG stream and the method context RNG lanes are traced.
- **RNG:** The direct-method fixture contract intentionally does not claim `createBrain` seed derivation. Each context declares a seed; the harness makes independent deterministic streams and records draw value/index/order for all lanes, including per-lane zero counts. Initially the runner also put a fourth `knowledge` lane on `ctx.rng`, which differs from source `BrainContext`/`BrainRngs` (three context lanes; Knowledge is a separately constructed object). I reported this; the author separated Knowledge construction from the context lane object. Verify the final trace still records the constructor stream while hooks receive only `decide`, `motor`, and `lapse`.
- **Services and callbacks:** Module path/log/learned/Knowledge/Memory callbacks capture actual argument order and results. ChestHunter's direct walk/sight callback descriptors are argument-sensitive; the real path service is used for declared real paths, and declared radius/half-plane denials are not answer tapes. The exact callback descriptor and all requested coordinates/results must stay in each case.
- **Map values:** The first runner draft stored map labels only. The evolving `capture.mts` now emits each exact static map as MethodValue plus `mapHashU32`, and the author confirmed the ID-to-map binding will be explicit for the reader/native guide. That addresses the immediate omission if each config map label resolves only to its corresponding embedded value. For final intake, bind each config `map` ID to one unique embedded MethodValue and verify its recorded map hash against that value (or explicitly document the hash as informational and use the embedded value itself). Do not infer a map from a name alone.
- **Value codec:** `codec.mts` distinguishes undefined, NaN, ±Infinity, negative zero, array holes, Map/Set order, Uint8Array, object entries and instance/callable diagnostics using explicit tags. The independent verifier rejects unknown tags, extra tag fields, duplicate map/object keys, invalid Uint8 values, duplicate case/map IDs and missing consumed required facts. It does not rely on plain JSON `null` to stand for every absent state.

## Nonfinite and numeric boundary to declare explicitly

The fixture currently applies recursive `declaredFinite` to declared operations, with an exception for source-sanitized learned callback values. The source author clarified that this finite method-fixture profile intentionally excludes nonfinite declared plan inputs; this is a bounded witness scope, not a claim that the source rejects such values. Indeed, `planning.ts::readDeal` accepts `endsAt` whenever `typeof endsAt === "number"`, and its number helper returns numeric `spawns`, `pick`, and `boon` values unchanged, including NaN/±Infinity. If the fixture uses this narrower profile, the schema/README and eventual native guide must say so without describing it as the complete direct-JavaScript acceptance domain. The existing planned malformed-but-source-valid cases should still preserve source-supported strings/optional fields and finite binary64 coercions.

Before freezing, document and validate the chosen finite plan-input profile as an intentional bounded scope, not a source semantic. Preserve finite binary64 values without integer narrowing; keep source string/non-number coercions in the actual `readDeal` path. Continue to reject nonfinite self geometry/clocks if those are declared as real Percept facts. Do not normalize sentinel results such as `cardScore === -Infinity` or learned callback Infinity to zero in captured output; allow them only at the exact source-supported fields and preserve the source sanitization behavior.

I sent this boundary distinction to Root and `/root/bot_tactics_source`. It is a declared-scope decision, not a generic JSON fuzz request. The native reader must apply corresponding field-aware checks before state/RNG/path mutation.
