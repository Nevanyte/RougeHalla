# Proposal: predict the ranged release pause (audit finding 3)

Status: **implemented 2026-11-10 for wand and swing wind-ups (option B, from delivered facts); bow release is blocked on a missing
server fact.** Owner approved ("we are trying to perfect the feel of the game"). See "Outcome" at the end; the original proposal below
is kept for the reasoning. Source: `docs/rework/CONTROLS_AUDIT.md` F2 and section 3 item 1.

## Problem

The server sets the owner's move multiplier to 0 for the last `RANGED_RELEASE_PAUSE_MS` (200 ms) before a bow or wand release,
during any swing windup, and during `root_until` (`crates/rh-sim/src/systems/weapons.rs:253-263`, `constants.rs:139`). The client
mirror (`LocalMotion.SpeedModifier`, `client-unity/RoguehallaNet/Net/LocalMotion.cs:432`) returns 1.0 by design. A player who
shoots while walking therefore keeps walking locally for about 200 ms (up to 34 u) while the server stands still, and is then
pulled back at 70 to 120 u/s. The legacy client predicted it (`syncLocalRangedPause`, `RaidScene.ts:1470`, fed by
`localAutos.rangedPause()`, `localAutos.ts:91`).

## What would be mirrored (exactly)

One pure function, no new state beyond one interval:

- `RangedPause { fromMs, untilMs }` in **server time**, set at the moment the owner's `Attack` is sent for a Bow or Wand
  (the client already knows the weapon from `Session.Me.Weapon`), with
  `untilMs = landsAt` and `fromMs = landsAt - min(RANGED_RELEASE_PAUSE_MS, windupMs)`.
- `landsAt` and `windupMs` are **not** guessed from the press. They come from the server: `weapons.rs` computes them from the
  weapon interval and `BOW_WINDUP_MAX_S/INTERVAL_SHARE` and `WAND_WINDUP_*` (`constants.rs:176-179`). Two options:
  - **A (preferred).** Derive them client-side from the same constants (add to the generated constants table the C# already reads)
    and the owner's published attack interval. Needs the interval on the wire or a constant per weapon; both are in the sim.
  - **B.** Do not predict the start; consume the existing server `walk_hint` (computed in the sim, unused by `client-unity`) so the
    pause begins only when the server says so. Smaller, but it cannot remove the first RTT of lead.
- `LocalMotion.SpeedModifier(nowMs)` returns 0.0 inside `[fromMs + D, untilMs + D]` where D is the measured order delay already
  tracked for reconciliation, else 1.0. Swing windup (melee) and `root_until` stay unpredicted: they are out of scope here.
- Cancel: any stagger, stun, swap or death message from the server clears the interval (`stagger` cancels a pending cast).

## Rust vectors that would prove it

The C-PARITY rule needs vectors generated by Rust, not by the client port:

1. A new `protocol/fixtures/ranged_pause_v1.json` written by `crates/rh-parity/tests/pnet1_goldens.rs` next to the existing
   `server_walk_v1.json`: for Bow and Wand, each with the walker moving, record per 50 ms tick the press time, the server's
   `lands_at`, the tick at which `move_multiplier` becomes 0, the resulting position, and the interval and constants used.
2. `LocalMotionTests` replays the fixture: with the pause enabled the predicted position must match the server within the existing
   reconciliation tolerance at every tick, and `SnapDistance` is never reached.
3. Negative vectors: attack that the server rejects (cooldown, stun) must leave the walk unpaused after the 1 s order expiry,
   and a stagger mid-draw must cancel the pause on the first snapshot after it.
4. Existing `server_walk_v1`, `PredictionLatencyTests` and `PredictionPollTests` stay green unchanged when no attack is pending.

## Risk

- **Rule leakage.** The client would encode a weapon timing rule. Mitigation: constants only from the generated table, one
  function, vector-checked; the server remains the authority and corrects any difference.
- **Wrong-way guess.** If the server rejects the attack (cooldown, stun, out of range sight), the client stands still for up to
  200 ms for nothing. The pause is short and symmetric with the lead it removes; the doc's alternative B avoids this entirely.
- **Order-delay coupling.** The pause window moves with the measured D; a bad D shifts it by tens of ms. Reconciliation already
  tolerates that class of error.
- **Scope creep.** Melee windup and roots are the next ask. Decide now whether the exception covers only ranged release.
- **Cost.** Rust fixture work plus a small C# change (about 40 lines) plus an ADR 0008 amendment. No wire change and no
  `PROTOCOL_VERSION` bump unless the attack interval must be added to the owner block (option A without a constant).

## Decision requested

Approve A, B, or neither (then accept the current rubber-band, softened only by a lower correction ceiling while a ranged attack
is held). The implementer will not start until the ADR amendment exists.


## Outcome (2026-11-10, branch `rework/pause`)

**Chosen: B, generalised.** The client does not time an attack from a key press. It consumes the facts the server already delivers to
the owner: the owner's `Windup` fx (ADR 0026: attacker, weapon, wait `ms`; sent in the tick the attack starts, so `tick time + ms` is the
landing), the owner's `Stagger` and `Cancel` fx, and the self block's weapon and stun bit. `LocalMotion` places the pause on the
server's 50 ms step grid (the walk of the step ending at tick T stops when `landsAt - 200 <= T < landsAt` for a wand, or
`tick <= T < landsAt` for a swing) and maps it onto the model clock through the sample stamp and the measured order delay
reconciliation already uses. The only rule constants added are `RangedReleasePauseMs = 200` and `TieEpsMs = 1e-6`, both pinned to the Rust values by
`ranged_pause_v1.json`; `TickMs` and `PlayerSpeed` were already mirrored.

| Case | Covered | How it is proved |
|---|---|---|
| Wand release pause | **yes** | `ranged_pause_v1.json` cases `wand-single-shot`, `wand-held` (3 casts), `wand-rejected-cooldown` |
| Swing wind-up | **yes, but a player swing has no wind-up** (`player_timings` gives melee 0 ms; only NPC swings and card-scaled windups are non-zero), so nothing visible changes | `sword-swing`: windup fx `ms = 0`, server never pauses |
| Stagger during the cast | **yes** (fx `Stagger` ends the pause at its tick) | `wand-staggered`, `wand-staggered-in-pause` |
| Weapon swap during the cast | **yes** (self block weapon change) | `wand-weapon-swap` |
| Stun | by the self-block stun bit; **not vector-proved** (no stun can be produced from `rh-parity` without editing `rh-sim`); unit-tested only | `AStunInTheSelfBlockEndsThePause` |
| `Cancel` fx (order-cancelled cast) | handled (pause ends the step before the cancel's tick, from the schedule order: inputs run before the multiplier); **not vector-proved** | none yet |
| Roots (`root_until`) | **no**, unchanged; players have none without cards | none |
| **Bow release pause** | **no: blocked.** The sim announces no `Windup` for a bow draw (`weapons.rs` `start_attack` sets `draw_started_at` only), and the owner block carries `draw_started_at` and `ready_at` but not the landing. The landing is `draw_started_at + min(BOW_WINDUP_MAX_S, BOW_WINDUP_INTERVAL_SHARE * interval)` scaled by the windup mirror: a rule the client must not hold. | `bow-single-shot` records a real 4-step server pause with no delivered fact; `ABowReleasePauseIsNotAnnouncedSoItIsNotMirrored` pins the gap |

**What would unblock the bow** (a separate reviewed change, not made here): the sim emitting `Event::Windup` for the bow too
(`start_attack`, one line, `ms = lands_at - now`), or carrying the landing time in the owner combat block. The mirror already
treats a `Bow` windup as a release, so no client change would be needed beyond regenerating `ranged_pause_v1.json`. Check ADR 0026 first:
the telegraph would then also draw for bows.

**Known residuals** (all bounded, none a snap): a cancel fact slower than the model's lead (stagger or swap arriving after the model has
already paused) costs up to the part of the pause already reached; the wire rounds `ms` to whole milliseconds, so a landing within 0.5 ms
above a step boundary can place the window one step (8.5 u) off; the first part of a melee-style wind-up is learned one link delay late.
The numbers are in the ADR 0008 amendment.

**Browser measurement** (real Web build, `--first-playable` server on 127.0.0.1:7997, `Tools/pause-proof.cjs`, 24 shots each): bow with the mirror
on, median pull-back 34.1 u per shot (max 53.3); with `?pausepredict=0`, median 34.0 u (max 34.5); walk-only baseline 0.15 u. Unchanged, because
a bow draw delivers no `Windup` fx (0 seen). The wand could not be measured in a browser: the first-playable map has no wand and the practice room needs
the PostgreSQL account service; its before/after numbers are the replay's (23 to 32 u drawn error and 8.5 u model-vs-server error at each pause sample, down to 0.00).
