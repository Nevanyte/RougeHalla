## Boundary: what F0 must consume

The only authoritative live input remains a completed accepted public frame. Current flow is
`ItemObserver::prepare` → `DeliverySession::prepare/commit` → `AcceptedFrame14` → `Policy::check_input` → policy →
`ItemObserver::resolve` → `validate`/`Sim::submit`. The headless runner uses the same `Seat` and `drive_seats` machinery;
the delayed-room path returns proposals to the room and resolves/submits them at delivery time. No bot gets a `Sim`,
`World`, server `State`, result event, secret RNG, unfiltered roster, or direct mutation capability.

`Frame14` is a lossless decoded view of the current protocol-14 groups, not yet the complete source `Percept`. The
existing `FairPercept14` explicitly marks owner/remote immunity, remote bow draw, wand cue history, flight courses,
NPC/item continuity and interpolated world as unpublished. Its `Fact` values and required-group checks must stay
three-state: absent/unavailable, delivered `None`, and delivered present (including empty) cannot collapse. Current
native `bots::perception::Perception::build` is a deliberately narrow hand adapter; it constructs string keys like
`p{id}`/`n{id}` and does not implement the source FrameRing, render-time interpolation, minimap dot ring, FX decoding,
memory-decayed views, full extras/events/features, or complete private Brain `Percept`.

The completed source-to-accepted-field classification is in the plan-only
[field closure review](../../evidence/bot-fair-activation-plan/field-closure.md), pinned to the admitted Brain source.
Before live binding, use that review as a gate and refresh it if source closure changes. Private native composition over
declared source inputs remains a separate dependency and need not wait for new public facts. The major producer seams
are:

## Identity, time and privacy rules

`AcceptedFrame14` is a local transactional handoff receipt; it does not attest that a browser or socket received data.
Its session identity is opaque. `FrameContext14.epoch` and sample ordinal are session-local, not global identities.
`NpcRef14` deliberately carries private session affinity and the accepted sample context: it is a reference to an NPC
in that accepted scene, not a durable NPC identity. Preserve the typed player/NPC distinction and scope through Memory,
FrameRing and Brain. `PlayerId` is allocated monotonically from `World.next_id`; a later implementation may use it for
within-match player history only while it also fences by accepted session and proves the allocator cannot wrap/reuse in
the supported match lifetime. NPC presented ids are regenerated on sampled-tick changes or public cue changes
(`ActorRefs::stage`), so they cannot key cross-sample Memory. No position/type matching is an identity substitute.
`ItemObserver` issues monotonically increasing pickup handles, preserves its counter across reconnect, scopes bindings
to the viewer, and retains retired bindings only for the 20-tick grace; the resolver never binds an expired handle to a
replacement. Keep item handle, viewer and session provenance explicit, and never carry a binding into a new run.

Reset every temporal history, Memory, cached identity, delayed input, and run summary at a real new match/session.
Within a session, enforce monotonically advancing accepted samples and the original source clock rules. Handle a
reconstructed/restored simulation as a new external observer epoch. Keep event catch-up judged against the sight at each
event's own step. Do not infer an event origin time where the event schema has none.

Fairness acceptance must include **hidden-state twins**: construct two valid simulations that differ only in server-only
facts (including hidden actors/fields or secret RNG) but produce the same accepted viewer frame/history and public
static inputs. The bot's Percept, Memory, callbacks, RNG use, goals, proposals and observable summary must remain the
same. Separately vary a legitimately visible fact and show the consumer changes only through that permitted fact.
Assertions must compare the bot's accepted-input trace, never use hidden state as a runtime fallback or expected answer.

After field ownership is settled, the smallest intended seams are:

1. Extend the typed `AcceptedFrame14` consumer/profile only for facts proved source-required. Keep all preflight checks
   before Memory, history, RNG, path service or Brain mutation. Retain current atomic delivery commit and supported
   `Fact`/optional semantics.
2. Bind the existing admitted private temporal/FrameRing cores through a dedicated full accepted-frame Percept composer
   owned by the policy seat, extending only missing shared seams. It must reconstruct source order/interpolation from
   accepted samples and public static map/features, then call the real admitted Brain. Brain owns Memory and its exact
   stamped/released-command `noteSent` calls; the composer must not record those a second time. Track later adapter
   acceptance/refusal separately where source consumes it. Do not duplicate an existing temporal engine, retrofit the

3. Bind the admitted private Brain once per seat using `MatchStart`'s actual owner, policy seed, arena/content,

4. Preserve one room-level `PathBudget::startTick` per room frame and each bot's service/cache. The standalone client

5. Route every proposal through existing observer resolution and normal `validate` + `Sim::submit` budgets/order limits.
   Delayed proposals remain proposals until their actual delivery tick, where current state/handles are resolved again.

If the accepted client-facing frame lacks necessary facts, provider work belongs to a separate precisely scoped
C-OBS/C-NET/Unity owner review. This packet does not authorize a privileged native-only view or hidden-state side
channel. Do not loosen `Policy::check_input` to accept partial data by substituting defaults.

## Minimal F1 driver and outcome seams

### Match lifecycle and results

`Policy::reset(&MatchStart)` already runs at compatible seat construction. There is no policy end/result callback today.
Add a once-only policy-run finalization seam at the shared seat/runner boundary, not inside `rh-sim` or a Brain tick.
It receives either the actual authoritative resolved bot result or an explicit void/interrupted outcome. Live room
results originate from `Event::Resolved` and the existing `RoomReport::Result` path; `Room::finish(interrupted)` discards
unresolved work on abort and must not invent a result. Headless execution already records actual `Event::Resolved`
results in `MatchSummary`; feed the same per-seat finalization path there. Guard duplicate event/close paths so
`Brain.end(result)` runs exactly once for a resolved run and `Brain.end(null)` exactly once for a void/interrupted run.
No end callback may flush or mutate the completed Brain summary; stop future ticks in the runner. Training rooms do not
settle/store runs today and must remain outside learned-result recording.

### Inputs, feature support and potions

F1 must demonstrate the full actual bot driver, including reset, ordinary proposals, accepted/rejected delivery,
resolution, death/void, end, result and summary. Every gameplay action—including `UseConsumable`—uses the same
`ItemObserver.resolve`/`validate`/`Sim::submit` path and action/order budgets as other actors. No direct potion/status
mutation is permitted.

Legacy `BotRunner.shouldUsePotion` uses the owner's live HUD and sends a heal only when alive, below 65% HP, stocked,
not healing, not stunned/casting, and at least 1000 ms after the last accepted send. It updates its throttle timestamp
only after the adapter accepts `useConsumable`. Native `WireInventory` currently has `potions_healing` but no
`healingUntil`; the Rust source producer sets that count from active HOT entries, clears both count and deadline when
the final HOT expires or the owner leaves standing state, and `potions::validate` checks the stored deadline against the
last HOT. Thus the consumed `potions_healing > 0` predicate can stand in for `healingUntil > now` only on a validated
non-ended owner inventory at the same `source_time` after the scheduled HOT update; ended snapshots are outside live Brain
ticks. It does not reconstruct the deadline. Add producer-boundary equivalence
controls (new HOT, overlapping HOTs, last-HOT expiry, same-time boundary). Advance the retry clock only when the
external adapter accepts the send: in the delayed path, admission to the delay queue already returns true and advances
it. A later resolve/submit/gameplay refusal does not undo that update. A mere Brain proposal, unsupported feature or
adapter/queue refusal does not advance it. Keep queue acceptance and later simulation outcomes separate. Feature support
is explicit and checked before proposal/hand state is committed. Test both live immediate and delayed-room boundaries.

### Existing learning only

`Brain.end(result)` remains pure and returns the source summary/choices. Join that summary to the existing
`BotRunFacts`/pure `RunSummary` fold only after a real resolved result, preserving the manager's faction choice and
the Brain's own choices. Expand the existing data adapter only as needed to retain those fields; do not add a new store,
model, training pipeline, service, dataset or inference dependency. Existing `LiveLearning` stays an off-tick writer
with the current Postgres backend; `rh-sim` remains pure. Void/interrupted and training runs do not write learning
facts. Headless evaluation may observe summaries but must not write to live learning storage.

Report exact inputs, versions, source/build identities, run count, action/result counts and the surfaces not covered.
Component parity, a private full-source transcript, a successful compile, or an isolated policy test alone is not full
live/headless bot acceptance. This plan reports no executed tests or runtime proof.

## Morning hosted Source proposal (verify on final merged tree)

For the one-owner test session, `--min-players 1` is required so one real owner can start Source. `--fill-bots 8` means
target total room occupancy of eight, not eight additional bots; the room's fill logic creates only the remaining seats.

```text
--runtime source-arena --map <reviewed-map> --min-players 1 --fill-bots 8 --max-rooms 1 --lobby-seconds 10 --fill-seconds 3
```

The map, final artifact/content identity and paths must come from the reviewed merged build; this packet invents none.
No `--hitboxes` flag is added: current protocol14 does not expose it, and the intended merged hitbox branch defaults
archetypes. After the Unity/hitbox merge, verify the actual defaults/parser, protocol/content identities, one-owner start,
target-total fill behavior, single-room limit, exact archetype hitbox set and final launch command against the same
reviewed server artifact. No hosting changes or deployment are authorized here.
