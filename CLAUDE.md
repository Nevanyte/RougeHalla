# CLAUDE.md — RougeHalla (package name `raid-br`)

Top-down 2.5D roguelike battle arena. Up to 8 players pick a faction, loot, farm mobs and fight. The last one standing wins Glorious Victory (GV, cosmetics-only). Phaser 4 client, Colyseus 0.18 authoritative server, npm workspaces monorepo. Colored shapes only. Design and numbers: `docs/GAME_DESIGN.md`. Running and playing: `README.md`. Faction ids are `fire`, `sentenced`, `plague`, `frost`, `holy` (shown to players as Demon Blood). Weapon ids are `sword`, `bow`, `wand`, `shield`, `axe`.

## Commands
```
npm install            # once, at the root
npm run dev            # server :2567 + client :5173 (concurrently)
npm test               # vitest in every workspace (about a minute; the server suite includes the e2e bot runs)
npm run typecheck      # tsc --noEmit in every workspace
npm run build          # production client build into packages/client/dist (Vite does not type-check)
npm run bots -- 3      # 3 headless bots join the running dev server
npm run bots -- -- 3 --url http://host:2567   # flags (--url, --prefix, --faction <id|rotate|random>, --loop to keep queuing, --verbose) need the second `--`: the root script nests npm, which eats them
npm run harness -w @raid/server               # weapon duel harness (report only, never fails; ~50 s): matrix, style grids (ranged stand/strafe/kite, melee stand/weave/jink), edge verdicts (HOLDS/FAILS, with thin faction columns), TARGET LOCK (both fighters click each other), kiting (shooter styles incl. `orbwalk`, the perfect kiter, and `lock`). `-- --core` skips the sensitivity passes (~40 s), `-- --quick` takes a few seconds, `-- --grid-setups full` gives steadier grids (slower), `-- --help` lists the filters
npm run harness:factions -- --python          # faction cycle per weapon in the real sim vs testing/realtime.py (~5 s; report only). Also --mode policy (moving fighters, ~20 s), --mode full (~7 s), --nmax N
npx tsx packages/server/bench/stepBench.ts            # step() cost with 8 players and 60 mobs (gate: avg < 5 ms, p99 < 15 ms; test/perf.test.ts)
npx tsx packages/server/bench/bandwidth.ts [seed=N]   # bytes/s per client, headless with the real encoder: typical, heavy, idle (gate: < 20 KB/s; test/bandwidth.test.ts)
npx tsx packages/server/bench/mobDuel.ts              # real-sim duels of a starting player against every region's mob and elite (`--style stand` is the design's measure, GAME_DESIGN 11)
python3 testing/test_rpsls.py                 # the faction design oracle (standard library only, ~9 s)
python3 testing/test_kite.py                  # the kiting guarantee at duel pace against an orb-walking shooter: it roots for its windup at each shot and walks between (needs numpy, ~5 s; exits 1 on a FAIL)
python3 testing/kite_windup_sweep.py          # which bow/wand windup caps and shares hold that guarantee, and the shortest Frost windup that lets a chaser arrive (needs numpy, ~10 s)
python3 testing/realtime_report.py            # the 20 Hz model's report (needs numpy, ~40 s)
python3 testing/weapon_reference.py           # prints the parity tables to paste after a weapon number changes (needs numpy)
```
Server env overrides (see `packages/server/src/config.ts`): `RAID_PORT`, `STASH_FILE` (the profile file; the name predates profiles v2), `MIN_PLAYERS`, `LOBBY_SECONDS`, `FILL_SECONDS`, `PATIENCE_SECONDS` (at 8 alive), `PATIENCE_MIN_SECONDS` (at ≤3 alive; default 40% of `PATIENCE_SECONDS`), `SUDDEN_DEATH_SECONDS`, `TRAINING_IDLE_SECONDS`, `COLYSEUS_LATENCY` (simulated ms), `DUMMIES=1` (training dummies and a weapon rack next to every spawn in arena runs too), `MOBS=0` (no regional mobs: they are on by default, one at every camp spot). Client: `VITE_SERVER_URL`. A dev build of the client exposes `window.__raid = { scene, room }`.

## Layout
- `packages/shared` — TS source consumed directly (no build). Contracts and pure logic used by both sides. `index.ts` re-exports everything except the schema.
  - Contracts: `constants.ts` (the tunables), `schema.ts` (Colyseus state: players, mobs, containers, the roster; no projectiles; import via `@raid/shared/schema`), `messages.ts` (client inputs, `FxEvent`, results, profile/shop/leaderboard DTOs), `fxCodec.ts` (the compact `fxs` wire form).
  - Combat rules: `factions.ts` (faction sheet, damage law, `BEATS`), `weapons.ts` (catalog, faction × weapon formula, timings, `WEAPON_BEATS`), `interactions.ts` (shield, stagger and ball-vs-arrow rules), `signatures.ts` (real-time signature numbers, chill, matchup score, damage flash), `policies.ts` (how to play each weapon: bots, harness, mobs, and `lockSpacing` for the target lock).
  - Arena rules: `rules.ts` (feed, bounty, patience and sudden-death formulas), `buffs.ts` (S-curve stacks, combos, the reward curve, the drop stat), `buffView.ts` (the HUD's buff maths and wording), `mobs.ts` (the regional mob catalog: `mobFaction` = region faction scaled by `MOB_K`/`ELITE_K`).
  - Meta: `cosmetics.ts` (catalog, slots, the packed `look` word), `achievements.ts` (goals, pure), `wheel.ts` (the counter wheel's two pentagrams, derived from `BEATS` / `WEAPON_BEATS`).
  - Map and maths: `map.ts` (types, helpers, `withGates`), `mapgen.ts`, `rng.ts`, `pathfind.ts`, `geometry.ts`, `interp.ts` (`SnapshotBuffer`). `scripts/printMap.ts` dumps a seed as ASCII.
- `packages/server`
  - `src/index.ts` (`defineServer`, the HTTP API), `config.ts` (env), `rooms/RaidRoom.ts` (thin adapter, mode `arena` or `training`), `rooms/FxChannel.ts` (the fighter roster and each step's `fxs` batch; `inFlight` for a client that joins mid-flight), `persistence/ProfileStore.ts` (profiles v2: GV, stats, cosmetics, achievements; migrates v1 stash files).
  - `sim/` is the pure game logic. `world.ts` (the World, hooks, ledger types), `step.ts` (lobby, tick order, add and remove players), `arena.ts` (run lifecycle: going down, results, GV, bounty, patience timer, coliseum teleport, sudden death), `gameplay.ts` (assembles the modules), `inputs.ts` (validation, per-player queues), `movement.ts`.
  - Combat: `combatant.ts` (players and mobs as one thing), `weapons.ts` (state machines, `setLock`/`dropLock`), `targeting.ts` (the target lock: accept, chase, drop), `projectiles.ts`, `melee.ts`, `ledger.ts` (the per-tick damage ledger), `factions.ts` (signatures: targets, engagement, chill, lifesteal, heals).
  - Mobs and economy: `mobs.ts` (training dummies and their setup), `mobLife.ts` (regional mobs: camps, damage taken, death and drops, regen), `mobAI.ts` (their inputs: idle, fight, return), `buffs.ts` (stacks, kill combos, the barrier), `feed.ts` (feed, lobby median, mob reward multiplier, rampage announcements), `loot.ts` and `lootTables.ts` (chests, weapons on the ground, pickups, bodies), `training.ts` (the practice room).
  - `bots/` (`BotClient`: a headless player that plays like a person with the game's controls and sends inputs only (`target`, `move`, `stop`, `swap`, `pickup`; never `aim`, `attack` or `release`); `mobHunt.ts` its mob-farming rules; `runBots.ts` the CLI), `harness/` (headless weapon duels: `runHarness` CLI, matrix, kiting, report, parity with the Python model; `runFactionCycle` the faction cycle per weapon), `bench/` (step, bandwidth and mob duel measurements).
  - Tests in `test/`. `e2e.test.ts` plays whole runs with four bots and mobs on. It replays once if the first run shows no kill, signature hit or mob death by a bot (about 1 run in 20 for the mob death), and fails if the replay lacks it too. Every bot's room also decodes every `fxs` batch against its own roster, with no tuple lost.
- `packages/client`
  - `main.ts` (the flow: hub, run or training, results), `net/` (connection, the REST profile client, clock sync and interpolation, `fxInbox.ts` holding `fxs` batches until the scene starts).
  - `scenes/RaidScene.ts` (a run or a training room: right-click sends `move`, left-click `target`, `S` `stop`; it never sends `attack`/`release`), `scenes/HubScene.ts` (the walkable hub: client-only, no server room) with `hub/` (layout, collision and avatar are pure; `hubArt.ts` draws).
  - `render/` (2.5D projection; player, mob, projectile, fx, trail, container and map views; `targeting.ts` picks the left-click target and `LockDisplay` shows an order before the patch, `TargetRings.ts` draws the hover and lock rings), `ui/` (DOM overlay: `menu.ts` docked beside the hub scene, `hub/` panels including the counter wheel, `hud.ts` with the buff rows in `buffsHud.ts`, minimap, weapon bar, training bar, screen feedback, results, toasts).
- `testing/` — the Python design tools (engine, class sheet, 20 Hz model) and the tuning logs. `docs/GAME_DESIGN.md` is the design.

## Architecture rules (do not break)
- **Authoritative server.** Clients send inputs only (`move`, `stop`, `target`, `aim`, `attack`, `release`, `swap`, `pickup`: `CLIENT_MESSAGE_TYPES`). The game client sends `target` and no longer sends `attack` or `release`; they are the low-level trigger that mobs and the weapon harness still use (the bots click their foe, like the game client). Never accept positions, damage, or outcomes from a client. Apart from a walk target, the numbers a client supplies are aim angles, a render time `t` (clamped to `MAX_REWIND_MS`, only on `attack`/`release`), a slot, a container id and a fighter id (`target`).
- **Fixed 20 Hz tick.** Message handlers validate and enqueue; they never mutate game state. `enqueueClientMessage` returns false for a rejected message, and only an accepted one counts as presence (training's idle limit). The sim consumes input queues at the start of each fixed 50 ms step.
- **Sim is pure.** `server/src/sim/*` must not import `@colyseus/core` or touch clients/sockets. It mutates the schema state and a non-synced runtime struct, and returns events. The Room converts events into messages and persistence. Test the sim headless.
- **Tick order is fixed** (`sim/step.ts`; do not reorder): inputs (players in the shuffled `actionOrder`, then mobs) → target locks (`updateTargets`) → weapon state machines → `afterWeapons` → movement → history → projectile sweep (present time, 10 ms substeps) → spawns → melee (rewound) → `beforeDamage` → sudden death's burn (recorded into the ledger) → ledger → systems → settle.
- **The ledger: one way down, one place to settle.** Every hit (projectile sweep, melee, signature damage) is recorded with `recordHit` (`sim/ledger.ts`) and applied all at once by `applyLedger`. Each hit is mitigated per victim, then goes to `applyHits` for a player (`sim/arena.ts`), `hurtMob` for a regional mob or `damageMob` for a dummy. Sudden death's burn is a ledger entry too (`suddenDeath`, recorded after `beforeDamage`: all true damage, from `SUDDEN_DEATH_KILLER`, no `hit` fx, no kill credit of its own), so it lands in the same pass as the tick's hits. Every exit from the fight (death, leave) goes through `downPlayer`. In-tick results come only from `settle()` at the end of the tick, so the shuffled input order never decides a winner. A fighter killed this tick still lands what it started. Simultaneous hits on one victim land together, and the kill goes to the largest rival hit. Simultaneous last deaths go to the higher hp fraction at tick start (an exact tie draws).
- **Spoils are paid after the pass.** While `applyLedger` runs (`world.combat.collecting`), a kill's GV, bounty, stacks, kill barrier, drops and combos are queued with `payLater`. They run once every victim has taken their damage, from the lobby median feed as it stood before the pass, so a reward never decides who survives (sudden death's burn is in the pass too). A killer who goes down in the pass keeps the kill and its GV but gets no raised bounty and no rampage announcement. Outside the pass (`applyDamage`, tests) `payLater` runs at once. A mob's kill goes to the player who did it the most damage over the whole fight, not whoever lands the last hit. A mob that finishes a player a rival hit within `KILL_CREDIT_SECONDS` credits that rival (kill GV and bounty), as leaving does.
- **Target lock** (`sim/targeting.ts`; `setLock`/`dropLock` in `sim/weapons.ts`; synced as `PlayerState.attackTarget`, "" = none). `target {id}` locks an enemy and the server plays the fight from then on, as mob AI does for a mob: each tick after the inputs, `policies.ts` `decide` with `lockSpacing` (close in to the weapon's `far`, then stand; never back off or strafe) sets the path (re-planned at most every `TARGET_REPATH_MS`, only when the goal moved over 8 u or the path ran out), holds the trigger while the target is in range with a clear line, and aims at its present position and velocity. The client's `aim` is ignored while locked, and `facing` follows the target (the shield's block cone reads it). Accepted only for another combatant that is standing, not evading, hostile (not self, not mob to mob; only players lock), within `TARGET_RANGE` (640 u); anything else is ignored with no change. Line of sight is not needed to lock (a target behind a wall is chased around it), only to attack. Dropped (trigger and path cleared, the fighter stops where it stands) when the target is no longer standing, is evading, is past `TARGET_RANGE`, or has been out of sight for `TARGET_LOS_GRACE_MS` (1.5 s; until then the chase paths around the wall) after having been seen once since the lock (`lockSeen`; a target locked behind a wall is chased until first seen, bounded by the leash), or the player holds no weapon. **Orders replace each other in arrival order within a tick** (`InputQueue.moveBefore`, like `aimBefore`): `move`/`stop`/`attack` drop the lock (an unreachable `move` still does), `target` lets go of the trigger. `releaseTrigger` (teleport, going down, a dropped client, training revive) drops it too; a swap or a pickup does not. An attack the lock starts records its `target` on the `PendingAction` and is aimed again as it lands (a swing straight at the target's position at its rewind time) or leaves (`leadAim` from the drawn origin at the target's present position and velocity), if the target still stands and is hostile; then it flies straight and can be dodged. An unlocked attack (a mob's, the harness's) keeps the old aims: a swing and a ball go where they were aimed when the attack started, an arrow along the aim held when its draw ends (the bow's aim at release), and `decide` leads the bow for the lags alone, without its windup. A locked attack has no client `t`: `lagMs = TICK_MS`.
- **Windups root.** Every attack roots its fighter from its start until the swing lands or the arrow or ball leaves (`moveMultiplier`: 0 while `action !== null` or inside `rootUntil`, else 1; nothing else slows a walk: buffs and Frost's chill are `world.moveModifiers`). The windup is committed: a `move` given during it is kept as the path and walked afterwards, only a stagger (not on the bow) or a swap cancels it. The bow is a fixed windup (kind `"draw"`, `landsAt`, `drawStartedAt` synced for the pull), never a partial draw. `weaponTimings`: sword and bash 0.1 s, axe 0.25 s / 25% of the interval and root 0.5 s / 50%, wand `min(WAND_WINDUP 0.4 s, 0.8 × interval)`, bow `min(BOW_WINDUP 0.6 s, 0.92 × interval)`. These are the anti-kiting lever (below, Weapons and factions).
- **Players and mobs fight through `Combatant`** (`sim/combatant.ts`). Weapons, melee, projectiles and the ledger take either; only how they go down differs. A regional mob's faction is its region's scaled by `MOB_K` (elite `ELITE_K`) and paced, read through `factionOf` like a player's, so signatures, armor and timings apply to it unchanged.
- **Mobs are players who send inputs.** `sim/mobAI.ts` is a system (after damage). It pushes `move`/`stop`/`aim`/`attack`/`release` into the mob's own `InputQueue`, and `step.ts` applies them next tick through the same handlers as a player's. Idle mobs send nothing, and mobs never lock a target. A mob walking home (`return`) is evading: `hurtMob` returns 0, `isEvading` keeps it out of hit tests, signature targets and contacts, it starts nothing new (a shot already in the air still lands), and it is whole when it arrives. It gives up 6 s after it last *dealt* damage, so kiting from outside its leash gains nothing. The coliseum teleport puts every mob back on its camp spot at full hp. Mobs never hurt each other (a hit is recorded with scale 0) and their shots fly past each other. A training world never spawns regional mobs.
- **Signatures ride the ledger.** Faction bonus damage (burn, backlash, disease, mark) is recorded in the tick's ledger in the `beforeDamage` phase, so it lands with the tick's hits. Heals go through `heal()` in `sim/factions.ts` (3 s out-of-combat lockout; Holy's lifesteal is exempt). `sim/factions.ts` stretches chilled fighters' `readyAt`, bow draw (its start and the moment the arrow leaves, so the cycle stays interval / chill) and press buffer every tick; the other windups are not stretched, so a chilled swing still lands on time. Weapon timing changes must keep the chill working: `npm run harness:factions` checks it against `testing/realtime.py`. A landed stagger (the 0.5 s immunity starts) pauses the staggered fighter's burn, disease and mark for its weapon's windup (`staggerPause`; none for a bow, whose draw a stagger never cancels; the real sim only, `realtime.py` has no staggers).
- **Buffs and the feed** (`shared/src/buffs.ts`, `sim/buffs.ts`, `sim/feed.ts`). Stacks are fractional floats on `PlayerState` (`stacksHp/As/Ms`). The S-curve bonus feeds max hp (`syncMaxHp`), `attackInterval`/`damagePerHit` (via `attackSpeedMult`) and `world.moveModifiers` (`moveSpeedMult`). Combos at 3 and 5 stacks fire on every kill. The mob reward curve and the catch-up read the feed (`kills + 0.25 × mob kills`). The **bounty reads player kills only**.
- **Combat netcode.** Projectiles are not in the synced state: they are plain objects in `world.projectiles`. A projectile is announced once, in the `fxs` batch of the step that loosed it, and never updated. Clients fly it from `(x, y, vx, vy, t)`, and a `projEnd` fx says where and why it stopped. A client that joins or reconnects mid-flight is sent the projectiles then flying as a batch of its own (`FxChannel.inFlight`, queued behind its full state by core). Melee samples the attacker and every target at the attacker's render time (`rewindT`: the client's `t` on a low-level `attack`; a locked attack, which is all the game client makes, has none and rewinds one tick, and the server aims it from the present: the target lock). A projectile leaves from the shooter's rewound (drawn) position, and the `aim` angles that low-level attacks and the shield use are measured from where the client draws its own player. Keep those three consistent.
- **Wire format.** All fx of a step go out as ONE `fxs` message (`shared/src/fxCodec.ts`, `rooms/FxChannel.ts`): integer tuples, fighters named by index into the append-only `RaidState.roster`, projectile launches in the same batch (`FxBatch.p`). Players still in the lobby are not rostered (no fx names one, and an entry is for good). A mob is rostered when it is placed. `unpackFx(batch, room.state.roster, onDrop?)` needs the client's copy of the roster: without it every id-bearing fx is dropped, and `onDrop` is how a skipped tuple is noticed (the client warns once in dev builds; the e2e run asserts nothing was dropped). The client holds `fxs` batches from the join until the scene starts (`net/fxInbox.ts`). The code tables are wire format: grow them at the end, never reorder. Adding a field to an `FxEvent` means adding it to its tuple and to `packages/shared/test/fxCodec.test.ts`. Synced numbers are narrow on the wire (float32 positions and hp, uint32 timers); the server keeps doubles.
- **The map is never synced.** Only `seed` is in state; both sides call `generateMap(seed)` (must stay deterministic: use `rng.ts`, never `Math.random`, in shared). Loot contents are rolled server-side with a non-public RNG. While `state.gatesLocked`, movement, line of fire and loot line of sight use `collisionMap(world)` (`withGates(world.map)`), never `world.map`. `coliseumSpots` hands out mapgen's coliseum inner spawns.
- **Clients render in the past.** Remote and local entities render at `serverNow − INTERP_DELAY_MS` via `SnapshotBuffer` (`shared/interp.ts`). No client-side prediction yet.
- **Rendering is separate from logic.** Phaser scenes only read interpolated state and send inputs. Projection lives in `client/src/render/projection.ts` (screenY = worldY · Y_SCALE, height drawn upward, depth = worldY).
- **The hub is client-only.** `HubScene` has no room and no server. Its layout and walking rules are pure (`hub/hubLayout.ts`), and a station only calls back into the menu (`onStation`). What it shows comes from the REST profile.
- **Training is a mode, not a fork.** `client.create(TRAINING_ROOM_NAME)` makes a private one-seat room of the same `RaidRoom` class. The server registers two handlers (`defineRoom(RaidRoom, { mode: "arena" })` under `ROOM_NAME`, `{ mode: "training" }` under `TRAINING_ROOM_NAME`). Colyseus merges handler options over the client's, so a client cannot choose the mode. A training world has `SimConfig.training` + `dummies`: a plain dummy, a shield dummy and a rack of every weapon next to the spawn, started the moment its player joins. It has no regional mobs, patience timer, teleport, sudden death, result, GV or stats. Three locks keep it from recording anything: `trainingSettle` replaces `suddenDeath`/`settle` (anyone down is revived), `RaidRoom.settle` and `bankVoided` return early in training (a down *between* ticks still emits `resolved`, which the Room ignores), and leaving is `abandonPlayer`, never MIA. A dropped or leaving client frees the profile at once (`onDrop` holds no seat in training). A player with no accepted input for `trainingIdleSeconds` (300) is let go: only an input `enqueueClientMessage` accepts refreshes `lastInputAt`. Every training branch sits behind `world.config.training` / `RaidRoom.training`; an arena world never reaches it.
- **GV banks at resolve.** The sim only accumulates run GV and reports it in `resolved` results. The Room banks it (`recordRun`, or `bankGv` for a run voided by shutdown). Run gear never persists.
- **Persistence is `ProfileStore`.** Mutations are synchronous in memory (nothing awaits between a check and its change), writes are coalesced and atomic (temp file, fsync, rename, directory fsync) with retry and backoff, and `flush()` runs on shutdown. A v1 file migrates on load. A file that cannot be parsed stops the server and is moved aside, never overwritten.
- **The shop is server-only.** Purchases and equips are `POST /api/profile/:name/purchase|equip` with the profile token. The client sends only a cosmetic id (and a slot). `ProfileStore.purchase/equip` check the token, the catalog price, ownership and the balance in one synchronous step, so a double spend is impossible. Spending lowers `gv` only, never `gvLifetime` or `gvByMonth` (the leaderboard ranks GV earned). Achievements are evaluated inside `recordRun`. An id lands in `achievements` once, and its reward cosmetics are granted in the same step. Win achievements and the per-faction/weapon counters count only `winQualified` wins (the win-bonus gate: `!winBonusWithheld`), so a walkover against a throwaway callsign earns nothing. Kill and bounty achievements are not gated (their rewards are unpriced; an owner decision). The leaderboard ranking is cached per month (dropped when GV is credited in it), and `you` on `GET /api/leaderboard` is sent only with that profile's own token. Equipped cosmetics reach other players as one synced `PlayerState.look` word, fixed at join.

## Conventions
- Colyseus 0.18 APIs (not 0.15/0.16 tutorials): `defineServer/defineRoom` from `@colyseus/core`, `Room<{ state: X }>`, `this.onMessage` (or `messages = { ... }`), `setTimestep` (`setSimulationInterval` is its deprecated name), `client.sessionId` (no `client.id`), a static `onAuth` for matchmake-time checks, client `@colyseus/sdk`. `RaidRoom` sets `patchRate = 0` after `setTimestep` and sends each patch itself after the step. The scene reads `room.state` every frame; there are no per-field callbacks.
- Schema uses the decorator-free `schema({ ... }, "Name")` + `t.*` builders. Give primitives `.default(...)`. No decorators anywhere.
- Only the server imports `@raid/shared/schema` at runtime; the client uses `import type` from it (it decodes by reflection).
- Tunables live in `shared/src/constants.ts`, the catalogs (`weapons.ts`, `factions.ts`, the combos in `buffs.ts`, `cosmetics.ts`) and the signature numbers in `signatures.ts`. Mob scale, leash, buff curves and the reward curve are in `constants.ts`. Loot weights are in `server/src/sim/lootTables.ts`. Units: world units (1 tile = `TILE` = 32), seconds for durations unless a name ends in `Ms`, server time in ms.
- Weapon numbers live in `shared/src/weapons.ts`: the v3 faction × weapon formula (a weapon is a % boost on the faction's rate; `attackInterval`, `damagePerHit`, `backlashPerSwing`). It must keep matching `testing/realtime.py`: `python3 testing/weapon_reference.py` prints the reference tables, pasted into `shared/test/weapons.test.ts` and `server/src/harness/parity.ts` when the design numbers change. `DUEL_PACE` (2) multiplies every faction damage number (not hp; Sentenced's mark ramp by k²) through `pacedFaction`. Sim combat reads the paced sheet through `factionOf` (`sim/combatant.ts`), never the raw one.
- Design rules the sheet left open are recorded in `docs/GAME_DESIGN.md` 9.4. Change them there and in the tests together.
- No `Math.random` in shared code. No enums or decorators (keeps tsx/Vite/TS7 happy).
- Keep comments sparse; explain *why*, not *what*.

## Known TODOs (keep this list honest)
Netcode and scale
- Interest management: every client receives every player's position and weapons, every container's contents, every mob and every projectile, wherever they are. Facing is synced for everyone at up to 20 Hz per player (every `aim` patches `facing`, and `maxMessagesPerSecond` is 100 to allow it). Plan: `StateView` + `.view()` fields, per-client add/remove by distance each tick. The bandwidth gate has little room left on a full map: with 60 mobs, typical load measures 9.4-10.5 KB/s per client, 8 camps fought at once 14.1-16.3, idle 4.1, against 20 (ws payload only; TCP/TLS framing adds a few KB/s; the margin is about ±1.5 KB/s of sim drift). `StateView` is the real fix for larger rooms.
- No client-side prediction for the local player (0.18 has `Predict`/`room.input()` if needed).
- Single process only: the "profile already in a raid" guard (`ActiveProfiles`) and the profile file are process-local.
- HP, status, containers and timers render at the latest patch while positions and fx are 100 ms behind (deaths are held back to match).
- Lag compensation (the melee rewind and the shooter's drawn position) trusts the client's `t` anywhere inside `[now − MAX_REWIND_MS, last published tick]`. A cheating client can pick the most favourable `t` in that 300 ms window (a projectile can leave from up to 300 ms back: its origin is taken when the attack starts, and the shooter is rooted until it leaves). Only the low-level `attack`/`release` carry a `t`; the game client's locked attacks do not, so the window matters for the harness's policy clients and cheaters only. Mitigation: bound `t` per client by measured RTT, or require it to be monotonic. `MAX_REWIND_MS = 300` covers clients up to ~150 ms RTT (render delay 100 ms + RTT + one tick). Beyond that, swings at moving targets start to miss (projectiles fly in present time and are not rewound).
- A room's first join blocks the event loop: `RaidRoom.onJoin` builds the world, and `generateMap` runs synchronously. `onCreate` only picks the seed, and the static `onAuth` refuses a profile that is already active or that opened a still-unjoined room in the last 5 s. A map costs about 20 ms on average and more on seeds that need several attempts (seed 732: 53 ms). The first map in a process takes about 80 ms, because it also builds the lane tables (about 18 MB, kept for the process, on the client too). Training rooms pay it on every entry. Mitigation: generate off the event loop (worker) or pre-generate the next seed.

Identity and persistence
- No rate limits. Matchmaking verifies the profile token before creating a room or reserving a seat (the static `RaidRoom.onAuth`) and nothing more. Profile creation is free: any client can `GET /api/profile/<new name>` as often as it likes, `/api` answers every origin (`Access-Control-Allow-Origin: *`), and each claim adds a profile and a file rewrite. The shop and equip endpoints have no limit either. Training rooms have only the one-active-room guard per profile, and a running room broadcasts a patch at 20 Hz until its player leaves or idles out, so many throwaway profiles can hold many rooms.
- Profiles are weakly authenticated: a random token in `localStorage`, stored in plain text in the profile file, no passwords, recovery or expiry, and no TLS. Clearing site data forfeits the profile.
- GV banks when a player's run resolves. A graceful shutdown (SIGTERM/SIGINT, uncaught exception) pays the GV earned so far (`bankVoided`). A hard kill (SIGKILL, power loss, OOM) mid-run loses it. A purchase is answered once it is in memory, before the file write lands: a hard kill in that window undoes the purchase together with its GV debit, never one without the other. Writes are batched (at most one per second; `close()` and `flush()` write at once), so the window is up to about 1 s. Under `npm run dev`, Ctrl+C reaches the server twice (terminal and tsx), and the second SIGINT exits mid-shutdown, so the last second of changes can be lost in dev.
- The profile file has a single-writer lock (`<file>.lock` holding the PID; a dead PID is taken over, and an exit hook frees it). In a container, a hard-killed server restarted with the same PID (PID 1) sees its own PID as live and refuses to start; delete the lock by hand there.
- GV can be farmed with free callsigns: the win bonus needs 3+ starters and damage on 2+ different opponents (`WIN_BONUS_MIN_*`), but two throwaway callsigns that get killed still pay kills and the bonus. Bounties are uncapped but come from player kills only (an owner decision), so a partner can only cash a bounty that real kills built. Mob GV is capped at `GV_MOB_CAP` per run.
- GV earned after a player's result went out is dropped (`awardGv`). A projectile outlives its owner and its hit still lands; a kill by a shooter who left or whose result is out is credited by name only (`killedBy`), with no GV and no bounty.
- Mob kills do not feed achievements (owner question). "Bounty claimed" counts runs that paid bounty GV (`progress.bountyRuns`), not individual claims. There is no end-of-month trophy job: the leaderboard keeps each month and nothing is awarded when one closes.
- A player who joins without picking a faction (old clients, bots without `--faction`) gets the round-robin default by join order (`defaultFaction`). A failed join or a lobby leave still uses up a slot.

Map
- Cover and range: the bow's 240 u and the wand's 220 u sit against `MAX_SIGHT_CORRIDOR` 480. Mapgen's cover and spawn screens are certified for 480, now twice the bow's range. Relaxing them is an owner decision.
- Spawn walking distance is uneven. Spawns within `MAX_SIGHT_CORRIDOR` of each other are screened against the sim's ranged hit cone (every aim ray passing within `RANGED_HIT_REACH` of the other's centre meets a wall first). But the walking distance from spawns to the coliseum centre varies a lot: max/min per map is 1.60 on average and 2.51 at worst over seeds 1-100 (an earlier measurement said 1.54 and 3.07). The owner's target is 1.2. Meeting it needs spawn selection reworked around walking-distance targets.
- Sight corridors narrower than one tile are not capped. Mapgen guarantees the 480 u limit for 32 u strips only. 24 u strips measured up to 473 u and 16 u strips up to about 580 u (earlier measurements, not re-run). A 24 u gap holds a player (`PLAYER_RADIUS` 12). The owner deferred guaranteeing these.
- Extraction leftovers: mapgen still places `extracts` (`ExtractZoneDef`, `EXTRACT_RADIUS`) and keeps chests out of their circles. Nothing in the game reads them, but removing them would move every seeded layout.
- Not built: the 30-second warning and host voice line before the teleport (GAME_DESIGN 6 and 15 describe them), the minimap pings for bountied players (the crown is built), quest NPCs, raid bosses and the rest of GAME_DESIGN 2.2.

Weapons and factions (numbers in `testing/`, the controls rework's in `testing/TUNING_CONTROLS.md`; the owner's open decisions are listed in `testing/TUNING_10.md` section 8)
- Weapon tuning (9.1, `testing/TUNING_9_1.md`; the controls rework, `testing/TUNING_CONTROLS.md`): kiting is held back by short ranges (bow 240 u, wand 220 u) and by the windup roots, not by move slows (the old 0.1x ranged multipliers and the ranged recovery are gone). A shooter that orb-walks (roots for its windup at each shot, walks at full speed between) gives a chaser about interval / windup times the free fire of one that stands, so **the ranged windups are the anti-kiting lever**: bow `min(0.6 s, 0.92 x interval)`, wand `min(0.4 s, 0.8 x interval)` (`BOW_WINDUP`/`BOW_WINDUP_SHARE`, `WAND_WINDUP`/`WAND_WINDUP_SHARE` in `shared/src/weapons.ts`, matched by the `windup`/`wshare` columns of `testing/realtime.py`). `testing/test_kite.py` judges the guarantee against an orb-walking shooter (`realtime.orbwalk_free_fire`, a DT 0.05 kinematic model of the TS rules; it assumes no attack-speed buffs) and passes all 20 cells; the tightest is Fire > Plague with the bow at x1.06 (the axe the weakest melee weapon: 1.23 s of tolerance against 1.16 s of orb-walk free fire; standing it is 1.06 s, margin x1.16), then Fire > Plague with the wand x1.08. `testing/kite_windup_sweep.py` finds the smallest windups that hold (bow share 0.89 at margin 1.0, wand 0.75). A Frost shooter walks a chilled chaser (x0.7 inside 100 u) back out to 100 u after every shot, so the chaser must cover the last 40 u inside ONE windup: a Frost windup under about 0.31 s keeps it out of reach for good. **The wand's cap must stay at or above about 0.35 s** (at the old 0.2 s the two Frost-loser wand cells are infinite). Real sim (`testing/TUNING_CONTROLS.md`): the policy matrix holds **9 of 10** edges (Wand > Shield fails at **23%**: the harness wand backs away from a charging shield; with both fighters locking each other it holds at 100%), the **target-lock pass holds 10 of 10**, and the KITING section's perfect kiter (`orbwalk`) is worst at **x1.40 for the wand at its 0.4 s cap** (sword vs wand, 1.05 s against 0.75 s of a motionless one; the bow x1.06). A longer wand root did not fix Wand > Shield (0.6 s / 0.8: 20%; 1.0 s / 0.95: 76%, but Axe > Wand fell to 73% and the Frost wand to 0%), so the wand stays at 0.8 / 0.4 s; the ranged slows were not brought back. A longer bow or wand, or a lower melee number, is tested against the kite check and the harness.
- Controls rework: best guesses the owner may overrule. A windup is committed (a move does not cancel it, as it would in League: mobs and the harness hold the trigger while moving and must still fire), and a move given during it waits for it. The click snap is `TARGET_SNAP_RADIUS` 64 u, and an empty left click does nothing (no attack-move). `TARGET_RANGE` 640 u is both the accept range and the leash. `TARGET_LOS_GRACE_MS` is 1.5 s, counted only once the target was seen; a lock needs no line of sight (the browser check showed clicks on enemies behind cover doing nothing when it did). The lock survives a swap or a pickup. The shield faces the locked target, else the cursor. A locked projectile is aimed once, at launch, and flies straight (dodgeable). The bow stays immune to stagger. The game client no longer sends `attack`/`release`, so nothing in the browser holds the trigger across a teleport or reconnect.
- Weapon edges, real sim (`testing/TUNING_CONTROLS.md`; the axe at 0.77 is unchanged from 9.1): against a straight charge, the harness's `weave` (55 degrees off the line, a new side every 0.4 s) and `jink` (50 degrees, every 0.3 s) nine of ten hold. Bow > Axe needs the axe at 0.77 (the window is 0.76-0.77: 0.75 and below break Axe > Wand, 0.78 and above thin Bow > Axe's Frost column). Since the controls rework Bow > Sword (100%) and Bow > Axe (96%, Fire 78%) are no longer thin in the Fire column. Thin spots: Wand > Bow in the Frost column against a strafing or kiting bow (33% / 0%), Axe > Wand in the Fire column (67%), and Wand > Shield, which fails in the policy matrix (23%, only the Plague column above 50%) and holds when both fighters lock (100%). Open owner question (GAME_DESIGN 18).
- `SIGNATURE_WEAPONS`: Sentenced stays on the bow (measured; a best-guess decision for the owner to overrule). On the sword, Sword > Wand decides Holy > Sentenced in the real sim (Holy wins 0 of 18 setups), and the axe fails it too (Holy wins 14 of 18). The bow holds all four of Sentenced's openings (policy mode, re-run after the controls rework: Holy > Sentenced keeps 24.4% at worst, 24.7% before). `testing/TUNING_10.md` section 7, GAME_DESIGN 10.1.
- Same-faction weapon edges flip with signatures on (owner decision, nothing retuned): in a Fire mirror Sword > Axe goes 100% to 0% and Sword > Wand to 11%; in a Sentenced mirror Sword > Axe, Sword > Wand and Axe > Wand go to 0%, because its damage is almost all the mark times the weapon's `dpsMult`. The weapon harness runs with signatures off by default. `testing/TUNING_10.md` section 8.
- Frost's axe against a chilled shooter was thin because the chill stretched the cooldown but not the ranged recovery, so a chilled shooter walked away between shots. The recovery is gone: a chilled shooter now roots for its windup and walks between shots (the orb-walk model does not apply a Frost chaser's chill to the shooter: conservative). Not re-measured in the real sim yet (`testing/TUNING_CONTROLS.md` open question 6; the old owner question is in GAME_DESIGN 18 and `testing/TUNING_10.md` sections 4 and 8). Still logged there: the shield mirror stalemate (two shields block every bash; the second weapon slot is the design's answer) and Fire's backlash per minimum-draw bow tap (the bow no longer has a minimum draw, so that one is moot).
- Lifesteal counts the whole hit, including overkill on a killing blow of a PLAYER and hits on training dummies that refill. Kept for parity with `testing/realtime.py`, which counts it the same. Regional mobs are capped: what lifesteal feeds on is the hp the hits removed (`ledger.ts`, `landedShare`). A lifesteal cap above 100% is not an option: it stalls Holy against Holy (`testing/TUNING_10.md` section 2). Lifesteal is applied after the tick's damage, so on Holy's death tick its same-tick heal can't save it (`realtime.py` nets the two); it only shortens fights Holy loses.
- Signatures need a trade: a hit or block between the pair within `ENGAGE_TRADE_SECONDS` (3 s), so a bow-range DoT faction (Sentenced, Plague) kiting a melee chaser keeps its signature with one shot every 3 s. `DUEL_PACE` 2 halves every kiting tolerance in `testing/COUNTER_REVIEW.md` while free-fire time (set by range and move speed) stays the same. Owner decision.
- `tieRank` (`sim/world.ts`, the target choice between equal hits) is keyed on the same secret `orderSalt` as `actionOrder`. A client that stages about 32 ties and reads the outcomes (brand/sig) could brute-force the salt (2^32) and predict same-tick item races. A separate salt would shift `world.random`'s sequence, so it waits for a reason.

Mobs
- Strength and spacing were measured with one scripted player per duel (`bench/mobDuel.ts`), never with humans or camp-mates. Expect playtests to move `MOB_K` (0.45), `ELITE_K` (0.65) and `MOB_LEASH_RADIUS` (9 tiles). A player who stands and fights (`--style stand`) finishes a normal mob in 24 of 25 starter-against-region pairings and an elite in 23 of 25; the default `policy` style, where ranged players back away, loses 5 of 25 normal pairings.
- Known holes: a Frost shield starter cannot finish a Frost shield mob (both block), so the second weapon is the answer (owner decision pending). A chasing mob's swing hits every standing player in its arc, so a player can drag an elite onto someone who never touched it (the leash limits it). A wand mob cannot hit a player standing on top of it (a ball that starts inside a body only hits if it heads into it). A retreating shooter drags a melee mob to its leash, where it evades and heals, so a ranged starter must burst a melee mob down inside one round.
