# CLAUDE.md — RougeHalla (package name `raid-br`)

Top-down 2.5D roguelike battle arena. Up to 8 players pick a faction, loot, farm mobs and fight. The last one standing wins Glorious Victory (GV, cosmetics-only). Phaser 4 client, Colyseus 0.18 authoritative server, npm workspaces monorepo. Colored shapes only. Design and numbers: `docs/GAME_DESIGN.md`. Running and playing: `README.md`. Faction ids are `fire`, `sentenced`, `plague`, `frost`, `holy` (shown to players as Demon Blood). Weapon ids are `sword`, `bow`, `wand`, `shield`, `axe`. The roguelike overhaul (zones, typed camps, contested chests, skills, relics) is planned in `docs/ROGUELIKE_PLAN.md`; built so far: R0 (contracts), R1/R2 (the zone map generator at 96x96, the map pool and its consumers), R3 (the planning phase and screen), R4a (the per-mob-type buffs and mono-type camps) and R5 (the camp runtime: camp-wide aggro, a contested shared skill chest per cleared camp, 21 passives, the training room's practice console). Zone terrain (collision classes, hazards, the five zone stylers, the zone art) is wired into the generator's hook (ZT-6): every map the game builds is themed (`MAP_STYLERS` on). Active skills, relics, the buffs' on-hit statuses (R4b) and boons are not built (the rules below say which). Each faction's Wish (`D`: `freeze`, `swarm`, `trial`, `blaze`, `lastStand`; GAME_DESIGN 8.8) and the status runtime and ability framework under it (8.9) are built.

npm run dev            # server :2567 + client :5173 (concurrently)
npm test               # vitest in every workspace (about a minute; the server suite includes the e2e bot runs)
npm run typecheck      # tsc --noEmit in every workspace
npm run build          # production client build into packages/client/dist (Vite does not type-check)
npm run bots -- 3      # 3 headless bots join the running dev server
npm run bots -- -- 3 --url http://host:2567   # flags (--url, --prefix, --faction <id|rotate|random>, --loop to keep queuing, --verbose) need the second `--`: the root script nests npm, which eats them
npm run harness -w @raid/server               # weapon duel harness (report only, never fails; ~50 s): matrix, style grids (ranged stand/strafe/kite, melee stand/weave/jink), edge verdicts (HOLDS/FAILS, with thin faction columns), TARGET LOCK (both fighters click each other), kiting (shooter styles incl. `orbwalk`, the perfect kiter, and `lock`). `-- --core` skips the sensitivity passes (~40 s), `-- --quick` takes a few seconds, `-- --grid-setups full` gives steadier grids (slower), `-- --kiting-only` runs only the KITING section and the KITE EDGES (the faction edges against a kiting shooter, signatures on), `-- --shooter-buff plagueRat:3,emberImp:3` gives the shooter of every kiting duel those buffs (`id:stacks`; the chaser has none) and `-- --shooter-as 1.2` an attack-speed multiplier on top (a mod source), `-- --help` lists the filters
npm run harness:factions -- --python          # faction cycle per weapon in the real sim vs testing/realtime.py (~5 s; report only). Also --mode policy (moving fighters, ~20 s), --mode full (~7 s), --nmax N
npx tsx packages/server/bench/stepBench.ts [--buffs] [--stress]  # step() cost with 8 players and the map's ~80 mobs (gate: avg < 5 ms, p99 < 15 ms; test/perf.test.ts, best of five, judged by the smaller of wall and CPU time); --buffs gives all 8 players 4 stacks of every buff; --stress is the pathfinder's worst case (every camp woken every second, players re-locking every `TARGET_REPATH_MS`; test/pathLoad.test.ts counts the searches); the CLI then runs the terrain variant (a hazard on every fourth floor tile, against the same map with the effects off; test/terrainPerf.test.ts)
npx tsx packages/server/bench/bandwidth.ts [seed=N]   # bytes/s per client, headless with the real encoder, the map's ~80 mobs (placed from `map.camps`; whole camps woken every 0.5 s): typical, heavy, idle, and typical with 5 camp chests up (gate: < 20 KB/s; test/bandwidth.test.ts)
npx tsx packages/server/bench/mobDuel.ts              # real-sim duels of a starting player against every region's mob and elite (`--style stand` is the design's measure, GAME_DESIGN 11)
npx tsx packages/server/bench/campDuel.ts             # the same against a whole mono-type camp (`--size N` mobs, 4 by default, the generator's median camp: that many normals, or the elite and N - 1), with a disc territory as on a generated map; report only. Also `--weapons` every weapon, `--seeds N`, `--cap SECONDS`, `--no-territory` (the camp pull's mobs keep the 9-tile circle too), `--map` (the camp pull on the game's zone-styled map: seed s builds the map of seed s and the duel is at one of the zone's real camps, territory, walls and hazards included), `--json FILE`, `--k X` / `--elite-k X` what-if scales, and `--sweep` with `--ks`, `--eks`, `--sizes`: pairings cleared (of 25) per MOB_K, ELITE_K and camp size
npx tsx packages/shared/scripts/printMap.ts <seed> [attempt]   # ASCII of a map: zones, territory edges, camps, chests, crates, the spawn pool, low ground (no attempt: the first that certifies)
npx tsx packages/shared/scripts/printZone.ts <seed> [zone] [--plain] [--props]   # ASCII of one zone of a generated map (lava, fences, bog, ice, light, pillars) with its footprint; --plain builds the seed without the stylers
npx tsx packages/shared/scripts/mapBench.ts [seeds=1000] [from=0] [styler=default|none|zone] [yard=<module>]   # generation cost per raw seed (every attempt until one certifies): mean/p50/p90/p99, attempts, discards, failures by reason, notes (ice cleared and frozen, rezoned tiles), the styler passes' ms, ms per stage; `styler=none` is the plain generator (no stylers), `yard` runs another generator interleaved as a load yardstick
npx tsx packages/shared/scripts/mapSweep.ts <count> [from=0] [styler=default|none|zone|demo]   # the independent certifier (test/mapCertify.ts) on every seed's pool map, plus exact strips, 16 u discs, the findPath walk ratio, the spawn-to-centre hazard exposure and the themes' presence; one JSON line (a non-empty `failed` list is a broken guarantee; it still exits 0), so ranges can run in parallel (`from=N`, not a bare number); default is the map the game builds (certifier in `styler=zone` mode: validateTerrain, every zone's floor and every territory 4-connected, hazard-free rings), `none` the plain generator, `demo` the demo hook
npx tsx packages/shared/scripts/pinMaps.ts > packages/shared/test/mapPins.ts   # re-pins seeds 0..199 (PINNED_MAPS with the zone stylers, PINNED_PLAIN without) after a deliberate generator change (see the certified-map rule)
python3 testing/test_rpsls.py                 # the faction design oracle (standard library only, ~9 s)
python3 testing/test_kite.py                  # the kiting guarantee at duel pace against an orb-walking shooter: it roots for its windup at each shot and walks between (needs numpy, ~5 s; exits 1 on a FAIL)
python3 testing/kite_windup_sweep.py          # which bow/wand windup caps and shares hold that guarantee, and the shortest Frost windup that lets a chaser arrive (needs numpy, ~10 s)
python3 testing/test_kite.py --shooter-as 1.08 [--shooter-dmg 1.1]   # the same 20 cells with every shooter buffed (attack-speed and outgoing-damage multipliers; the chaser never is)
python3 testing/kite_buff_sweep.py [--jobs N] # how much a buff on the shooter can add before that guarantee breaks: the largest attack-speed multiplier that holds all 20 cells, Plague Rat's row at 3 stacks / one camp / the plateau, a damage row (needs numpy, ~30 s on 8 cores; report only; numbers in testing/TUNING_ROGUE.md)
python3 testing/realtime_report.py            # the 20 Hz model's report (needs numpy, ~40 s)
python3 testing/weapon_reference.py           # prints the parity tables to paste after a weapon number changes (needs numpy)

Server env overrides (see `packages/server/src/config.ts`): `RAID_PORT`, `STASH_FILE` (the profile file; the name predates profiles v2), `MIN_PLAYERS`, `LOBBY_SECONDS`, `FILL_SECONDS`, `PATIENCE_SECONDS` (at 8 alive), `PATIENCE_MIN_SECONDS` (at ≤3 alive; default 40% of `PATIENCE_SECONDS`), `SUDDEN_DEATH_SECONDS`, `PLAN_SECONDS` (the planning phase after the lobby, 12; 0 skips it), `FIRST_PATIENCE_SECONDS` (the first patience timer of a run, flat, 300, or `PATIENCE_SECONDS` when only that one is set; 0 = it scales with the players like the later ones), `TRAINING_IDLE_SECONDS`, `WISH_LOCK_SECONDS` (default 45: how long every Wish stays locked after the run starts; the e2e uses 5), `COLYSEUS_LATENCY` (simulated ms), `DUMMIES=1` (training dummies and a weapon rack next to every spawn in arena runs too), `MOBS=0` (no regional mobs: they are on by default, one at every camp spot), `MAP_POOL` (certified maps the pool keeps ready, 8; 0 = no worker thread, every room certifies its map on the main thread). Client: `VITE_SERVER_URL`. A dev build of the client exposes `window.__raid = { scene, room }`.

## Architecture rules (do not break)
- **Authoritative server.** Clients send inputs only (`move`, `stop`, `target`, `aim`, `attack`, `release`, `swap`, `pickup`, `plan`, `cast`, `choose` (a pick at a camp's shared chest), and `train` (the practice console, accepted in a training room only): `CLIENT_MESSAGE_TYPES`). The game client sends `target` and `cast` and no longer sends `attack` or `release`; they are the low-level trigger that mobs and the weapon harness still use (the bots click their foe, like the game client). Never accept positions, damage, or outcomes from a client. Apart from a walk target, the numbers a client supplies are aim angles, a render time `t` (clamped to `MAX_REWIND_MS`, only on `attack`/`release` and `cast`; a Wish never rewinds, so a cast's `t` only sets `CastRuntime.lagMs`, which nothing reads yet), a slot (a weapon slot, or an ability slot `wish`/`q`/`e` on `cast`), a container id, a fighter id (`target`, and a `cast`'s unit target `id`), the cursor's ground point `x, y` on a `cast` (always sent, clamped like a `move`'s point: a point or direction for the ability, ignored by a self cast), an option index 0 or 1 and a ready flag (`plan`), a pick index (`choose`: -1 skips; `train` adds catalog ids, a rank and a stack count, in training rooms only) and an order number `seq` (an integer 0..255 on `move`/`stop`/`cast`; a bad one is dropped and the order still counts). `step.ts` `applyMove` copies a player's `seq` into the synced `PlayerState.moveSeq` on the tick it applies the order, and `handleCast` does the same for a `cast` that carries one, accepted or refused (a refused blink is then un-predicted at its ack): nothing reads it but the client, which learns from it when its order took effect (the prediction's delay, `net/localMotion.ts`).
- **Fixed 20 Hz tick.** Message handlers validate and enqueue; they never mutate game state. `enqueueClientMessage` returns false for a rejected message, and only an accepted one counts as presence (training's idle limit). The sim consumes input queues at the start of each fixed 50 ms step.
- **Sim is pure.** `server/src/sim/*` must not import `@colyseus/core` or touch clients/sockets. It mutates the schema state and a non-synced runtime struct, and returns events. The Room converts events into messages and persistence. Test the sim headless.
- **Tick order is fixed** (`sim/step.ts`; do not reorder): inputs (players in the shuffled `actionOrder`, then mobs) → abilities (`updateAbilities`: statuses and areas expire, every cast due lands, a Trial zone ends when its subject leaves it) → target locks (`updateTargets`) → weapon state machines → `afterWeapons` → movement → history → projectile sweep (present time, 10 ms substeps) → spawns → melee (rewound) → `beforeDamage` (signature damage, then status damage: trail contacts and `dot` ticks) → sudden death's burn (recorded into the ledger) → ledger (status changes made inside it wait for its end) → systems → settle. The abilities phase was ADDED by the Wishes; nothing was reordered. It runs before the locks so a fighter that just became untargetable loses its locks in the same tick. That is the run's tick (`active`); the lobby and planning ticks are separate (next rule).
- **Planning phase** (`sim/planning.ts`, `step.ts`). With `SimConfig.planSeconds` above 0 (the live server's `PLAN_SECONDS`) a closing lobby goes `planning` → `active`; unset or 0 keeps today's flow exactly, training forces 0, and a room test that wants that flow sets `planSeconds: 0` and `firstPatienceSeconds: 0` (`loadConfig({})` now plans). The Room locks at planning start (joins are refused from then on), `RaidState.planEndsAt` is set and every player is dealt two spawns from `map.spawnPool`. A planning tick drains every player's inputs in the tick's secret `actionOrder` and applies only `plan` `{ spawn?: 0|1, boon?: 0|1, ready?: boolean }`, an index into the player's OWN two options, never a pool index or a position; everything else is dropped (a `plan` in any other phase too), nobody moves or is hurt, and no mob exists yet. The first to pick a spawn holds it, and within one tick the secret order decides, never the join order; picking the other option frees the first; `ready: true` latches (`PlayerState.planReady`) and freezes the picks. It ends at `planEndsAt` or once every CONNECTED player is ready (a dropped one does not hold it up): `assignSpawns` places everyone (a pick stands; the rest take their first free option, then the other, then the free spawn nearest in walk) and `startRaid` runs as ever. **The first patience timer** is `firstPatienceSeconds` flat (live `FIRST_PATIENCE_SECONDS` 300; unset or 0 = the usual scaling), armed there, after planning; later timers scale. **Deals are private**: drawn only from `world.rewardRandom` (never `world.random` or the public seed), kept in `world.planning`, and sent to a player only as their own `plan` message (`PlanMessage`: `endsAt`, `spawns` as pool indexes, `taken` = held by ANOTHER player's pick, `pick`, `boons` (empty until R7), `boon`) when planning starts, on every change to it and on a reconnect (`RaidRoom.sendPlan` → `planFor`); the synced state holds `planEndsAt` and `planReady` and nothing else (a test compares two differently dealt worlds). The two spawns of a pair lie in one walking tier (within `PLAN_WALK_TOLERANCE` 8% of a shared value, `sameTier`) and in different zones, and no spawn is dealt twice while 2 × players ≤ the pool; when tier pairs run out the deal keeps as many as it can and fills with the closest walks in different zones. A dropped player KEEPS the seat (`allowReconnection`, as in the run, not the lobby: the room is locked, so a blip would cost the whole run) and gets the default spawn without a pick. **Leaving during planning is MIA** (owner ruling: planning is part of the run, so nobody can see the deal and requeue for free; only the lobby is free to leave): a consented leave, or a drop whose reconnect grace ran out, goes through `removePlayer` → `missInPlanning` (`sim/arena.ts`): a `resolved` result with outcome `mia`, `place` = the players still in the room, 0 GV, which `recordRun` counts as a run and a death (`runs + 1`, `deaths + 1`); no body, no kill credit, no settle. `leavePlanning` then frees what they held. The leaver stays a STARTER (`PlanningRuntime.starters`, set at planning start, feeds `startedWith` in `beginRun`), so the win-bonus gate counts them; with one player left in a room that started planning with two or more (`lastOneStanding`) the run starts at once and the next tick's settle makes that player the winner with the bonus withheld (nobody was damaged). A shutdown during planning voids the run instead (`RaidRoom.onLeave` while `shuttingDown` → `abandonPlayer` + `bankVoided`: no result, nothing recorded). The void is sticky: `abandonPlayer` sets `world.arena.voided` in planning as in the run, and `updatePlanning` returns at once while it is set, so a tick between two abandons can never start the run (`lastOneStanding`) and hand the last player a win; only `beginRun` clears the flag, and a voided room never reaches it. `fighterOut "removed"` fires for every planning leave, and the Wishes' cleanup tolerates a fighter with no statuses, cast or `world.abilities`.
- **The ledger: one way down, one place to settle.** Every hit (projectile sweep, melee, signature damage) is recorded with `recordHit` (`sim/ledger.ts`) and applied all at once by `applyLedger`. Each hit is multiplied by its attacker's outgoing multiplier (next rule), mitigated per victim, then goes to `applyHits` for a player (`sim/arena.ts`), `hurtMob` for a regional mob or `damageMob` for a dummy. Sudden death's burn is a ledger entry too (`suddenDeath`, recorded after `beforeDamage`: all true damage, from `SUDDEN_DEATH_KILLER`, no `hit` fx, no kill credit of its own), so it lands in the same pass as the tick's hits. Every exit from the fight (death, leave) goes through `downPlayer`. In-tick results come only from `settle()` at the end of the tick, so the shuffled input order never decides a winner. A fighter killed this tick still lands what it started. Simultaneous hits on one victim land together, and the kill goes to the largest rival hit. Simultaneous last deaths go to the higher hp fraction at tick start (an exact tie draws).
- **The outgoing multiplier is fixed at the start of the pass.** `applyLedger` computes every entry's multiplier (`outgoingMult`, `sim/mods.ts`) before any victim takes damage, from the hp as the pass began, so the order victims are processed in never changes it, and applies it to the entry's raw damage before `mitigateShares`, together with the status runtime's `damageFactor` (Trial's zone; the status table is frozen during the pass, so it too reads the same for every entry). It is 1 + the attacker's damage sum + every `vs` row whose test holds against the victim + every `scale` row's bonus: rows within the damage key ADD (two +5% rows are +10%). It covers the attacker's weapon hits and its signature damage, damage-over-time and the mark included (that is how a damage buff reaches Sentenced, whose damage is nearly all its mark), and NEVER an ability entry (`e.ability` set: a Wish's damage and its `dot` chunks keep a multiplier of 1; flat power, see Statuses, abilities and areas; owner ruling "Keep Wishes flat") or the arena's burn; mobs have no rows. `vs` tests `hpAbove`/`hpBelow` read the victim's hp fraction, the others are false until R4b. A `scale` row (Penitent) adds its `per` for every WHOLE `step` of the owner's missing hp (10% steps).
- **Spoils are paid after the pass.** While `applyLedger` runs (`world.combat.collecting`), a kill's GV, bounty (and the buffs it moves), buff grants, drops, a trigger's heal and a camp's clear (its fx and chest) are queued with `payLater`. They run once every victim has taken their damage, from the lobby median feed as it stood before the pass, so a reward never decides who survives (sudden death's burn is in the pass too). A killer who goes down in the pass keeps the kill and its GV but gets no raised bounty and no rampage announcement. Outside the pass (`applyDamage`, tests) `payLater` runs at once. A mob's kill goes to the player who did it the most damage over the whole fight, not whoever lands the last hit. A mob that finishes a player a rival hit within `KILL_CREDIT_SECONDS` credits that rival (kill GV and bounty), as leaving does.
- **`hitLanded` is a hook, not a rule engine** (`WorldHooks`, called in `applyVictim`, `sim/ledger.ts`; `chainHook` adds to it). It fires once per ledger entry that took damage (mitigated amount above 0, so not sudden death's burn and not a victim that nothing got through to; DoT entries count), after the victim's damage and its `hit` fx, still inside the pass (`world.combat.collecting`, so kill spoils are still queued). It gets `(world, entry, applied)`, `applied` being the damage after armor and shield. Unset it costs nothing, and a hook must never change who survives or what a later entry of the same pass sees, or the ledger's order would matter. R4b's on-hit effects hang here: they decide from a snapshot taken at the start of the tick (or defer what they write until the pass ends, as `payLater` does; `addStatus`, `removeStatuses`, `cleanse` and `displace` already defer themselves, see Statuses, abilities and areas), and what they apply counts from the next tick. Nothing consumes it yet. 
- **`hurt` is the hook for a survivor's own hp** (`WorldHooks`, chainable; `applyVictim`, `sim/ledger.ts`). It fires once per victim per pass, after that victim's hits landed together (the arena's burn included) and before their `hit` fx and `hitLanded`, only if they took damage and are STILL standing, with `(world, c, applied, hpBefore)` (`applied` is what reached the pool, the whole hit under a Last Stand floor, so a "crossed the threshold" test reads `hpBefore`, the hp as the pass began, never hp + applied). A handler decides from that fighter's own state alone and defers what it pays with `payLater`, so it can never change who else survives the pass. Blood Saint's and Second Wind's `trigger` rows (`on: "hpBelow"`, `sim/factions.ts`) hang here: a `once` row fires the first time a pass leaves its owner below the threshold, even if it already was when it got the row (`PlayerRuntime.fired`, per run); other rows when a pass takes it across. `heal` with `ignoreLockout` skips the 3 s out-of-combat lockout and nothing else, and with `ms` it is spread over time (`startHealOverTime`); `barrier` grants through `grantBarrier`; `status`, `cleanse` and `cooldown` actions do nothing yet.
- **Statuses, abilities and areas** (`shared/src/status.ts`, `abilities.ts`, `blink.ts`; `sim/status.ts`, `fields.ts`, `displace.ts`, `abilities.ts`; GAME_DESIGN 8.8 and 8.9).
  - **One status runtime, one table.** `sim/status.ts` is a leaf: it imports only shared, `buffs`, `mods` (a leaf), `combatant` and `world`, and what a status DOES to a cast, a windup or an area is `sim/abilities.ts`, called through the hooks below. `STATUS_RULES` (`shared/status.ts`) is the ONLY place for a kind's max time, cap, stacking (`any`/`sum`/`max`/`product`), cleanse class (`soft`/`hard`/`never`), effect bit and `playersOnly`: never hard-code one elsewhere. An instance is (kind, source id, ability ?? tag): re-applying extends `until` (at most now + `maxMs`) and keeps the larger `value`, or accumulates with `add: {per, cap}`; different instances combine through `statusValue`. Readers ignore an instance past its `until`, `updateAbilities` removes it, and a stale one counts as a fresh application. `addStatus` returns null for a `playersOnly` kind on a mob (`invulnerable`, `hidden`, `deathFloor`) and for a fighter that is not standing. `invulnerable` raises `immuneUntil` (never removed early). The bits live in the synced `effects` (`refreshEffects`, written only on a change; `EFFECT_HIDDEN` only outside the reveal window, `EFFECT_CASTING` while a cast with `castMs > 0` is pending); the statuses themselves, casts and reveal times are server-only. `STATUS_KINDS`, `ABILITY_IDS` and `FIELD_KINDS` are wire orders: append only.
  - **The status table is frozen during the ledger pass** (`world.combat.collecting`). `addStatus`, `removeStatuses`, `cleanse` and `displace` called then queue themselves with `payLater` (they return null or empty) and run once the pass is over, still in the tick and before `systems`, so `damageFactor`, `floorHp` and immunity read one consistent table and the shuffled order decides nothing. `fighterOut` clears wait the same way. A status applied by a hit therefore counts from the next tick's damage, and lifesteal (a system) already sees it.
  - **Hooks** (`WorldHooks`, chainable; `sim/abilities.ts` installs them): `statusApplied(world, c, st, fresh)` (after the bits: a stun cancels the weapon windup, the bow's draw included, its cooldown spent, and a stun, silence or root interrupts a cast whose def lists it; applying a `slowAttack` calls `recomputeMods`, and `removeStatuses` (so a cleanse, an expiry, the teleport's clear) calls it when one is removed, so no weapon reads a slow that is gone), `attackStarted` (`startAttack`: a hidden attacker is revealed), `staggered` (when a stagger takes: interrupts a cast that lists `stagger`; no Wish does), `fighterOut(id, "down" | "removed")` (`downPlayer`, `killMob`, `removePlayer`, `abandonPlayer`) and `runEnded` (`endRun`). The sim reads statuses through guards: `cannotMove` (stunned, rooted or casting a cast with a cast time; `statusMoveMultiplier` is a `world.moveModifiers` entry that returns 0 for it, else `(1 - slowMove) x hasteMultiplier`), `actionBlocked` (stunned or casting: no attack start, swap or pickup; a cast with no cast time lands in its own tick, never counts as casting, and so blocks nothing queued after it), `isStunned` (facing frozen: `applyAim`, `handlePress`, `handleRelease`; `follow` does not chase, aim or fire; a stunned mob's inputs are drained and lost and its AI does not think), `isUntargetable` (see Swarm below). A stunned or rooted player's `move`/`stop`/`target` still apply and are walked or fought afterwards; a shield still blocks while stunned. Attack slow is a `world.modSources` source (`attackSlowSource`: an `asMult` of `1 - slow`), so the stat mirrors stay the one source of truth for attack speed.
  - **The cast pipeline.** A `cast` input becomes an `ActionCommand`; `handleCast` (players only) validates in this order and a refusal changes nothing (no cooldown, no fx) except that a `seq` is echoed in `moveSeq`: the slot holds an ability (`abilityInSlot`: `wish` is the faction's Wish, `q`/`e` are empty until skills), the run is active, the caster stands, the coliseum teleport is not within `CAST_TELEPORT_GRACE_MS` (300 ms: a cast that was aimed at the world before the teleport is refused, and a refusal is free; `world.abilities.teleportedAt`), `castBlocked` (the def's `blockedBy`: Wishes list stun and silence, a root does not stop one), no `rt.cast` already, `now >= slotReadyAt`, then the target (`unit`: `validUnitTarget` within `range + CAST_RANGE_SLACK`, standing, hostile, not evading, not untargetable, not teleport-immune, in line of sight on `collisionMap`; `point` with a blink: `blinkLanding` is not null). Accepting spends the cooldown at once (`abilityCooldownMs`), stores a `CastRuntime` in `rt.cast` (OUTSIDE `PendingAction`: it roots through `castMs` but only its def's `cancelledBy` ends it; Wishes list `stun` and `silence`, so a sword stagger never wastes one), faces the target or point, and, for `castMs > 0` or an `ownOrder`, cancels the caster's weapon windup (`cancelLockedWindup`, else `cancelAction` plus a `cancel` fx); an `ownOrder` (the blink) also drops the lock and the path, and a `dropsLock` (Swarm, a best guess: a locked auto-attack would reveal it at once) drops the lock only (`dropLock` also takes a locked caster's chase with it; a walk the caster ordered itself survives the cast root and goes on after it, so an escape does not stop you). The lock survives any other cast. `updateAbilities` (the phase) expires statuses and areas, then lands every cast due in TWO passes: pass 1 re-validates all of them against the state as it stood when the phase began (a failure is `cancelCast("fizzle")`), the survivors stop casting, then pass 2 applies all their SELF effects and then all their TARGET effects, each in the tick's secret rank, through an exhaustive switch over `AbilityEffect` (a new verb is a compile error until it is handled), so no processing order decides an outcome; then zones, then the bits. **Fizzle costs:** refused at validation is free; accepted and then failing at landing (`castEnd` `fizzle`) or interrupted (`interrupted`) keeps the cooldown spent; the coliseum teleport cancels a cast and REFUNDS it (`prevReadyAt`, `castEnd` `cancelled`); a death, a leave and the run's end cancel without a refund.
  - **Displacement and areas.** `displace(world, c, to)` is the one forced move: it sets the position, resets the rewind history to `to` (as the teleport does), re-plans a walk in hand from there (dropped if unreachable), bumps `PlayerState`/`MobState.displaceSeq` (uint8, wrapping), and restarts the lock of every player who has locked the fighter ("not seen yet", re-plan at once), so a blink through a wall is chased to, not dropped by the line-of-sight grace (the `TARGET_RANGE` leash still bounds it). Areas are `FieldRuntime`s in `world.abilities.fields` (null until first use: every entry point tolerates that), mirrored ONCE into the synced `state.fields` (`FieldState`) and deleted when they end; the server never updates one (a cloud is drawn at its owner's drawn position, `vx`/`vy` are for a later moving area). Zones and clouds end with their owner, a trail outlives it (as a projectile does), and the teleport and the run's end remove all.
  - **Ability damage is named.** It goes through `recordHit` under the caster (`by`) with `weapon: null`, `ability` and, for damage over time, `dot: true` (`LedgerEntry`, `LandedHit`), so kill credit, the bounty, `lastHit`, mob threat and the mob kill credit work unchanged. `contactsOf` skips it (it never starts or keeps a signature engagement); it feeds lifesteal and the heal lockout's combat clock like signature damage. A `dot` entry makes no `hit` fx of its own: `abilityDotFx` (a system) reports one per victim and source every `DOT_FX_MS`, with the ability code as the fifth tuple element, and the client draws no damage flash for `isAbilityDot`. `statusDamage` (a `beforeDamage` entry) ignites a trail's contacts (anyone standing on it but its owner, not evading and not teleport-immune, gets a `dot` status from the owner) and then records every active `dot` instance as true damage: the generic ticker, so an on-hit burn needs no code of its own. Trial lives in ONE place, `applyVictim`: it multiplies each non-arena entry's raw by `damageFactor(attacker, victim)` before mitigation (a zoned subject's outgoing damage by `dealtMult`; damage to it from the zone's caster by `takenFromSourceMult`; several zones multiply; the arena's burn is exempt; the `zoned` status carries `dealtMult` as its `value`, so `statusValue(zoned)`, a product kind, is what the subject deals now and 1 when it is not zoned). Last Stand lives in `applyHits`: `floorHp` holds hp at `min(floorHp, before)` and adds the whole `total` (after mitigation and the kill barrier, including the overkill it prevented) to the status's `taken`, and `applyHits` then returns that `total` (what reached the pool) instead of the hp removed, so a hit on a fighter already at the floor still staggers it, shows its number, lands in `world.combat.landed` and reaches `hitLanded`; its heal is `healShare` of `taken`, paid at expiry or by the teleport through `heal(..., { ignoreLockout: true })` (an anti-heal still cuts it).
  - **Flat power, one funnel.** No ability number reads buffs (the ledger skips ability entries in `outgoingMults`, so a caster's damage, `vs` and `scale` rows never touch a Wish's damage or its DoT ticks; Trial's `damageFactor` still applies): `haste` ADDS `value x PLAYER_SPEED` (`hasteMultiplier(base, bonus) = 1 + bonus / base`), trail damage is true, and neither chill nor attack speed stretches a cast or a cooldown. `abilityCooldownMs` is the only place a cooldown is computed (a `flat` def ignores reduction; a training world gives a Wish `TRAINING_WISH_COOLDOWN_SECONDS`). Trial's ±20% is the one relative number (owner rule).
  - **Lifecycle.** Death, leaving and `abandonPlayer` (`fighterOut`, deferred in a pass): `castEnd` `cancelled` with the cooldown spent, every status removed with no heal, the zones and clouds the fighter owns and the zones it is the subject of removed (no stun), its trail stays. The coliseum teleport (`teleported` hook): every cast refunded, every status and area ended, a Last Stand still pays. The run's end (`runEnded`): everything cleared, nothing paid. Expiry: a `hidden` ends its cloud, a `zoned` its zone, a `deathFloor` pays. A dropped connection leaves casts and statuses alone (everything drawable is synced, so a reconnect is right at once). `raidStarted` (`armWishes`) sets `wishReadyAt = raidStartedAt + wishLockSeconds x 1000` (`SimConfig.wishLockSeconds`, env `WISH_LOCK_SECONDS`, default 45; ready at once in training) and clears statuses, casts and areas.
  - **Swarm (the `hidden` status).** It hides on the CLIENT (`PlayerView` draws no remote hidden fighter, the local one at 0.45 alpha; `targetable(effects)` keeps it out of the click pick) and the SERVER makes it untargetable: `lockable` refuses it, locks on it drop in the same tick (`updateAbilities` runs before `updateTargets`), `lockedFoe` never re-aims at it, `validUnitTarget` refuses it, and a mob's `pickTarget` skips it (the threat is kept; with no one else the mob gives up and walks home). Casting it drops the caster's own lock (`dropsLock`, a best guess) but not its walk: its locked auto-attack would otherwise reveal it at once, and a Plague that wants to ambush clicks its target again. Its own attack or cast reveals it from the NEXT tick (`reveal` sets `revealFrom = now + TICK_MS`, so a reveal applied mid-phase by `attackStarted` or `handleCast` never changes what another fighter reads in that tick, whichever joined first) until `landsAt + HIDDEN_REVEAL_MS` (500 ms); being hit does not. A second Swarm while the first is up (training's 5 s cooldown) replaces the first cloud and extends the one status. Projectiles in flight, swings along their start aim, areas and signatures still reach it, and its position stays in the synced state (see the Known TODO on cheating).
- **Target lock** (`sim/targeting.ts`; `setLock`/`dropLock` in `sim/weapons.ts`; synced as `PlayerState.attackTarget`, "" = none). `target {id}` locks an enemy and the server plays the fight from then on, as mob AI does for a mob: each tick after the inputs, `policies.ts` `decide` with `lockSpacing` (close in to the weapon's `far`, then stand; never back off or strafe) sets the path (re-planned at most every `TARGET_REPATH_MS`, only when the goal moved over 8 u or the path ran out), holds the trigger while the target is in range with a clear line, and aims at its present position and velocity. The client's `aim` is ignored while locked, and `facing` follows the target (the shield's block cone reads it). Accepted only for another combatant that is standing, not evading, hostile (not self, not mob to mob; only players lock), within `TARGET_RANGE` (640 u); anything else is ignored with no change. Line of sight is not needed to lock (a target behind a wall is chased around it), only to attack, but a target out of sight with no path to it is refused (a mob across the locked coliseum gates; the client also offers no mobs while `gatesLocked`). Clicking the fighter already locked changes nothing; a new lock clears the earlier walk. A `target` order costs at most one path search per `TARGET_REPATH_MS` per player (`lockSearchAt`; an order out of sight sooner than that is refused, and its search doubles as the chase's first plan), and the chase's own re-plan time (`lockPlanAt`) survives setting or dropping a lock, so spamming orders (up to `MAX_ACTIONS_PER_TICK` a tick) never buys extra searches. `endRun` drops every lock, so a winner's `attackTarget` is not synced through the linger. Dropped (trigger and path cleared, the fighter stops where it stands) when the target is no longer standing, is evading, is past `TARGET_RANGE`, or has been out of sight for `TARGET_LOS_GRACE_MS` (1.5 s; until then the chase paths around the wall) after having been seen once since the lock (`lockSeen`; a target locked behind a wall is chased until first seen, bounded by the leash), when it is out of sight and the chase finds no path to it, or the player holds no weapon. **Orders replace each other in arrival order within a tick** (`InputQueue.moveBefore`, like `aimBefore`): `move`/`stop`/`attack` drop the lock (an unreachable `move` still does), `target` lets go of the trigger. **A player's own order cancels the attack its lock is winding up** (`cancelLockedWindup`, `sim/weapons.ts`, LoL's move-cancels-windup): a `move`, a `stop` (applied in `step.ts`, an unreachable move included) or an accepted `target` on another fighter, while its `PendingAction.target !== undefined` and it has not landed. No swing, ball or arrow; the cooldown is refunded (`readyAt = startedAt`, it was over when the attack began); the root goes (`cancelAction`); the bow's `drawStartedAt` clears; a `cancel` fx tells every client to drop that fighter's telegraph, and the walk starts in the same tick. Re-clicking the locked fighter (or, once the lock has dropped, the fighter the attack is already aimed at), a refused `target` and a landed attack (the axe's root after its swing stays) cancel nothing, and neither does an `attack` input. `releaseTrigger` (teleport, going down, a dropped client, training revive) drops it too; a swap or a pickup does not. An attack the lock starts records its `target` on the `PendingAction` and is aimed again as it lands (a swing straight at the target's position at its rewind time) or leaves (`leadAim` from the drawn origin at the target's present position and velocity), if the target still stands and is hostile; then it flies straight and can be dodged. An unlocked attack (a mob's, the harness's) keeps the old aims: a swing and a ball go where they were aimed when the attack started, an arrow along the aim held when its draw ends (the bow's aim at release), and `decide` leads the bow for the lags alone, without its windup. A locked attack has no client `t`: `lagMs = TICK_MS`.
- **Windups root.** Every attack roots its fighter from its start until the swing lands or the arrow or ball leaves (`moveMultiplier`: 0 while `action !== null` or inside `rootUntil`, else 1; nothing else slows a walk: buffs and Frost's chill are `world.moveModifiers`). A directional windup (a mob's, the harness's, an `attack` input) is committed: a `move` given during it is kept as the path and walked afterwards, only a stagger (not on the bow) or a swap cancels it. One the target lock started is the player's own click, so the player's next `move`/`stop`/`target` cancels it too (see Target lock): the game client walks away from a windup it no longer wants. The bow is a fixed windup (kind `"draw"`, `landsAt`, `drawStartedAt` synced for the pull), never a partial draw. `weaponTimings`: sword and bash 0.1 s, axe 0.25 s / 25% of the interval and root 0.5 s / 50%, wand `min(WAND_WINDUP 0.4 s, 0.8 × interval)`, bow `min(BOW_WINDUP 0.6 s, 0.92 × interval)`. These are the anti-kiting lever (below, Weapons and factions).
- **Players and mobs fight through `Combatant`** (`sim/combatant.ts`). Weapons, melee, projectiles and the ledger take either; only how they go down differs. A regional mob's faction is its region's scaled by `MOB_K` (elite `ELITE_K`) and paced, read through `factionOf` like a player's, so signatures, armor and timings apply to it unchanged.
- **Mobs are players who send inputs.** `sim/mobAI.ts` is a system (after damage). It pushes `move`/`stop`/`aim`/`attack`/`release` into the mob's own `InputQueue`, and `step.ts` applies them next tick through the same handlers as a player's. Idle mobs send nothing, and mobs never lock a target. A mob walking home (`return`) is evading: `hurtMob` returns 0, `isEvading` keeps it out of hit tests, signature targets and contacts, it starts nothing new (a shot already in the air still lands), and it is whole when it arrives. It gives up when it leaves its leash or 6 s after it last *dealt* damage, so kiting from outside its leash gains nothing. **The leash is the camp's territory** (`leashOk` in shared `mobs.ts`, ROGUELIKE_PLAN D15): a mob of a camp whose territory holds its home spot (`camp.area` > 0) stays on that camp's `territoryGrid` cells and within `min(camp.radius, MOB_LEASH_CAP)` of its home, the cap being 12 tiles (generated camps measure a radius of 10.8 to 30 tiles, so the cap binds on almost all); any other mob (no camp, `area` 0, an all-zero `territoryGrid`, a spot outside the territory: hand-built maps and tests) keeps the `MOB_LEASH_RADIUS` 9-tile circle. A ranged mob backs off only to points whose four ±24 u axis neighbours are inside the leash too. The coliseum teleport puts every mob back on its camp spot at full hp. Mobs never hurt each other (a hit is recorded with scale 0) and their shots fly past each other. A training world places no mobs of its own (the console's practice camps aside).
- **Signatures ride the ledger.** Faction bonus damage (burn, backlash, disease, mark) is recorded in the tick's ledger in the `beforeDamage` phase, so it lands with the tick's hits. Heals go through `heal()` in `sim/factions.ts` (3 s out-of-combat lockout; every lifesteal is exempt, and `ignoreLockout` skips only the lockout: Blood Saint). Three buff effects live in this module, so none of them runs in a world built with `signatures: false`: **lifesteal** works for any faction from `lifesteal` rows, capped at `LS_CAP` 0.25, Holy's own comes on top, the total never passes `LIFESTEAL_MAX` 1 (`lifestealShare`); **`markRate`** makes Sentenced's mark's engaged time grow (1 + rate) times as fast toward the same cap (it does nothing for anyone else); **Blood Saint** is the `hurt` trigger above. `sim/factions.ts` stretches chilled fighters' `readyAt`, bow draw (its start and the moment the arrow leaves, so the cycle stays interval / chill) and press buffer every tick; the other windups are not stretched, so a chilled swing still lands on time. Weapon timing changes must keep the chill working: `npm run harness:factions` checks it against `testing/realtime.py`. A landed stagger (the 0.5 s immunity starts) pauses the staggered fighter's burn, disease and mark for its weapon's windup (`staggerPause`; none for a bow, whose draw a stagger never cancels; the real sim only, `realtime.py` has no staggers).
- **Buffs and the feed** (`shared/src/buffs.ts`, `sim/buffs.ts`, `sim/feed.ts`). Every mob type is also a buff (`BuffId` = `MobTypeId`; `BUFFS` in `MOB_TYPES` order: zone, elite flag, `effects` rows valued at 3 STACKS (D6), `worksWith`/`counters` tags). A mob kill grants stacks of the buff of ITS type: `MOB_BUFF_STACKS` 1.1 × m (`ELITE_BUFF_STACKS` 3.1 × m for an elite), m = the reward curve × the catch-up (`payMobKill` → `grantBuff`, through `payLater`). Stacks live in `PlayerState.buffs` (a float32 map by id; only players hold buffs). At n stacks every number of a buff is scaled by `buffScale(n)` = S(n)/S(3), S(x) = sigmoid(x − 3) − sigmoid(−3): 1 stack 0.16×, 2 0.49×, 3 1×, 4 1.51×, 6 2×, a plateau of about 2.1× (an on-hit effect's `cap` never moves). The bounty (`transferBuffs`, on the `bountyClaimed` hook) moves half of EACH buff id the victim owns. Rows that need statuses (`needs: "status"`: the `onHit` rows of Chain Warden, Bloatfly, Rot Monk and Frost Wisp, Inquisitor's streak and Glacial Warden's slowed `vs` rows) are catalog data: the HUD and tooltips show them, nothing applies them until R4b. The kill combos, kill bursts, kill shield and the old three-stat stacks are gone (the `combo` fx is retired); `barrier` stays for R6's skills. The reward curve and the catch-up read the feed (`kills + 0.25 × mob kills`); the **bounty reads player kills only**. A mob kill's grant no longer draws from `world.random` (the old stat roll did), so loot rolls after a mob kill differ from before. "Shield" in a buff's text is the magic-resistance stat (D7), not the barrier.
- **Stat mods: the mirrors are the one source of truth** (`shared/src/mods.ts`, `effects.ts`, `sim/mods.ts`). `PlayerState.asMult`, `windupMult`, `speedMult` (uint16 THOUSANDTHS, 1000 = ×1) and `armorBonus`, `shieldBonus` (int16 TENTHS of a point) hold the stats that effects change. The quantized value is authoritative (D22): `recomputeMods` writes a mirror only when its quantized value changed (so it patches only then), and the sim reads back the DECODED value (`decodeMult`/`decodeFlat`), never the double it folded, so a client decodes exactly what the sim used. Readers: `attackSpeedMult`/`moveSpeedMult`, `timingsOf` (`windupMult` through `scaleWindup`: the windup, and the axe's root with it), `defenseOf` (the flat bonuses). Max hp, the damage sum, lifesteal and the mark rate are read from the build's sums, not mirrored. A player's build is its buffs' rows (`buffRows`, `needs` rows left out) and its live passives' rows (the Passives rule), rebuilt only when its buffs or its build change. The fold: `stat`, `flat` and `while` rows ADD within a key, a multiplier key becomes `1 + sum`, different keys MULTIPLY where the sim combines them (attack speed with damage, `speedMult` with the chill), flat rows add points; `vs`, `scale`, `onHit` and `trigger` rows do not fold; a row whose `requires` ids are not all owned is off. Every `world.modSources` entry is asked too (multipliers multiply in, flats add). **`AS_MULT_CAP` (1.5, owner ruling) caps attack speed from ALL sources**: `mirrorsOf` multiplies the rows' fold and every source's `asMult` (the Wishes' `slowAttack` included), then `capAsMult`, then encodes, so the capped value is the one on the wire and the one the sim, the local prediction and the bow art decode; a slow multiplies the uncapped product, so it only shows once the product is under the cap. Nothing else is capped this way: the damage rows stay uncapped on purpose (fed players may beat their counters). The kite model (`testing/test_kite.py`) holds only to x1.25; the real-sim harness holds to x1.5 (`testing/TUNING_ROGUE.md`). Folding is event driven, never every fighter every tick: `grantBuff` (so `transferBuffs`) re-folds at once, so a grant changes the attack and the walk in the same tick; a source whose answer changes must call `recomputeMods`; `updateMods` (the last `world.systems` entry; `gameplay.ts` installs it last) checks only players that own a `while` row and, with sources registered, every fighter's answer. Cinder Hound's `chasingLock` holds while the player has a target lock (on or off, so its mirror patches only when a lock starts or ends) and is re-checked once a tick, so the mirror follows the lock one tick late, by design. A mob has no synced mirror (what a source gives it stays server-side). `sim/mods.ts` is a leaf: it must not import `weapons.ts`, `arena.ts`, `ledger.ts`, `buffs.ts`, a status runtime or anything else that imports it (type-only imports are fine).
- **Clients decode the mirrors, never recompute them.** The client reads `PlayerState.buffs` only to DISPLAY them (the build strip, tooltips, the buff toast). The local prediction (`net/localPrediction.ts`) and `FighterArt` read only the decoded mirrors (`decodeMirrors`/`decodeMult`/`decodeFlat`; `scaleWindup` for the bow's draw and the axe's root, `fullDrawSeconds` takes WIRE values), never stacks or rows, and `sync.test.ts` compares the mirrors bit for bit. A client test fixture spreads `WIRE_IDENTITY_MIRRORS` (1000, 1000, 1000, 0, 0), never 1; to regenerate `SERVER_FULL_DRAW` in `fighterArt.test.ts`, run the server's `timingsOf` on a new `PlayerState` with the mirrors set through `encodeMult`.
- **Camp rosters are mono-type, rolled at world build and published** (`shared/src/rosters.ts`, `sim/camps.ts`; ROGUELIKE_PLAN D5). Before anyone joins, each camp of `map.camps` gets one normal mob type and `RaidState.camps[i]` (`CampState`: `type`, `alive`, `state` (next rule) and `reward` "" until R7) holds it at the camp's own index; a training world or one with `mobs: false` publishes none. Every non-elite mob of a camp has the camp's type, and the zone's elite stands at the `eliteSpot` of its elite camp (the rest of that camp is the camp's normal type). Types are drawn per zone without repeats, zones in first-seen order, from `world.rewardRandom` only (never `world.random`, so the loot rolls and every test's scripted sequence are what they were): a generated zone has four camps, so its three normal types each stand in one camp and a fourth camp repeats one (counts 1, 1, 2; the first three camps in camp order are always distinct); a hand-built map's zone with fewer camps lacks a type. Mobs still appear at `raidStarted`: `spawnRegionalMobs` walks `map.camps` and sets each mob's `MobState.type`, `.camp` (index + 1) and name from the roster and `MOB_TYPES` (a mob placed with no type falls back through `mobTypeOf`), `killMob` counts `alive` down, and a world assembled without `gameplay.ts` gets its roster from `ensureRosters` when mobs spawn. The roster is public from the lobby on, by design (the planning screen shows each camp's type and buff); only what is rolled after it stays private (the `rewardRandom` rule).
- **A camp is cleared for good** (`sim/camps.ts`; `CampState.state` 0 idle, 1 engaged, 2 cleared). `hurtMob` engages a camp on its first damage (sticky: it never goes back to 0). `killMob` calls `campMobDied`: `alive` counts down and the last death sets state 2 at once, even when nobody gets the kill (mob kill credit is unchanged), then queues the `campCleared` fx and hook with `payLater`, so the chest appears after the ledger pass. Camps never respawn and nothing re-opens one: the coliseum teleport only puts the LIVING mobs of uncleared camps back on their spots at full hp. Every camp, elite ones too, drops a skill chest until R7 sets `CampState.reward`.
- **Camp-wide aggro** (D24; `CAMP_WIDE_AGGRO` in `constants.ts`, a one-line flip; `mobAI.aggro` → `wakeCamp`). Each damage to a member wakes every other IDLE, living member of its camp (`MobState.camp`) onto the same target, even when the hit mob was already fighting. A LETHAL hit wakes them too: `killMob` calls `mobAI.wakeMatesOnKill` with the credited killer (the same rules: `CAMP_WIDE_AGGRO`, a standing killer only, not a hidden or untargetable one, idle mates only, no recursion; a one-hit kill used to leave the camp asleep). The mates hold the target with 0 threat (`threat` is set only if absent), so a mob's kill credit, which reads its own threat, is unchanged and a pull never earns a kill. A returning (evading) mate ignores it, a hidden or untargetable target (Swarm) is never handed on (the hit mob's own fight drops it too, so the mates wait for a hit on someone they can see), and a stunned mate does nothing until the stun ends. Off, each mob wakes on its own damage only.
- **The camp's shared chest** (`sim/chests.ts`, `shared/rewards.ts`; plan D1-D3, D12, D16, D17). One reward container (`kind "reward"`, never a weapon container: `pickup` says "Nothing to take", `containerWeapon` returns null) is created from the `campCleared` hook, after the pass, at `CampDef.chest` (the camp's centre when that tile is a wall). Its options come from `world.rewardRandom` only (never `world.random`), rolled with NO build because one chest serves everyone: each picker's own ranks decide what a pick gives. The interim rule (`CHEST_RULE` "interim" until R6 switches to "d6"): `CHEST_OPTIONS` (3) = ONE live passive of the camp's zone as card 1 (none when the zone has no free live one, so Fire and Frost give neutrals only until R4b) + live neutrals, no duplicates; an owned rank-1 passive is offered and gives rank 2, one at rank 2 is refused. Synced on it: `camp` (index + 1; 0 for the console's), `expiresAt` (`CHEST_SECONDS` 15 after the drop, never extended), `options` (SkillIds in card order), `takenBy` (parallel; "" free) and `pickers` (took or skipped). The contents are public by design (D17: contested, and they survive a reconnect; the UI shows them only in range; see the Known TODOs). The chest goes exactly at `expiresAt` (`expireChests` runs after the tick's inputs, which already refuse it), at the coliseum teleport and at run end (`clearChests`).
- **`choose { chest, pick, replace? }` is an action** (active run, alive players, resolved in the shuffled `actionOrder` like a pickup, so the secret order decides a same-tick race and the loser gets a toast and may pick again; `replace` is R6's, accepted and ignored). `handleChoose` checks in this order and a refusal uses up nothing: standing player (silent); not stunned or casting (`actionBlocked`: "Can't do that now"); the chest exists, is a reward, was not born this tick and `now < expiresAt` ("Chest gone"); the SERVER position within `CHEST_RANGE` (96 u; "Too far away") with a clear line on `collisionMap` ("Can't reach that"); not already in `pickers` ("You already picked"); then `pick` -1 is a skip, any other index the chest lacks is ignored silently, an option taken by another is refused ("Already taken"), one the picker holds at rank 2 too ("Already at rank 2"). Success sets `takenBy`, joins `pickers`, `grantSkill` (rank 1 or 2 in `PlayerState.build`, `recomputeMods`, `syncMaxHp`) and sends `chestTaken { chest, by, option }`. One pick per player, a skip counts. A pick is not a reveal (see the Known TODOs).
- **The skip (D12)** heals `SKIP_HEAL_SHARE` (15%) of max hp through `heal()`, so the 3 s out-of-combat lockout applies; if that heals nothing (in combat, or at full hp) it pays `GV_SKIP` (3) GV instead, reason `skip`, in the `GV_MOB_CAP` pot (`awardSkipGv`; none in a training room, so no "+3 GV" toast there).
- **Passives are effect rows** (`shared/skills.ts`: 21 passives of two ranks, in `PlayerState.build`, id → rank). `ready` says whose machinery they need and `LIVE_SKILL_READY` (`["r5"]`) says which are live: only the 9 live ones (Whetstone, Swift Boots, Quickdraw, Thick Hide, Bounty Hunter, Second Wind, Witness, Pestilence, Last Rites) are rolled or folded, the rest are catalog data and inert. `sim/mods.ts` folds the live rows with the buffs' (same sums: stat, flat and `while` rows add within a key, damage rows share the one sum; a rank's `byFaction` rows replace its `effects` for that faction), rebuilt when the buffs or the build change. The `vs` tests beyond hp are answered by the ledger's `vsProbe` from the state at the START of the pass, like every other outgoing-multiplier input: `higherFeed` (Bounty Hunter, players only) and `thirdParty` (Witness: the victim's lock, its mob fight target or its signature target names anyone but the attacker). Pestilence gives a Plague fighter an `executeBand` stat row (`executeBandOf`: 0.5 + the sum, so 60% hp at rank 1 and 70% at rank 2; `EXECUTE_BAND`, `signatures.ts`) and everyone else a `vs hpBelow 0.6` damage row. Last Rites is a stepped `while hpBelow` attack-speed row (its mirror patches only when the condition flips). **Second Wind** is a `trigger` (hpBelow 0.25, `once`) whose heal is spread: `ms` 2000 is `healOverTimeSteps` = four steps of `HEAL_OVER_TIME_STEP_MS` (500) of 5% max hp (rank 2 7.5%), the first with the pass, the rest from the `healOverTime` system, so it SPANS 1.5 s (`healOverTimeSpanMs`, which its text says: "over 1.5 s"); the coliseum teleport drops the steps still to come (`dropHealsOverTime`), so a re-armed rank 2 never pays two heals; each through `heal({ ignoreLockout: true })` (an anti-heal still cuts it; a fighter who goes down loses the rest). Both ranks share one once-key, so an upgrade does not re-arm it; rank 2's `rearm: "teleport"` forgets the key at each coliseum teleport.
- **The training console** (`train { cmd: "buff" | "passive" | "camp" | "chest" | "clear" }`; `shared/training.ts`, `sim/training.ts`) is for training rooms only, behind three locks: `enqueueClientMessage` drops it unless the Room passes `{ training: true }`, only `installTraining` registers `world.actions.train`, and the handler re-checks `world.config.training`. A bad id, a non-integer rank, a non-finite amount or a bad option list refuses the whole message (not presence). `buff` SETS stacks (default 3, clamped 0..12, 0 removes); `passive` sets a rank (0, 1 or 2) of any known skill (a non-live one is set but inert, and the toast says so); `camp` places 3 mobs of a type (one for an elite type) asleep on free floor about 7 tiles away, with pseudo camp numbers 101..255 so camp-wide aggro pulls them together (no `state.camps` entry: no clear, no chest); `chest` drops a reward chest about 2 tiles away with 1 to 3 chosen skills, or 3 random live ones for the player's faction, on the normal 15 s clock; `clear` removes buffs, passives, practice mobs and chests (the dummies and the rack stay), ends the projectiles the practice mobs have in flight (`clearProjectilesOf`, reason `cleared`: they would still land) and re-arms the once-per-run triggers. Caps: 12 practice mobs alive, 150 spawned per room (the roster never shrinks), 6 chests up, 300 ms between camps and between chests. Practice kills pay nothing (`payMobKill` returns in training: no GV, feed, buff or drop), nor does a chest skip (`awardSkipGv` returns 0).
- **Bots take one pick per chest** (`bots/chestHunt.ts`, pure; `BotClient` sends it). A reward chest within 88 u (`CHEST_RANGE − CHEST_PANEL_SLACK`) with a clear line and over 350 ms of life gets exactly ONE `choose`, even mid-fight, and is never retried whatever the server answers: the best free option the bot can use (own faction's pool +4; damage, attack speed and hp rows most; held back if it needs a weapon the bot lacks; ties go to the first), else a skip. It waits out a stun or its own cast first (the server would refuse and the one try would be spent). Otherwise it walks (`move` only) to the nearest chest that has a usable option, a path and enough life left; in a fight or with an awake mob within 220 u only if the chest is within 12 tiles, never while retreating or in the coliseum, and it gives up a walk that stops closing in after 3 s of walking to THAT chest (the record is per chest id and counts only walking time, so a fight that keeps interrupting the walk neither resets nor feeds it). `BotClient.chestStats` is `{ seen, tried, taken, skipped }`.
- **The chest panel is display plus `choose`** (`ui/chestPanel.ts`, `chestMath.ts`). A non-modal Chrome card at the right edge (z 8, under the map screens, toasts and chrome) whose root and box are click-through: only `.cp-card` and `.cp-skip` take the pointer (mouse clicks blur the button at once; a mouse click in the first `CHEST_PANEL_CLICK_GUARD_MS` 250 ms after the panel opens is ignored, so a spam-clicking cursor cannot take a pick it never saw), so a canvas click still locks and a right-click still walks. The cards and Skip have `tabIndex` -1 until C focuses the panel (restored on leave, on focus leaving it and on close), so a stray browser Tab cannot put the focus inside, where the digits and Esc would stop being the game's. It opens from the latest SERVER position (`PlayerState.x/y`, never the predicted one) within `CHEST_RANGE − CHEST_PANEL_SLACK` (88 u) with a clear line, and shows the contents only then; once open it closes only beyond 92 u (`PANEL_CLOSE_RANGE`, `CHEST_PANEL_HYSTERESIS` 4, `pickReward`'s `openId`), so weaving on the edge neither flickers it nor drops `pending`. Keys are physical codes: C focuses it (ignored while a `[role=dialog]` has focus), then 1/2/3 pick, 0 skips, Esc or C leave; Esc and the digits are consumed only while the panel has focus (capturing window keydown), so 1/2 still switch weapons and Esc still leaves training otherwise. A reward chest is never an F target (F stays the weapon pickup). R6's `choose.replace` goes in `ChestPanel.choose()`, a slot-replace prompt between `pick()` and `choose()`.

- **Combat netcode.** Projectiles are not in the synced state: they are plain objects in `world.projectiles`. A projectile is announced once, in the `fxs` batch of the step that loosed it, and never updated. Clients fly it from `(x, y, vx, vy, t)`, and a `projEnd` fx says where and why it stopped. A client that joins or reconnects mid-flight is sent the projectiles then flying as a batch of its own (`FxChannel.inFlight`, queued behind its full state by core). Melee samples the attacker and every target at the attacker's render time (`rewindT`: the client's `t` on a low-level `attack`; a locked attack, which is all the game client makes, has none and rewinds one tick, and the server aims it from the present: the target lock). A projectile leaves from the shooter's rewound (drawn) position, and the `aim` angles that low-level attacks and the shield use are measured from where the client draws its own player: since the local fighter is predicted, that is the PREDICTED position, which is where the server will have it when the aim lands (closer to the server's present than the old delayed one). Locked attacks stay server-aimed from the present; `attack`/`release` users (the harness, mobs) keep the rewound origin and `t`. Keep those three consistent.
- **Wire format.** All fx of a step go out as ONE `fxs` message (`shared/src/fxCodec.ts`, `rooms/FxChannel.ts`): integer tuples, fighters named by index into the append-only `RaidState.roster`, projectile launches in the same batch (`FxBatch.p`). Players still in the lobby are not rostered (no fx names one, and an entry is for good). A mob is rostered when it is placed. `unpackFx(batch, room.state.roster, onDrop?)` needs the client's copy of the roster: without it every id-bearing fx is dropped, and `onDrop` is how a skipped tuple is noticed (the client warns once in dev builds; the e2e run asserts nothing was dropped). The client holds `fxs` batches from the join until the scene starts (`net/fxInbox.ts`). The code tables are wire format: grow them at the end, never reorder (the newest fx kinds are R5's `chestTaken`, 19: `[19, chest, by, option]`, a pick at a camp's shared chest (the chest's container id travels as a string, never a roster index; option -1 is a skip), and `campCleared`, 18: `[18, camp]`, the camp's index in `map.camps`; R5 appended them after the Wishes' kinds when the two lines merged, the Wishes being on `main` first. Before them `status`, 17: `[17, id, status, ms, by|null]`, a status instance newly applied; after `castEnd` 16, `castLand` 15 and `cast` 14 for the ability casts, and `cancel` 13, a player's own order cancelled its lock's attack; abilities and status kinds travel as their index in `ABILITY_IDS` and `STATUS_KINDS`, so those lists only grow at the end). A `hit` fx carries an optional fifth element, the ability code, for damage an ability dealt (its weapon is null); a reader that predates it ignores it, a bad code drops the tuple. `castLand` carries `x2, y2` together, only for a blink's landing. `buff` (10) is `[10, id, B, stacks × 1000, total × 1000]`, B being the buff's code 0..19 in `MOB_TYPES` order (the BUFF table: append a type at its end); kind 11, `combo`, is retired with the kill combos: the encoder never emits it, its code is never reused, and the decoder drops it through `onDrop`. Adding a field to an `FxEvent` means adding it to its tuple and to `packages/shared/test/fxCodec.test.ts`. Synced numbers are narrow on the wire (float32 positions and hp, uint32 timers); the server keeps doubles.
- **The map is never synced.** State carries only how to build it: `seed`, `attempt` (the certified generator attempt) and `mapHash` (uint32 of `mapHashU32(map)`: the 32-bit FNV-1a of every gameplay layer: seed, attempt, size, `tiles`, `terrain`, `regionGrid`, `territoryGrid`, camps, spawn pool, regions, ruins, crate and ground spots; NOT the cosmetic `props`), set once in `createWorld`. The server, the bots and every client run exactly `generateMap(seed, attempt)`: that one attempt, never a loop (it throws when the attempt does not certify). The server and the bots build with `decor: false` (no `props`, drawn from a stream of their own so no other layer moves); the client builds with decor, and a test guards that both hash the same. A client whose map hashes to anything else shows "This raid's map did not match your client. Please reload." and leaves with a consented leave (`net/roomMap.ts`, `main.ts`: the profile is freed at once); a bot throws (`roomMap`). `generateMap(seed)` without an attempt loops: for tests, benches and tools, never for a map a peer must match. Loot contents are rolled server-side with a non-public RNG. While `state.gatesLocked`, movement, line of fire and loot line of sight use `collisionMap(world)` (`withGates(world.map)`), never `world.map`. `coliseumSpots` hands out the coliseum's inner spawns. `RaidScene`, `MapView`, `PlanningView` and the minimap take the map as a parameter and never generate it.
- **Generated maps are certified, with no relaxed attempt** (`mapgen.ts`, `zones.ts`, `cover.ts`, `coliseum.ts`; `test/mapCertify.ts` re-checks every guarantee below from the `GameMap` alone). `generateMap(seed, attempt?, { styleZones?, decor? })` (`styleZones: null` builds the plain map with no stylers, the `styler=none` of the benches): with an attempt, exactly that one (throws when it fails); without, attempts 0, 1, ... until one certifies (a guard throws after 64). `tryAttempt(seed, attempt)` is the map or null; `certifiedMap(seed)` the first of `MAX_ATTEMPTS` 16 that certifies, or null (the pool discards that seed). Any failed check fails the attempt; nothing is ever relaxed. **Determinism:** one `mulberry32` stream per attempt (`seed` for attempt 0, else `seed + attempt * 0x9e3779b1`), drawn in a fixed order (changing the order moves every map: re-pin on purpose with `scripts/pinMaps.ts`); only `+ - * /`, `sqrt`, `floor`, `ceil`, `round`, `abs`, `min`, `max` (`detSin`/`detCos` in `cover.ts` are built from them), never `Math.pow`, `exp`, `log`, `atan2`, `hypot`, `sin`, `cos` or `random` (a test spies on 23 Math functions through a generation, lane tables included); integer value noise, integer 5/7 chamfer distance transforms and heap keys; total comparators (value, then tile index). Hot imports are copied to module constants in `zones.ts`, `cover.ts` and `mapgen.ts`: under vitest each use of an import is a property read (30% slower).
- **What an attempt certifies** (96x96; the numbers are in `zones.ts`, `mapgen.ts`, `coliseum.ts`).
  - *Connectivity and gates:* all walkable floor is one 4-connected piece with the gates open; with `withGates` closed the arena is sealed, in one piece, and the rest is one piece. Four straight 4-wide gates (n, e, s, w) are floor in `map.tiles` and the only links between the arena and the rest; a clear lane lies in front of each. The coliseum is the same fixed layout on every map (one of 8 pillar variants per seed).
  - *The 480 u sight cap:* with the gates open, no 32 u-wide strip of sight-open ground is longer than `MAX_SIGHT_CORRIDOR` (also inside the coliseum with the gates closed). It is certified on the fine lattice (48 directions, lines a quarter tile apart, every lane at most 14.98 tiles) **anchored at `LATTICE_ORIGIN`**, the coliseum centre less (32, 32): the pillar layouts, shifted by `CX - 32`, were certified where they sat at 64x64, and from a corner anchor some leave a 15.5-tile lane inside the footprint that no rock may cut. `longestLane` and the tests use the same anchor. The independent certifier also measures the exact strip at off-lattice angles (longest 464 u) and bounds 16 u discs at 576 u (every 10th seed); narrower gaps stay unguaranteed (Known TODOs).
  - *Zones:* five, each one 4-connected painted piece and each one's walkable floor one 4-connected piece too (the cover prefers a rock that keeps a zone's floor locally connected, and the generator checks it), painted areas within 8 tiles of each other (`AREA_TOLERANCE`; equal within 1 tile before the territory repair), walkable floor share max/min <= 1.15, at least 24 ring-road tiles each (`RING_CONTACT_MIN`: every zone touches the coliseum), at most 100 sliver tiles (`SLIVER_MAX`). They are grown "paint bucket" style from a ring-road arc joined to an outer seed by its spine, so there are no ridges or passes: zones meet directly, and the order of the five around the ring is shuffled by the seed. Every tile off the border wall is a zone or the coliseum in `regionGrid`.
  - *Camps and territories:* four camps per zone (`CAMPS_PER_ZONE`), one elite camp per zone (its camp farthest from the coliseum, the elite at spot 0), centres at least 9 tiles apart map-wide (`CAMP_GAP`: a camp's halo, its 2.5-tile clearing plus one tile, is protected ground, so two closer would form a lane no rock could cut). A **territory** is the part of its zone nearer to a camp than to the zone's other camps by path cost; the territories of a zone partition all its painted tiles (`territoryGrid` = 1 + camp index), and each one's floor is one 4-connected piece holding its clearing, spots and chest tile (the cover's territory guard treats a rock that would split one as a last resort; the repair after the cover joins a cut-off piece to the territory it touches (the one whose camp keeps the piece within 30 tiles when there is a choice), walls up a piece of at most `WALL_UP_MAX` 120 tiles that touches only other zones' floor when it holds no crate, pool member, camp ground or ruin and the rest of the floor stays one piece (the zone keeps its painted area), moves a piece of at most `STRAY_MAX` 40 tiles to the zone it touches otherwise (hazards of the old zone's kind on it are cleared; low ground on it fails the attempt), and fails the attempt for any other piece). The camp stands at its territory's **pole** (the deepest cell by 5/7 chamfer distance whose halo fits) and no territory floor tile is more than `TERRITORY_RADIUS_MAX` 30 tiles from it. That bound is a seating rule, not a filter (as a filter it would reject about 65% of layouts): the pole is searched only among cells within 30 tiles of every tile of the territory, the camp seeds are placed for coverage, and a zone set whose camps cannot be seated is redrawn inside the attempt.
  - *Spawn pool:* 24 to 32 members tagged by zone, in at least 4 zones, all within 8% of one BFS 5/7 walking distance to the coliseum centre, at least 5 tiles apart and from every camp centre (picked 7 away, so the cover can cut ground between a spawn and a halo), each with a plain 3x3 of floor outside ruins and no floor hazard in its 5x5, and screened so that no two members within 480 u can shoot each other (every aim ray within `RANGED_HIT_REACH` of the other's centre meets a wall first). **The pool is picked before the stylers**, on the open ground: up to 40 members within 4.5% of one contour value, their 3x3s protected from the stylers and hazards cleared from their 5x5s afterwards. Picked after the stylers, their walls and hazards left half the candidates and the pool did not survive the cover's shifts in walking distance (the cover moves a spawn's walk by 3% to 100%). After the cover and the territory repair the longest run of the pool within 8% is kept and trimmed to 32 from its extremes. The `findPath` walk ratio max/min over the pool is 1.17 on average and 1.200 at worst (seeds 0-1999; the owner's target is 1.2).
  - *Terrain (the zone stylers' layer, `validateTerrain(map, { styled: true })` T1-T11 gating every attempt):* every kind lies in its home zone; no floor hazard (ember, bog, ice, light) on a spawn's 5x5, the 3x3 of a crate, camp chest or ground-loot spot, or the camp clearing + 1; ICE has plain floor on all eight sides (T11). The cover does not avoid ice (keeping rocks off it, even as a last resort, split the Rime's territories and made one attempt in three fail): a rock clears the ICE around it, and the Rime then freezes over every clear tile it has left (`freezeClearGround`, about 40 tiles a map, 3% of its floor: the 480 u cap puts a rock in nearly every 3x3). A styler breach, a failed `validateTerrain` and a rezoned piece holding low ground fail the attempt (`A:styleBreach`, `A:terrain`, `A:rezoneLow`); `A:styleBreach` never happens on the 200 swept seeds (a test asserts it), the other two are rare normal retries.
- **The zone style hook** (`styler.ts`, `zoneStyle/hook.ts`; the zone-terrain contract). `ZONE_STYLE_HOOK` is `zoneStylerHook` while `MAP_STYLERS` (constants.ts, a compile-time switch: server, bots and clients must be built alike; `mapHash` is what tells them apart) is on, which it is since ZT-6, and null when it is off (the plain generator, for tests and what-if runs: `generateMap(seed, attempt, { styleZones: null })`). The hook is a plain adapter from the generator's `StyleState` onto `styleZones(ZoneStyleState)`: `territoryGrid` is passed as `territory`, `decor` becomes the option, `camps[].r` is in TILES (`CAMP_R`) on both sides, the generator's `protect` is the stylers' `hard`, and the `StyleResult[]` telemetry lands in `STYLER_STATS` (nothing in a map depends on it). It runs once per attempt with the whole zone grid (`StyleState`), after the zones, camps, territories, ruins and the spawn pool and BEFORE the rock chunks, the crates and the cover, so the crates' picks and the cover certification see the styled ground and its walls count as cover. It may only turn painted FLOOR outside `protect` (the border, the coliseum, the ring road + 1, gate lanes, camp halos, ruins + 1, the map corners and the pool's 3x3s) into WALL or LOW, write `terrain` kinds and append `props`, and draws from `styleRng(seed, attempt, zone, stream)` = `mulberry32(hashSeed(seed, attempt, zone, stream))` (streams 0 shape, 1 decor, 2 surface), never the generator's stream. A breach of that contract fails the attempt (`A:styleBreach`), `validateTerrain(map, { styled: true })` gates a styled attempt, and crates only take tiles with no terrain, ground spots none within a 3x3 of a floor hazard. The generator then drops props whose tile changed class, props within a tile of a spawn, crate or ground spot, `keepLow` stays empty (no styler lists a LOW tile the cover may not rock), and a test asserts that no LOW tile ever ends as FLOOR.
- **Collision classes and masks.** `tiles` is the collision layer: `TILE_FLOOR` 0, `TILE_WALL` 1 (stops everything), `TILE_LOW` 2 (fence, lava, crevasse: stops bodies and melee swings, not sight or shots). Every query names its mask (`map.ts`): `MASK_SIGHT` (= wall; eyes, projectiles, target acceptance, `lockSeen`, abilities, ranged signature reach), `MASK_MOVE` (0xff; bodies, A*, placement, pickup reach) and `MASK_MELEE` (wall | low; swings), the last through `reachMask(weapon)` (`interactions.ts`: an arc weapon gets the melee mask, a projectile weapon the sight mask), so the lock's `clear` (the `los` `decide` gets), mob `los`, the arc-weapon signature reach and the bots' attack-ready test all read it, and flipping the melee mask is one constant. `raycast`/`hasLineOfSight` default to sight; `circleClear`/`segmentClear`/`findPath` default to move. `isWallTile` means OPAQUE, never use it for movement (`server/test/architecture.test.ts` scans for it). Nobody stands on LOW: every placement checks a disc on the move mask, the ice slide collides on it, and a blink or knockback must validate its landing on it. The masks are derived views (`sightMask`, `moveMask`, `moveComponents`, cached per map object, the gated copy has its own), never `GameMap` fields; maps are read-only, a test that turns wall into floor after a query calls `forgetMapCaches`. `moveComponents` makes an unreachable goal O(1) and the lock drops a target that is provably unreachable; string pulling looks ahead at most `PULL_WINDOW` candidates. On the generator's side `cover.ts`, the territory repair and the certifier read `MASK_SIGHT` for lanes, cones and the spawn screen and `MASK_MOVE` for connectivity, sealing, the ring road, the territory guard and walking distances; probes restore the byte they saved, so a probed LOW tile never comes back as floor.
- **Terrain hazards** (`terrain.ts`, `sim/terrainEffects.ts`, `shared/walk.ts`; GAME_DESIGN 5.2). `GameMap.terrain` holds a kind per tile (none, lava, fence, crevasse on LOW; ember, bog, ice, light on floor; a WALL tile may keep a LOW kind as a pillar; append-only ids), `props` is cosmetic and never read by the sim. A fighter is judged by the tile under its centre, the home faction of the zone is exempt (Fire/ember, Plague/bog, Frost/ice) or boosted (Holy/light x2), regional mobs are of their region's faction. Ember is a ledger entry like sudden death's burn (`arena: true`, true damage, `by` "terrain:ember", no fx, not combat, credit by `recentRival`); bog is a `world.moveModifiers` entry (the product of all modifiers is clamped to `MOVE_MULT_FLOOR` 0.35 when above 0); light is `heal(..., {quiet: true})` so the 3 s lockout applies; ice replaces `advanceAlongPath` with `walkFighter` only while a fighter stands on slipping ground or still carries slide state (otherwise today's code, bit for bit), and any root plants a sliding fighter. All of it returns on its first line when the map has no such terrain or `SimConfig.hazards` is false (`SimConfig.hazards` is server-only and not synced: keep it out of live room configs or the prediction is wrong for good). `MoveModifier` takes an optional `dtMs`; burn skips a locked arena (sudden death owns that pass; the coliseum has no terrain); `TerrainRuntime.combatAt` is light's own combat clock so the 3 s lockout holds without the faction layer; `WorldHooks.arenaHurt` reports the hp an `arena` entry really removed (`HazardStats.damage`). Ice must keep one tile of clear floor around every ICE tile (`validateTerrain` T11; the slide overshoots corners and a solid neighbour livelocks it), and `slipWalk` carries a breaker for a bad map: three stuck re-plans toward one goal set `gripUntil` and the fighter walks its path exactly for about a second. `displace()` and the training revive clear the slide. The CLIENT predicts all of it: `LocalMotion` runs the same `slipWalk` while `FrameInput.slipAt(sim) > 0` (carrying its own last-frame velocity onto the ice, `regrip` and a 500 ms grace on leaving it, rebase stays position-only, `DIVERGE_ERR_SLIP` 16 while sliding), `LocalPrediction.speedMult` multiplies the bog factor read at the MODEL's position and floors the product like `step.ts`; off ice both are bit-identical to the old walk. A path-search budget note: the slide adds its own stuck re-plans (at most 4 a second per stuck fighter, none on a valid map) and a `regrip` search on leaving ice, on top of the lock's one search per `TARGET_REPATH_MS`.
- **Zone stylers** (`shared/src/zoneStyle/`, GAME_DESIGN 5.2). One pass `styleZones` per map, called by the generator's hook (previous rule), three rng streams per zone from `hashSeed(seed, attempt, zone, stream)` (shape, decor, surface; never the generator's main stream), every write through a guard (`canBlock`/`canSurface`: FLOOR in the zone, outside `protect`, a 3-tile rim from the zone edge, the simple-point test and a bounded join check so floor and territories stay connected, wall runs <= 14, the guard never closes a fence yard (the Gallows recipe gives each yard >= 2 openings), a fence detour <= 10), hazards placed in the same pass (EMBER only beside lava, no wall or LOW next to ICE), `keepLow` empty (cover may turn any LOW tile into a rock; a WALL that replaces LOW keeps its LOW kind as a pillar), props from the decor stream (cosmetic, never hashed, never read by the sim). Zone isolation holds (replacing one zone's styler with a no-op leaves every other zone byte-identical after the pass: a test on the generator's hook, and the pinned output on the synthetic open fixture `test/zoneStyleOpen.ts`). The old dev adapter that styled finished wedge maps is gone with the wedge generator. The themes on the generator's maps (a test asserts each on at least 90% of 200 seeds; the sweeps find all five on every seed): Scorch lava, embers and obsidian, Gallows fences and cell blocks, Warren bog and tunnels, Rime ice, shelves and crevasses, Sanctum colonnades and light shafts.

Floors bake into chunked dynamic textures (scale 1, 0.75 or 0.5 to fit a 48 MB budget), wall and fence strips are packed onto atlas pages and y-sorted (lava and crevasse are flat in the floor chunks), animation is four alpha buckets per overlay kind plus capped closed-form particles gated by `juiceScale`. - **Map contract** (`map.ts`, ROGUELIKE_PLAN 3.2; fully real since R2). `GameMap` carries `attempt`, `camps: CampDef[]` (`id` "fire-1", `zone`, centre, clearing radius `r`, 3-5 `spots`, `eliteSpot`, the reward `chest` tile (the clearing centre, which no spot takes), `area` (floor tiles of its territory), `radius` (its farthest floor tile)), `territoryGrid` (0 = none, else 1 + the camp's index in `camps`), `spawnPool`, `terrain`, `props`, and `regions[]` with `pole` (the zone's label point: a floor tile outside ruins) and `area` (its painted tiles). `camps` runs in `REGION_FACTIONS` order, then camp index; `regions[].mobCamps`, `regions[].spawns` and `map.spawns` (the pool interleaved by zone) are VIEWS of `camps` and `spawnPool`; `crateSpots` (3-4 weapon crates per zone) and `groundSpots` (20-30) feed `loot.ts` as before. Extraction (`extracts`, `ExtractZoneDef`, `EXTRACT_RADIUS`), the ridges and passes between zones, `regions[].anchor` and the wedge generator are gone; a hand-built map (`mapFromTiles`) has no regions or camps and all-zero grids. Read today: `camps` (the mob spawn, rosters, planning screen, bots), `spawnPool` (the deal), `pole` (labels), `territoryGrid`, `area` and `radius` (the leash), `chest` (where a cleared camp's chest drops, `sim/chests.ts` `chestSpot`), everything (`mapHash`). A map is read-only once built: the caches are per object (`withGates`, the masks, `moveComponents`; `forgetMapCaches` for a test that edits tiles).
- **Rooms take their map from the pool** (`server/src/mapPool.ts`, ROGUELIKE_PLAN D20). `RaidRoom.buildWorld` (a room's first join, a training room's too) calls `maps.take()` synchronously and hands the map to `createGameWorld({ seed: map.seed, map })`, so `onAuth` and `onJoin` stay synchronous and a room nobody joins takes none; `createWorld` without a `map` calls `generateMap(state.seed)` in process (tests, benches, the harness). One `worker_thread` per process (`mapWorker.ts`, started through `mapWorkerBoot.mjs`, with its own 44 MB of lane tables) certifies crypto-random seeds with `certifiedMap(seed, { decor: false })`, only while the queue is short (`MAP_POOL_TARGET` 8, refilled at `MAP_POOL_REFILL_AT` 6: an idle server costs nothing), and posts each whole map by structured clone (about 52 KB, 0.2 ms) with its hash; the main thread checks seed, attempt and `mapHashU32` again and drops a mismatch, so the pool serves only a certified (seed, attempt) a client can rebuild. An empty queue (a burst, a worker that is down or warming) falls back to ONE synchronous `certifiedMap` on the main thread, logged (about 35 ms, 75-120 at p99; a discarded seed moves on to the next, up to `MAP_FALLBACK_SEEDS` 8). A worker that crashes or errors restarts with a backoff of 1 s doubling to 60 s and never takes a room down. `warmMapgen()` runs at boot on both threads and shutdown terminates the worker; `MAP_POOL=0` (tests: `MapPool({ target: 0 })`) runs no worker.
- **The client builds the map off the page's thread** (`net/mapWorker.ts`, `mapWorkerEntry.ts`, `roomMap.ts`). A module Web Worker builds the lane tables (44 MB) and runs one throwaway attempt once the hub is drawn and the page idle (`warmWhenIdle`), so the first real map meets a warm JIT. `enterRoom` then shows "Building the map…", awaits `generateMap(seed, attempt)` from the worker (tile layers transferred, cached by (seed, attempt), one map object per room), checks the hash and only then registers its handlers and starts the scene; a room that closes meanwhile is noticed there. Without a worker (tests, a failed spawn) the same call builds on the page thread.
- **`world.rewardRandom` is a private stream** for reward and roster rolls (camp rosters, plan deals and chest options draw from it today; "?" kinds will). `createWorld` seeds it (sfc32, a 128-bit state) from `rewardSalt`, four words `RaidRoom` takes from `crypto.randomBytes` (never the public seed, which every client holds; a 32-bit state could be brute-forced once rolls are revealed). A number is also accepted and expanded, for tests. It is separate from `world.random` so that drawing rewards never shifts the loot rolls or the sequence tests script (`createWorld` takes exactly one draw from `random`, for `orderSalt`, and none for this), and separate from `orderSalt` because that salt also keys `tieRank`, whose outcomes a client can stage and read (Known TODOs): a stream derived from it could be brute-forced. Without a `rewardSalt` (tests, the harness) it is derived from `orderSalt` by a tagged hash, so it matches neither `actionOrder` nor `tieRank`: fine for a test world, never for a live room. Anything hidden ("?" flags, chest rolls, plan deals) comes from here and stays server-side or in private messages; a roster is rolled from here too but is published in `state.camps`.
- **Clients render in the past, except the local fighter.** Remote entities render at `serverNow − INTERP_DELAY_MS` via `SnapshotBuffer` (`shared/interp.ts`). The LOCAL fighter is predicted (`net/localMotion.ts`, presentation only: nothing it computes is ever sent, the server stays authoritative): an order walks a model at once along the same shared A* path, `drawn = sim + visual`, and each patch pulls the model back in line (`S(T)` against the model `delay` earlier, `delay` measured from `moveSeq`; small errors go into a decaying `visual` offset, never faster than the `CORRECT_SPEED_*` caps). It cannot drift or hang: an order the server never applies (lost while reconnecting) is forgotten after `ORDER_EXPIRE_MS` and does not hold the comparison off; samples off by more than `DIVERGE_ERR` for `DIVERGE_PATCHES` in a row with nothing in flight and the server not heading where the model walks (a revive, a halt, a walk it did not order) drop the model's walk; an error past `SNAP_DISTANCE` (even with an order pending, beyond what that order's walk explains) or an offset past `VISUAL_SNAP_DISTANCE` snaps to the server and plans the destination again from there; the teleport and the local death fx `cut()` it (the next sample snaps, however short the jump); the scene resets it while `room.reconnection.isReconnecting`; a click is clamped to the world as `parsePoint` clamps it. Dead, in the lobby, after the run ends, and until a teleport is drawn it is drawn from the snapshots, except that while its death or the teleport's cut is still ahead of what is drawn it stays where it was last drawn (`localDrawSource`). After a `target` it follows the server's chase (the newest sample carried one tick by its velocity): the lock is the server's. The model enters follow when a patch shows the lock (`PlayerState.attackTarget`; not while a move or stop of ours is still in flight, which would end it) or at once on a click it expects to be accepted (`expectLock`, for the responsiveness), and leaves when the lock empties; a lock that never shows within `ORDER_EXPIRE_MS` was refused, and the walk it interrupted is planned again. The scene feeds it the speed mirror and the chill (a Frost mob chills like a Frost player), and the axe's root (`net/localPrediction.ts`), and what the abilities do to it: a stun or root and a cast's own root from the `status`/`cast`/`castEnd` fx (the synced `effects` bits stand in only when no fx told of one, as after a join), Last Stand's haste added on top as the server adds it, and a blink. A Blaze Step is predicted: `castSlot` runs the shared `blinkLanding` on the predicted position, tells the prediction (`noteCast`, which calls `LocalMotion.blink`: the model and the drawn fighter jump at once, the walk and lock in hand stop being predicted, the order carries its jump so the comparison does not read the lead as a divergence) and sends the `cast` with a `seq`; the patch that acks it also shows a changed `displaceSeq`, which `LocalMotion` reads as its OWN blink (the error to the server's landing is absorbed like any other, or snaps past `SNAP_DISTANCE`: a refused blink is echoed in `moveSeq` with no `displaceSeq` change, so the whole jump is the error and the prediction is pulled back to the server), while a changed `displaceSeq` with no blink of ours behind it is a forced displacement (the model, its history and the drawn fighter all shift by the jump, with no snap test, and a walk in hand is planned again from there). `EntityInterpolator` treats a changed `displaceSeq` as a cut for that fighter, so a remote blink is not slid into. Slow magnitudes are not predicted (only a bit is synced); anything unmodelled is the server's correction. Remote fighters and fx stay in render time, so what is drawn at the local fighter (hits on it, its telegraph) plays at its predicted position: accepted.

A chip's identity is its zone colour, the zone's marker shape and, for an elite's buff, a star; the strip is click-through (`pointer-events: none`, pinned by `buffsHudPointer.test.ts`): a right-click move or a left-click lock under it, which can be about 420 px tall, reaches the canvas and the aim keeps streaming, so a chip's tooltip is found by hit-testing a passive window `pointermove` against the chips' rectangles, never by `:hover`; do not give a chip pointer events. A row the server does not apply yet is marked "(coming)". There are no kill bursts or combo UI (`ToastTone` is buff, error or ok).
- **The picture is a viewport, not the window.** `view/viewport.ts` fixes the world height every player sees (`REF_VIEW_H` projected px; wider windows show more width, capped at 21:9 with bars; below 4:3 the width stays at the 4:3 minimum), the canvas is rendered at the device density (capped at 2x and a 4K pixel budget, `settings.hiDpi` off = 1x) and the camera zoom is canvas px per projected world px. Never assume camera zoom 1 or 1 canvas px = 1 CSS px: read a pointer's world point through the camera (`screenToWorld`, `pointer.updateWorldPoint`), set a scroll with `scrollForTopLeft` or `centerOn`, and scale a Phaser camera shake by `1 / zoom²` (`ScreenJuice`). The DOM overlay `#ui` is laid out at `--ui-w` x `--ui-h` and CSS-scaled, so overlay code uses those variables and `data-ui-short`/`data-ui-narrow` instead of `vw`/`vh`/size media queries, and `getBoundingClientRect()` for anything that meets the pointer.
- **The hub is client-only.** `HubScene` has no room and no server. Its layout and walking rules are pure (`hub/hubLayout.ts`), and a station only calls back into the menu (`onStation`). What it shows comes from the REST profile.
- **Training is a mode, not a fork.** `client.create(TRAINING_ROOM_NAME)` makes a private one-seat room of the same `RaidRoom` class. The server registers two handlers (`defineRoom(RaidRoom, { mode: "arena" })` under `ROOM_NAME`, `{ mode: "training" }` under `TRAINING_ROOM_NAME`). Colyseus merges handler options over the client's, so a client cannot choose the mode. A training world has `SimConfig.training` + `dummies`: a plain dummy, a shield dummy and a rack of every weapon next to the spawn, started the moment its player joins. It has no planning phase (the Room forces `planSeconds` 0), map mobs, camp rosters, patience timer, teleport, sudden death, result, GV or stats. Three locks keep it from recording anything: `trainingSettle` replaces `suddenDeath`/`settle` (anyone down is revived), `RaidRoom.settle` and `bankVoided` return early in training (a down *between* ticks still emits `resolved`, which the Room ignores), and leaving is `abandonPlayer`, never MIA. A dropped or leaving client frees the profile at once (`onDrop` holds no seat in training). A player with no accepted input for `trainingIdleSeconds` (300) is let go: only an input `enqueueClientMessage` accepts refreshes `lastInputAt`. Every training branch sits behind `world.config.training` / `RaidRoom.training`; an arena world never reaches it.
- **GV banks at resolve.** The sim only accumulates run GV and reports it in `resolved` results. The Room banks it (`recordRun`, or `bankGv` for a run voided by shutdown). Run gear never persists.
- **Persistence is `ProfileStore`.** Mutations are synchronous in memory (nothing awaits between a check and its change), writes are coalesced and atomic (temp file, fsync, rename, directory fsync) with retry and backoff, and `flush()` runs on shutdown. A v1 file migrates on load. A file that cannot be parsed stops the server and is moved aside, never overwritten.
- **The shop is server-only.** Purchases and equips are `POST /api/profile/:name/purchase|equip` with the profile token. The client sends only a cosmetic id (and a slot). `ProfileStore.purchase/equip` check the token, the catalog price, ownership and the balance in one synchronous step, so a double spend is impossible. Spending lowers `gv` only, never `gvLifetime` or `gvByMonth` (the leaderboard ranks GV earned). Achievements are evaluated inside `recordRun`. An id lands in `achievements` once, and its reward cosmetics are granted in the same step. Win achievements and the per-faction/weapon counters count only `winQualified` wins (the win-bonus gate: `!winBonusWithheld`), so a walkover against a throwaway callsign earns nothing. Kill and bounty achievements are not gated (their rewards are unpriced; an owner decision). The leaderboard ranking is cached per month (dropped when GV is credited in it), and `you` on `GET /api/leaderboard` is sent only with that profile's own token. Equipped cosmetics reach other players as one synced `PlayerState.look` word, fixed at join.

## Conventions
- Colyseus 0.18 APIs (not 0.15/0.16 tutorials): `defineServer/defineRoom` from `@colyseus/core`, `Room<{ state: X }>`, `this.onMessage` (or `messages = { ... }`), `setTimestep` (`setSimulationInterval` is its deprecated name), `client.sessionId` (no `client.id`), a static `onAuth` for matchmake-time checks, client `@colyseus/sdk`. `RaidRoom` sets `patchRate = 0` after `setTimestep` and sends each patch itself after the step. The scene reads `room.state` every frame; there are no per-field callbacks.
- Schema uses the decorator-free `schema({ ... }, "Name")` + `t.*` builders. Give primitives `.default(...)`. No decorators anywhere.
- Only the server imports `@raid/shared/schema` at runtime; the client uses `import type` from it (it decodes by reflection).
- Tunables live in `shared/src/constants.ts`, the catalogs (`weapons.ts`, `factions.ts`, the buff rows in `buffs.ts`, `cosmetics.ts`) and the signature numbers in `signatures.ts`. Mob scale, leash, the buff S-curve and grants, the lifesteal cap, the reward curve and the planning numbers are in `constants.ts`. Loot weights are in `server/src/sim/lootTables.ts`. Units: world units (1 tile = `TILE` = 32), seconds for durations unless a name ends in `Ms`, server time in ms.
- Weapon numbers live in `shared/src/weapons.ts`: the v3 faction × weapon formula (a weapon is a % boost on the faction's rate; `attackInterval`, `damagePerHit`, `backlashPerSwing`). It must keep matching `testing/realtime.py`: `python3 testing/weapon_reference.py` prints the reference tables, pasted into `shared/test/weapons.test.ts` and `server/src/harness/parity.ts` when the design numbers change. `DUEL_PACE` (2) multiplies every faction damage number (not hp; Sentenced's mark ramp by k²) through `pacedFaction`. Sim combat reads the paced sheet through `factionOf` (`sim/combatant.ts`), never the raw one.
- Design rules the sheet left open are recorded in `docs/GAME_DESIGN.md` 9.4. Change them there and in the tests together.
- No `Math.random` in shared code. No enums or decorators (keeps tsx/Vite/TS7 happy).
- Keep comments sparse; explain *why*, not *what*.

Identity and persistence
- No rate limits beyond two narrow ones. Matchmaking verifies the profile token before creating a room or reserving a seat (the static `RaidRoom.onAuth`), and refuses a profile that is already active or opened a still-unjoined room in the last 5 s. A target order out of sight costs at most one path search per `TARGET_REPATH_MS`. In-match orders are otherwise unlimited (up to `MAX_ACTIONS_PER_TICK`): a scripted client sending `stop` then `target` every tick starts and cancels a windup each tick, which broadcasts about 40 small fx a second (one windup and one `cancel`) to the room. It's bounded and cheaper than move spam (an A* search per tick), but both want a per-player order budget. Profile creation is free: any client can `GET /api/profile/<new name>` as often as it likes, `/api` answers every origin (`Access-Control-Allow-Origin: *`), and each claim adds a profile and a file rewrite. The shop and equip endpoints have no limit either. Training rooms have only the one-active-room guard per profile, and a running room broadcasts a patch at 20 Hz until its player leaves or idles out, so many throwaway profiles can hold many rooms.
- Profiles are weakly authenticated: a random token in `localStorage`, stored in plain text in the profile file, no passwords, recovery or expiry, and no TLS. Clearing site data forfeits the profile.
- GV banks when a player's run resolves. A graceful shutdown (SIGTERM/SIGINT, uncaught exception) pays the GV earned so far (`bankVoided`). A hard kill (SIGKILL, power loss, OOM) mid-run loses it. A purchase is answered once it is in memory, before the file write lands: a hard kill in that window undoes the purchase together with its GV debit, never one without the other. Writes are batched (at most one per second; `close()` and `flush()` write at once), so the window is up to about 1 s. Under `npm run dev`, Ctrl+C reaches the server twice (terminal and tsx), and the second SIGINT exits mid-shutdown, so the last second of changes can be lost in dev.
- The profile file has a single-writer lock (`<file>.lock` holding the PID; a dead PID is taken over, and an exit hook frees it). In a container, a hard-killed server restarted with the same PID (PID 1) sees its own PID as live and refuses to start; delete the lock by hand there.
- GV can be farmed with free callsigns: the win bonus needs 3+ starters and damage on 2+ different opponents (`WIN_BONUS_MIN_*`), but two throwaway callsigns that get killed still pay kills and the bonus. Bounties are uncapped but come from player kills only (an owner decision), so a partner can only cash a bounty that real kills built. Mob GV and chest-skip GV share the `GV_MOB_CAP` cap per run.
- GV earned after a player's result went out is dropped (`awardGv`). A projectile outlives its owner and its hit still lands; a kill by a shooter who left or whose result is out is credited by name only (`killedBy`), with no GV and no bounty.
- Mob kills do not feed achievements (owner question). "Bounty claimed" counts runs that paid bounty GV (`progress.bountyRuns`), not individual claims. There is no end-of-month trophy job: the leaderboard keeps each month and nothing is awarded when one closes.
- A player who joins without picking a faction (old clients, bots without `--faction`) gets the round-robin default by join order (`defaultFaction`). A failed join or a lobby leave still uses up a slot.

Mobs
- Strength and spacing were measured with one scripted player per duel (`bench/mobDuel.ts`) and per camp (`bench/campDuel.ts`), never with humans or other players. Since R5's weaker-mobs ruling (for camp-wide aggro) `MOB_K` is 0.22 (it was 0.45) and `ELITE_K` 0.65. A starter on its signature weapon clears a FULL normal camp that wakes at the first hit (`campDuel`, `camp` pull, 12 seeds, cleared in every seed) in 21 of 25 faction × zone pairings at 4 mobs, the zone maps' mean (23 at 3, 14 at 5), and an elite camp (the elite and 3 normals) in 9: every zone's elite camp falls to at least one starter, and elites stay harder by ruling. A lone mob (`mobDuel --style stand`, the design's measure) falls in 24 of 25 pairings with about 91% hp left, a lone elite in 22 of 25 (54% left); the default `policy` style, where ranged players back away, wins 22 of 25 normal pairings. Those camp figures were first measured on an open floor with the 9-tile leash circle; with the territory leash (the camp pull's disc territory, about the median one, 330 tiles) they hold exactly (21 of 25 normal pairings cleared in every seed, 22 in at least half, 9 of 25 elite camps, 12 seeds), and on the game's themed maps (`--map`, the zone's real camp, 12 seeds) 20 of 25 in every seed, 21 in at least half, and 9 of 25 elite (the dip is the Sentenced bow against its own zone's camp, 8 of 12 seeds to 5, and one seed of its plague camp). Expect playtests to move `MOB_K`, `ELITE_K` and `MOB_LEASH_CAP` (12 tiles; the 9-tile `MOB_LEASH_RADIUS` is only the fallback). `mobDuel` fights on a hand-built floor, so its mob keeps that 9-tile circle (the nearest what-if for a generated camp is `--leash 336`, the cap `--leash 384`).
- Known holes: a Frost shield starter cannot finish a Frost shield mob or camp (both block), so the second weapon is the answer (owner decision pending). A Holy wand cannot beat a Sentenced sword camp (0 of 12 seeds: Sword beats Wand in the real sim, and against a lone one it wins only if it stands and fights), a Sentenced bow clears no Fire camp (0 of 12: four axe mobs with burn on the smallest hp pool, and the bow's 0.6 s windup root lets them close) and only 8 of 12 seeds of its own zone's. Ranged starters do worst against a camp, and more so as it grows: at 5 mobs the clears fall to 14 of 25 because five bodies out-damage them before the first kills' buffs matter. A chasing mob's swing hits every standing player in its arc, so a player can drag an elite onto someone who never touched it (the leash limits it). A wand mob cannot hit a player standing on top of it (a ball that starts inside a body only hits if it heads into it). A retreating shooter drags a melee mob to its leash, where it evades and heals, so a ranged starter must burst a melee mob down inside one round (easier since `MOB_K` 0.22).

Wishes and statuses (GAME_DESIGN 8.8, 8.9 and 18; the numbers' reasoning is `testing/WISHES.md`)
- Swarm can be cheated. `hidden` hides a fighter only on an honest client, and the server only makes it untargetable (no lock, no ability, no mob pick): every client still receives every position (the cloud marks the place anyway), and `attack`/`release` are still accepted from anyone, so a modified client can send low-level `attack` inputs at a hidden player's true position (a swing or an arrow along an aim it picked, rewound by its own `t`). The fix is interest management (`StateView`, with per-client filtering of every fx that carries a position or names the fighter: `swing`, `death`, `projEnd`, the launch tuples, `windup`, `hit`) AND refusing `attack`/`release` from game clients (only the harness and mobs need them). Owner question.
- Blaze Step and Last Stand have no pre-cast (`castMs` 0): a blink with a pre-cast is no escape and a survival button with a delay loses to burst, so their tell comes after the cast (a flare at both ends and a trail, a gold burst and a rim). Owner question whether the enemy deserves a warning.
- Best guesses the owner may overrule, nothing measured: the trail (30 true dps, lingering 2 s, about 60 per crossing, lasting 2.5 s), `TRAINING_WISH_COOLDOWN_SECONDS` 5, every cap and `maxMs` in `STATUS_RULES`, every Wish number. Last Stand pays its heal at the coliseum teleport and counts the overkill the floor prevented, so its floor can keep a fighter alive through sudden death's burn for 5 s. Trial's ±20% is relative (a fed caster gains more). A stunned shield still blocks with its facing frozen (a flank beats it). Nothing was retuned: the weapon harness and `testing/test_kite.py` never cast a Wish. The one finding in `testing/WISHES.md`: in the 20 Hz what-if, Trial's x1.2 / x0.8 over the whole of a 2.5 s Fire > Sentenced duel (inside its 5 s ring) cuts the weakest melee tolerance from 1.89 s to 0.88 s (bow) and 1.74 s to 0.83 s (wand) against 1.16 s and 1.49 s of orb-walk free fire, so Trial can flip that edge; the 0.35 s cast it costs the Sentenced is not charged there. Not measured in the real sim.
- The e2e needs a bot's Wish to land (`expectWish`, one more replay criterion beside the kill, the signature hit and the mob kill). If it ever fails the replay too, keep the invariants (every cast fx names a player and that faction's Wish, none before the lock is over, the cast counts) and drop the requirement rather than loosen the others.
- `cast` carries a render time `t` that only sets `CastRuntime.lagMs`, which nothing reads (a Wish never rewinds): bound it by RTT before any skill rewinds (the lag-compensation TODO above). A refused `cast` costs the server a validation (a blink: up to 60 landing probes over cached tables) and no fx, within `MAX_ACTIONS_PER_TICK` like any order.
- A cast's reveal (`reveal` in `handleCast`) takes effect in the shuffled input phase, so another player's `target` or `cast` on a hidden caster that casts again in the same tick can read it either way. Unreachable today (the only cast a hidden fighter makes is a 300 s Wish, and training is one seat), but a Q/E skill used while hidden breaks the status freeze's premise that nothing before the ledger pass reads statuses in an order-dependent way: store the reveal on the cast and apply it at the start of `updateAbilities`, or read a tick-start snapshot.
- `CastCancel` lists `"displace"`, but nothing interrupts a cast on a forced displacement yet (`displace()` calls no hook, and no Wish lists it): wire it into `displace` or a hook when the first skill needs it. Only `stun`, `silence`, `root` (through `statusApplied`) and `stagger` (through `staggered`) cancel a cast today.
- The prediction reads any `haste` status as Last Stand's `LAST_STAND_SPEED_BONUS` (the `status` fx carries no value and it is the only haste there is), and a slow only as a bit. A skill with another haste or a slow needs the value on the wire or in the synced state.

Roguelike overhaul (docs/ROGUELIKE_PLAN.md; R0, R1/R2, R3, R4a and R5 are built and zone terrain is wired into the generator; R4b and R6 on are not)
- The status runtime (timed statuses, silence, cleanse, invulnerability, displacement, areas) and the ability framework are the Wishes' (owner ruling, plan D21 reversed) and are built (see Statuses, abilities and areas): `shared/effects.ts` imports `StatusKind` from `status.ts` and a trigger's `status` and `cleanse` verbs are `AbilityEffect`'s, and the attack slow is a `ModSource` (applying or removing one calls `recomputeMods`; `AS_MULT_CAP` still caps the product). Still open for the plan: the four `onHit` rows (Chain Warden, Bloatfly, Rot Monk, Frost Wisp) and the two `vs` tests (Inquisitor's streak, Glacial Warden's slowed) are catalog data with `needs: "status"`: shown, never applied (R4b hangs them on `hitLanded`, which fires and has no consumer yet, through `addStatus` with `add` and `tag`); the `barrier` kind and a crowd-control immunity are R6 appends (effect bits 8192, 16384 and 32768 are spare); `TriggerAction` keeps its own `heal`, `barrier` and `cooldown` until R6 appends them to `AbilityEffect` (then `trigger.do` becomes an `AbilityEffect`), and a trigger's `status`, `cleanse` and `cooldown` actions do nothing yet; `statusMoveMultiplier` should keep only its stop once the `speedMult` mirror folds slows and haste.
- Mobs have no synced mirrors (`MobState` has no `asMult`, `windupMult` or `speedMult`): what a mod source gives a mob stays server-side, so once mobs can be slowed (R4b) a client would draw a slowed mob's bow pull at the unslowed pace. R4b adds them.
- Zone terrain is wired (ZT-6, the Known TODOs above): every map is themed, and the benches that build a map (`stepBench`, `bandwidth`, the e2e) read the themed one. `campDuel` plays on an open floor with a disc territory unless it gets `--map` (the zone's real camp on the game's map).
- `CampState.reward` stays "" until R7: every camp, elite ones too, drops a skill chest.
- The deal on zone maps (a pool of 24 to 32, 200 maps): for 2 to 8 players every dealt spawn lies in one walking tier on 100% of maps, with no same-zone pair and no spawn dealt twice; a deal takes under 0.9 ms and `spawnWalks` 3.5 ms per map. (The wedge maps' pool of 15 gave 95.8% at 8 players and one shared spawn on every map.)
- A deal reaches a client only as `plan` messages, resent only when its content changes or on a reconnect, and nothing acknowledges one: a message lost before the client's handler existed (the last joiner's deal goes out one tick after it joins) would stay lost. The client registers the handler in `enterRoom` right after the join and holds the newest message, and a player with no deal still presses Ready and is given a spawn, so it has not shown up; a bot presses ready after `PLAN_WAIT_MS` (1 s) without one.
- One buff is weaker than one stat it replaces: mostly +4% to +30% at the quoted value (3 stacks, after the owner's "double them" ruling), plus +20 armor or +16 and +20 magic resist, and about 2.1 times that at the plateau, against +67% max hp, +48% attack speed and +29% move speed (a build stacks several buffs). `ELITE_K`, the feed curve, the catch-up and the bounty's half-the-stacks were tuned to the old magnitudes, and the owner retunes.
