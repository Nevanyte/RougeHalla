# CLAUDE.md — RougeHalla (package name `raid-br`)

Top-down 2.5D roguelike battle arena. Up to 8 players pick a faction, loot, farm mobs and fight. The last one standing wins Glorious Victory (GV, cosmetics-only). Phaser 4 client, Colyseus 0.18 authoritative server, npm workspaces monorepo. Colored shapes only. Design and numbers: `docs/GAME_DESIGN.md`. Running and playing: `README.md`. Faction ids are `fire`, `sentenced`, `plague`, `frost`, `holy` (shown to players as Demon Blood). Weapon ids are `sword`, `bow`, `wand`, `shield`, `axe`. The roguelike overhaul (zones, typed camps, contested chests, skills, relics) is planned in `docs/ROGUELIKE_PLAN.md`; only its R0 contracts are built (the rules below say which). Each faction's Wish (`D`: `freeze`, `swarm`, `trial`, `blaze`, `lastStand`; GAME_DESIGN 8.8) and the status runtime and ability framework under it (8.9) are built.

Server env overrides (see `packages/server/src/config.ts`): `RAID_PORT`, `STASH_FILE` (the profile file; the name predates profiles v2), `MIN_PLAYERS`, `LOBBY_SECONDS`, `FILL_SECONDS`, `PATIENCE_SECONDS` (at 8 alive), `PATIENCE_MIN_SECONDS` (at ≤3 alive; default 40% of `PATIENCE_SECONDS`), `SUDDEN_DEATH_SECONDS`, `TRAINING_IDLE_SECONDS`, `WISH_LOCK_SECONDS` (default 45: how long every Wish stays locked after the run starts; the e2e uses 5), `COLYSEUS_LATENCY` (simulated minimum RTT in ms), `NET_JITTER_MS`, `NET_LOSS_PCT`, `NET_SEED` (the TCP-faithful model of `server/src/net/netSim.ts`: per connection and direction a FIFO, right-skewed jitter, a lost message stalls everything behind it for a retransmission timeout; core's own `COLYSEUS_LATENCY` handling is switched off because it would stack), `MAP_WORKER=0` (maps on the main thread), `DUMMIES=1` (training dummies and a weapon rack next to every spawn in arena runs too), `MOBS=0` (no regional mobs: they are on by default, one at every camp spot). Client: `VITE_SERVER_URL`. A dev build of the client exposes `window.__raid = { scene, room }`.

## Architecture rules (do not break)
- **Authoritative server.** Clients send inputs only (`move`, `stop`, `target`, `aim`, `attack`, `release`, `swap`, `pickup`, `cast`: `CLIENT_MESSAGE_TYPES`). The game client sends `target` and `cast` and no longer sends `attack` or `release`; they are the low-level trigger that mobs and the weapon harness still use (the bots click their foe, like the game client). Never accept positions, damage, or outcomes from a client. Apart from a walk target, the numbers a client supplies are aim angles, a render time `t` (clamped to `MAX_REWIND_MS`, only on `attack`/`release` and `cast`; a Wish never rewinds, so a cast's `t` only sets `CastRuntime.lagMs`, which nothing reads yet), a slot (a weapon slot, or an ability slot `wish`/`q`/`e` on `cast`), a container id, a fighter id (`target`, and a `cast`'s unit target `id`), the cursor's ground point `x, y` on a `cast` (always sent, clamped like a `move`'s point: a point or direction for the ability, ignored by a self cast) and an order number `seq` (an integer 0..255 on `move`/`stop`/`cast`; a bad one is dropped and the order still counts). `step.ts` `applyMove` copies a player's `seq` into the synced `PlayerState.moveSeq` on the tick it applies the order, and `handleCast` does the same for a `cast` that carries one, accepted or refused (a refused blink is then un-predicted at its ack): nothing reads it but the client, which learns from it when its order took effect (the prediction's delay, `net/localMotion.ts`).
- **Fixed 20 Hz tick.** Message handlers validate and enqueue; they never mutate game state. `enqueueClientMessage` returns false for a rejected message, and only an accepted one counts as presence (training's idle limit). The sim consumes input queues at the start of each fixed 50 ms step.
- **Sim is pure.** `server/src/sim/*` must not import `@colyseus/core` or touch clients/sockets. It mutates the schema state and a non-synced runtime struct, and returns events. The Room converts events into messages and persistence. Test the sim headless.
- **Tick order is fixed** (`sim/step.ts`; do not reorder): inputs (players in the shuffled `actionOrder`, then mobs) → abilities (`updateAbilities`: statuses and areas expire, every cast due lands, a Trial zone ends when its subject leaves it) → target locks (`updateTargets`) → weapon state machines → `afterWeapons` → movement → history → projectile sweep (present time, 10 ms substeps) → spawns → melee (rewound) → `beforeDamage` (signature damage, then status damage: trail contacts and `dot` ticks) → sudden death's burn (recorded into the ledger) → ledger (status changes made inside it wait for its end) → systems → settle. The abilities phase was ADDED by the Wishes; nothing was reordered. It runs before the locks so a fighter that just became untargetable loses its locks in the same tick.
- **The ledger: one way down, one place to settle.** Every hit (projectile sweep, melee, signature damage) is recorded with `recordHit` (`sim/ledger.ts`) and applied all at once by `applyLedger`. Each hit is mitigated per victim, then goes to `applyHits` for a player (`sim/arena.ts`), `hurtMob` for a regional mob or `damageMob` for a dummy. Sudden death's burn is a ledger entry too (`suddenDeath`, recorded after `beforeDamage`: all true damage, from `SUDDEN_DEATH_KILLER`, no `hit` fx, no kill credit of its own), so it lands in the same pass as the tick's hits. Every exit from the fight (death, leave) goes through `downPlayer`. In-tick results come only from `settle()` at the end of the tick, so the shuffled input order never decides a winner. A fighter killed this tick still lands what it started. Simultaneous hits on one victim land together, and the kill goes to the largest rival hit. Simultaneous last deaths go to the higher hp fraction at tick start (an exact tie draws).
- **Spoils are paid after the pass.** While `applyLedger` runs (`world.combat.collecting`), a kill's GV, bounty, stacks, kill barrier, drops and combos are queued with `payLater`. They run once every victim has taken their damage, from the lobby median feed as it stood before the pass, so a reward never decides who survives (sudden death's burn is in the pass too). A killer who goes down in the pass keeps the kill and its GV but gets no raised bounty and no rampage announcement. Outside the pass (`applyDamage`, tests) `payLater` runs at once. A mob's kill goes to the player who did it the most damage over the whole fight, not whoever lands the last hit. A mob that finishes a player a rival hit within `KILL_CREDIT_SECONDS` credits that rival (kill GV and bounty), as leaving does.
- **`hitLanded` is a hook, not a rule engine** (`WorldHooks`, called in `applyVictim`, `sim/ledger.ts`; `chainHook` adds to it). It fires once per ledger entry that took damage (mitigated amount above 0, so not sudden death's burn and not a victim that nothing got through to; DoT entries count), after the victim's damage and its `hit` fx, still inside the pass (`world.combat.collecting`, so kill spoils are still queued). It gets `(world, entry, applied)`, `applied` being the damage after armor and shield. Unset it costs nothing, and a hook must never change who survives or what a later entry of the same pass sees, or the ledger's order would matter. R4b's on-hit effects hang here: they decide from a snapshot taken at the start of the tick (or defer what they write until the pass ends, as `payLater` does; `addStatus`, `removeStatuses`, `cleanse` and `displace` already defer themselves, see Statuses, abilities and areas), and what they apply counts from the next tick. Nothing consumes it yet.
- **Statuses, abilities and areas** (`shared/src/status.ts`, `abilities.ts`, `blink.ts`; `sim/status.ts`, `fields.ts`, `displace.ts`, `abilities.ts`; GAME_DESIGN 8.8 and 8.9).
  - **One status runtime, one table.** `sim/status.ts` is a leaf: it imports only shared, `buffs`, `combatant` and `world`, and what a status DOES to a cast, a windup or an area is `sim/abilities.ts`, called through the hooks below. `STATUS_RULES` (`shared/status.ts`) is the ONLY place for a kind's max time, cap, stacking (`any`/`sum`/`max`/`product`), cleanse class (`soft`/`hard`/`never`), effect bit and `playersOnly`: never hard-code one elsewhere. An instance is (kind, source id, ability ?? tag): re-applying extends `until` (at most now + `maxMs`) and keeps the larger `value`, or accumulates with `add: {per, cap}`; different instances combine through `statusValue`. Readers ignore an instance past its `until`, `updateAbilities` removes it, and a stale one counts as a fresh application. `addStatus` returns null for a `playersOnly` kind on a mob (`invulnerable`, `hidden`, `deathFloor`) and for a fighter that is not standing. `invulnerable` raises `immuneUntil` (never removed early). The bits live in the synced `effects` (`refreshEffects`, written only on a change; `EFFECT_HIDDEN` only outside the reveal window, `EFFECT_CASTING` while a cast with `castMs > 0` is pending); the statuses themselves, casts and reveal times are server-only. `STATUS_KINDS`, `ABILITY_IDS` and `FIELD_KINDS` are wire orders: append only.
  - **The status table is frozen during the ledger pass** (`world.combat.collecting`). `addStatus`, `removeStatuses`, `cleanse` and `displace` called then queue themselves with `payLater` (they return null or empty) and run once the pass is over, still in the tick and before `systems`, so `damageFactor`, `floorHp` and immunity read one consistent table and the shuffled order decides nothing. `fighterOut` clears wait the same way. A status applied by a hit therefore counts from the next tick's damage, and lifesteal (a system) already sees it.
  - **Hooks** (`WorldHooks`, chainable; `sim/abilities.ts` installs them): `statusApplied(world, c, st, fresh)` (after the bits: a stun cancels the weapon windup, the bow's draw included, its cooldown spent, and a stun, silence or root interrupts a cast whose def lists it; applying a `slowAttack` calls `recomputeMods`, and `removeStatuses` (so a cleanse, an expiry, the teleport's clear) calls it when one is removed, so no weapon reads a slow that is gone), `attackStarted` (`startAttack`: a hidden attacker is revealed), `staggered` (when a stagger takes: interrupts a cast that lists `stagger`; no Wish does), `fighterOut(id, "down" | "removed")` (`downPlayer`, `killMob`, `removePlayer`, `abandonPlayer`) and `runEnded` (`endRun`). The sim reads statuses through guards: `cannotMove` (stunned, rooted or casting a cast with a cast time; `statusMoveMultiplier` is a `world.moveModifiers` entry that returns 0 for it, else `(1 - slowMove) x hasteMultiplier`), `actionBlocked` (stunned or casting: no attack start, swap or pickup; a cast with no cast time lands in its own tick, never counts as casting, and so blocks nothing queued after it), `isStunned` (facing frozen: `applyAim`, `handlePress`, `handleRelease`; `follow` does not chase, aim or fire; a stunned mob's inputs are drained and lost and its AI does not think), `isUntargetable` (see Swarm below). A stunned or rooted player's `move`/`stop`/`target` still apply and are walked or fought afterwards; a shield still blocks while stunned. Attack slow is a `world.modSources` source (`attackSlowSource`: an `asMult` of `1 - slow`), so the stat mirrors stay the one source of truth for attack speed.
  - **The cast pipeline.** A `cast` input becomes an `ActionCommand`; `handleCast` (players only) validates in this order and a refusal changes nothing (no cooldown, no fx) except that a `seq` is echoed in `moveSeq`: the slot holds an ability (`abilityInSlot`: `wish` is the faction's Wish, `q`/`e` are empty until skills), the run is active, the caster stands, the coliseum teleport is not within `CAST_TELEPORT_GRACE_MS` (300 ms: a cast that was aimed at the world before the teleport is refused, and a refusal is free; `world.abilities.teleportedAt`), `castBlocked` (the def's `blockedBy`: Wishes list stun and silence, a root does not stop one), no `rt.cast` already, `now >= slotReadyAt`, then the target (`unit`: `validUnitTarget` within `range + CAST_RANGE_SLACK`, standing, hostile, not evading, not untargetable, not teleport-immune, in line of sight on `collisionMap`; `point` with a blink: `blinkLanding` is not null). Accepting spends the cooldown at once (`abilityCooldownMs`), stores a `CastRuntime` in `rt.cast` (OUTSIDE `PendingAction`: it roots through `castMs` but only its def's `cancelledBy` ends it; Wishes list `stun` and `silence`, so a sword stagger never wastes one), faces the target or point, and, for `castMs > 0` or an `ownOrder`, cancels the caster's weapon windup (`cancelLockedWindup`, else `cancelAction` plus a `cancel` fx); an `ownOrder` (the blink) also drops the lock and the path, and a `dropsLock` (Swarm, a best guess: a locked auto-attack would reveal it at once) drops the lock only (`dropLock` also takes a locked caster's chase with it; a walk the caster ordered itself survives the cast root and goes on after it, so an escape does not stop you). The lock survives any other cast. `updateAbilities` (the phase) expires statuses and areas, then lands every cast due in TWO passes: pass 1 re-validates all of them against the state as it stood when the phase began (a failure is `cancelCast("fizzle")`), the survivors stop casting, then pass 2 applies all their SELF effects and then all their TARGET effects, each in the tick's secret rank, through an exhaustive switch over `AbilityEffect` (a new verb is a compile error until it is handled), so no processing order decides an outcome; then zones, then the bits. **Fizzle costs:** refused at validation is free; accepted and then failing at landing (`castEnd` `fizzle`) or interrupted (`interrupted`) keeps the cooldown spent; the coliseum teleport cancels a cast and REFUNDS it (`prevReadyAt`, `castEnd` `cancelled`); a death, a leave and the run's end cancel without a refund.
  - **Displacement and areas.** `displace(world, c, to)` is the one forced move: it sets the position, resets the rewind history to `to` (as the teleport does), re-plans a walk in hand from there (dropped if unreachable), bumps `PlayerState`/`MobState.displaceSeq` (uint8, wrapping), and restarts the lock of every player who has locked the fighter ("not seen yet", re-plan at once), so a blink through a wall is chased to, not dropped by the line-of-sight grace (the `TARGET_RANGE` leash still bounds it). Areas are `FieldRuntime`s in `world.abilities.fields` (null until first use: every entry point tolerates that), mirrored ONCE into the synced `state.fields` (`FieldState`) and deleted when they end; the server never updates one (a cloud is drawn at its owner's drawn position, `vx`/`vy` are for a later moving area). Zones and clouds end with their owner, a trail outlives it (as a projectile does), and the teleport and the run's end remove all.
  - **Ability damage is named.** It goes through `recordHit` under the caster (`by`) with `weapon: null`, `ability` and, for damage over time, `dot: true` (`LedgerEntry`, `LandedHit`), so kill credit, the bounty, `lastHit`, mob threat and the mob kill credit work unchanged. `contactsOf` skips it (it never starts or keeps a signature engagement); it feeds lifesteal and the heal lockout's combat clock like signature damage. A `dot` entry makes no `hit` fx of its own: `abilityDotFx` (a system) reports one per victim and source every `DOT_FX_MS`, with the ability code as the fifth tuple element, and the client draws no damage flash for `isAbilityDot`. `statusDamage` (a `beforeDamage` entry) ignites a trail's contacts (anyone standing on it but its owner, not evading and not teleport-immune, gets a `dot` status from the owner) and then records every active `dot` instance as true damage: the generic ticker, so an on-hit burn needs no code of its own. Trial lives in ONE place, `applyVictim`: it multiplies each non-arena entry's raw by `damageFactor(attacker, victim)` before mitigation (a zoned subject's outgoing damage by `dealtMult`; damage to it from the zone's caster by `takenFromSourceMult`; several zones multiply; the arena's burn is exempt; the `zoned` status carries `dealtMult` as its `value`, so `statusValue(zoned)`, a product kind, is what the subject deals now and 1 when it is not zoned). Last Stand lives in `applyHits`: `floorHp` holds hp at `min(floorHp, before)` and adds the whole `total` (after mitigation and the kill barrier, including the overkill it prevented) to the status's `taken`, and `applyHits` then returns that `total` (what reached the pool) instead of the hp removed, so a hit on a fighter already at the floor still staggers it, shows its number, lands in `world.combat.landed` and reaches `hitLanded`; its heal is `healShare` of `taken`, paid at expiry or by the teleport through `heal(..., { ignoreLockout: true })` (an anti-heal still cuts it).
  - **Flat power, one funnel.** No ability number reads buffs: `haste` ADDS `value x PLAYER_SPEED` (`hasteMultiplier(base, bonus) = 1 + bonus / base`), trail damage is true, and neither chill nor attack speed stretches a cast or a cooldown. `abilityCooldownMs` is the only place a cooldown is computed (a `flat` def ignores reduction; a training world gives a Wish `TRAINING_WISH_COOLDOWN_SECONDS`). Trial's ±20% is the one relative number (owner rule).
  - **Lifecycle.** Death, leaving and `abandonPlayer` (`fighterOut`, deferred in a pass): `castEnd` `cancelled` with the cooldown spent, every status removed with no heal, the zones and clouds the fighter owns and the zones it is the subject of removed (no stun), its trail stays. The coliseum teleport (`teleported` hook): every cast refunded, every status and area ended, a Last Stand still pays. The run's end (`runEnded`): everything cleared, nothing paid. Expiry: a `hidden` ends its cloud, a `zoned` its zone, a `deathFloor` pays. A dropped connection leaves casts and statuses alone (everything drawable is synced, so a reconnect is right at once). `raidStarted` (`armWishes`) sets `wishReadyAt = raidStartedAt + wishLockSeconds x 1000` (`SimConfig.wishLockSeconds`, env `WISH_LOCK_SECONDS`, default 45; ready at once in training) and clears statuses, casts and areas.
  - **Swarm (the `hidden` status).** It hides on the CLIENT (`PlayerView` draws no remote hidden fighter, the local one at 0.45 alpha; `targetable(effects)` keeps it out of the click pick) and the SERVER makes it untargetable: `lockable` refuses it, locks on it drop in the same tick (`updateAbilities` runs before `updateTargets`), `lockedFoe` never re-aims at it, `validUnitTarget` refuses it, and a mob's `pickTarget` skips it (the threat is kept; with no one else the mob gives up and walks home). Casting it drops the caster's own lock (`dropsLock`, a best guess) but not its walk: its locked auto-attack would otherwise reveal it at once, and a Plague that wants to ambush clicks its target again. Its own attack or cast reveals it from the NEXT tick (`reveal` sets `revealFrom = now + TICK_MS`, so a reveal applied mid-phase by `attackStarted` or `handleCast` never changes what another fighter reads in that tick, whichever joined first) until `landsAt + HIDDEN_REVEAL_MS` (500 ms); being hit does not. A second Swarm while the first is up (training's 5 s cooldown) replaces the first cloud and extends the one status. Projectiles in flight, swings along their start aim, areas and signatures still reach it, and its position stays in the synced state (see the Known TODO on cheating).
- **Target lock** (`sim/targeting.ts`; `setLock`/`dropLock` in `sim/weapons.ts`; synced as `PlayerState.attackTarget`, "" = none). `target {id}` locks an enemy and the server plays the fight from then on, as mob AI does for a mob: each tick after the inputs, `policies.ts` `decide` with `lockSpacing` (close in to the weapon's `far`, then stand; never back off or strafe) sets the path (re-planned at most every `TARGET_REPATH_MS`, only when the goal moved over 8 u or the path ran out), holds the trigger while the target is in range with a clear line, and aims at its present position and velocity. The client's `aim` is ignored while locked, and `facing` follows the target (the shield's block cone reads it). Accepted only for another combatant that is standing, not evading, hostile (not self, not mob to mob; only players lock), within `TARGET_RANGE` (640 u); anything else is ignored with no change. Line of sight is not needed to lock (a target behind a wall is chased around it), only to attack, but a target out of sight with no path to it is refused (a mob across the locked coliseum gates; the client also offers no mobs while `gatesLocked`). Clicking the fighter already locked changes nothing; a new lock clears the earlier walk. A `target` order costs at most one path search per `TARGET_REPATH_MS` per player (`lockSearchAt`; an order out of sight sooner than that is refused, and its search doubles as the chase's first plan), and the chase's own re-plan time (`lockPlanAt`) survives setting or dropping a lock, so spamming orders (up to `MAX_ACTIONS_PER_TICK` a tick) never buys extra searches. `endRun` drops every lock, so a winner's `attackTarget` is not synced through the linger. Dropped (trigger and path cleared, the fighter stops where it stands) when the target is no longer standing, is evading, is past `TARGET_RANGE`, or has been out of sight for `TARGET_LOS_GRACE_MS` (1.5 s; until then the chase paths around the wall) after having been seen once since the lock (`lockSeen`; a target locked behind a wall is chased until first seen, bounded by the leash), when it is out of sight and the chase finds no path to it, or the player holds no weapon. **Orders replace each other in arrival order within a tick** (`InputQueue.moveBefore`, like `aimBefore`): `move`/`stop`/`attack` drop the lock (an unreachable `move` still does), `target` lets go of the trigger. **A player's own order cancels the attack its lock is winding up** (`cancelLockedWindup`, `sim/weapons.ts`, LoL's move-cancels-windup): a `move`, a `stop` (applied in `step.ts`, an unreachable move included) or an accepted `target` on another fighter, while its `PendingAction.target !== undefined` and it has not landed. No swing, ball or arrow; the cooldown is refunded (`readyAt = startedAt`, it was over when the attack began); the root goes (`cancelAction`); the bow's `drawStartedAt` clears; a `cancel` fx tells every client to drop that fighter's telegraph, and the walk starts in the same tick. Re-clicking the locked fighter (or, once the lock has dropped, the fighter the attack is already aimed at), a refused `target` and a landed attack (the axe's root after its swing stays) cancel nothing, and neither does an `attack` input. `releaseTrigger` (teleport, going down, a dropped client, training revive) drops it too; a swap or a pickup does not. An attack the lock starts records its `target` on the `PendingAction` and is aimed again as it lands (a swing straight at the target's position at its rewind time) or leaves (`leadAim` from the drawn origin at the target's present position and velocity), if the target still stands and is hostile; then it flies straight and can be dodged. An unlocked attack (a mob's, the harness's) keeps the old aims: a swing and a ball go where they were aimed when the attack started, an arrow along the aim held when its draw ends (the bow's aim at release), and `decide` leads the bow for the lags alone, without its windup. A locked attack has no client `t`: `lagMs = TICK_MS`.
- **Windups root.** Every attack roots its fighter from its start until the swing lands or the arrow or ball leaves (`moveMultiplier`: 0 while `action !== null` or inside `rootUntil`, else 1; nothing else slows a walk: buffs and Frost's chill are `world.moveModifiers`). A directional windup (a mob's, the harness's, an `attack` input) is committed: a `move` given during it is kept as the path and walked afterwards, only a stagger (not on the bow) or a swap cancels it. One the target lock started is the player's own click, so the player's next `move`/`stop`/`target` cancels it too (see Target lock): the game client walks away from a windup it no longer wants. The bow is a fixed windup (kind `"draw"`, `landsAt`, `drawStartedAt` synced for the pull), never a partial draw. `weaponTimings`: sword and bash 0.1 s, axe 0.25 s / 25% of the interval and root 0.5 s / 50%, wand `min(WAND_WINDUP 0.4 s, 0.8 × interval)`, bow `min(BOW_WINDUP 0.6 s, 0.92 × interval)`. These are the anti-kiting lever (below, Weapons and factions).
- **Players and mobs fight through `Combatant`** (`sim/combatant.ts`). Weapons, melee, projectiles and the ledger take either; only how they go down differs. A regional mob's faction is its region's scaled by `MOB_K` (elite `ELITE_K`) and paced, read through `factionOf` like a player's, so signatures, armor and timings apply to it unchanged.
- **Mobs are players who send inputs.** `sim/mobAI.ts` is a system (after damage). It pushes `move`/`stop`/`aim`/`attack`/`release` into the mob's own `InputQueue`, and `step.ts` applies them next tick through the same handlers as a player's. Idle mobs send nothing, and mobs never lock a target. A mob walking home (`return`) is evading: `hurtMob` returns 0, `isEvading` keeps it out of hit tests, signature targets and contacts, it starts nothing new (a shot already in the air still lands), and it is whole when it arrives. It gives up 6 s after it last *dealt* damage, so kiting from outside its leash gains nothing. The coliseum teleport puts every mob back on its camp spot at full hp. Mobs never hurt each other (a hit is recorded with scale 0) and their shots fly past each other. A training world never spawns regional mobs.
- **Signatures ride the ledger.** Faction bonus damage (burn, backlash, disease, mark) is recorded in the tick's ledger in the `beforeDamage` phase, so it lands with the tick's hits. Heals go through `heal()` in `sim/factions.ts` (3 s out-of-combat lockout; Holy's lifesteal is exempt). `sim/factions.ts` stretches chilled fighters' `readyAt`, bow draw (its start and the moment the arrow leaves, so the cycle stays interval / chill) and press buffer every tick; the other windups are not stretched, so a chilled swing still lands on time. Weapon timing changes must keep the chill working: `npm run harness:factions` checks it against `testing/realtime.py`. A landed stagger (the 0.5 s immunity starts) pauses the staggered fighter's burn, disease and mark for its weapon's windup (`staggerPause`; none for a bow, whose draw a stagger never cancels; the real sim only, `realtime.py` has no staggers).
- **Buffs and the feed** (`shared/src/buffs.ts`, `sim/buffs.ts`, `sim/feed.ts`). Stacks are fractional floats on `PlayerState` (`stacksHp/As/Ms`). The S-curve bonus feeds max hp (`syncMaxHp`), `attackInterval`/`damagePerHit` (via `attackSpeedMult`) and `world.moveModifiers` (`moveSpeedMult`), both of which read the stat mirrors (next rule), not the stacks. Combos at 3 and 5 stacks fire on every kill. The mob reward curve and the catch-up read the feed (`kills + 0.25 × mob kills`). The **bounty reads player kills only**.
- **Stat mods: the mirrors are the one source of truth** (`shared/src/mods.ts`, `effects.ts`, `sim/mods.ts`). `PlayerState.asMult`, `windupMult`, `speedMult`, `armorBonus` and `shieldBonus` hold the stats that effects change. Today only attack speed and move speed have a source (the S-curve bonuses of `stacksAs`/`stacksMs`, as `stat` rows) and a reader (`attackSpeedMult`/`moveSpeedMult` call `asMultOf`/`speedMultOf`, never `buffMultiplier(stacks)`; the hp stacks stay with `syncMaxHp`); the windup, armor and shield mirrors sit at the identity with no reader until R4a wires them (`windupMult` into `timingsOf`, the flat bonuses into `defenseOf`). `recomputeMods` is the only writer, and the fold is fixed: `stat`, `flat` and `while` rows ADD within a key (two +10% attack speed rows are +20%), each key becomes one multiplier `1 + sum`, different keys MULTIPLY where the sim combines them (attack speed with damage, `speedMult` with the kill bursts and the chill), flat rows add points; `vs`, `scale`, `onHit` and `trigger` rows are not stats and do not fold; a row whose `requires` ids are not all owned is off. Then every `world.modSources` entry is asked (a `ModSource` answers from the present state, null = nothing; its multipliers multiply in, its flats add). Who calls it: `grantStacks` (so `transferStacks` too) re-folds at once, so a grant changes the attack and the walk in the same tick; a source whose answer changes must call `recomputeMods` itself; and `updateMods`, the last `world.systems` entry (`gameplay.ts` installs it last), re-asks every source each tick so an expiry shows by the end of its tick (a source must answer from `until > now`, not from a list another system prunes). A mob has no synced mirror: what the sources give it is kept server-side, so a slowed mob attacks slower but a client still draws its bow pull at the unslowed pace. `sim/mods.ts` is a leaf: it must not import `weapons.ts`, `arena.ts`, `ledger.ts`, a status runtime or anything else that imports `buffs.ts` (type-only imports are fine).
- **Clients decode the mirrors, never recompute them.** The wire form is exact: the multipliers are float64 (the very double the sim used) and the flats int16 tenths of a point, so the local prediction and `FighterArt` read them through `decodeMirrors`/`decodeMult`/`decodeFlat` (`net/localPrediction.ts`, `render/FighterArt.ts`) and never from the stacks, and `sync.test.ts` compares them bit for bit. The kill combos and bursts still read the stacks (they go with the stacks in R4a). The plan's 0.001 quantization is deferred to R4a on purpose: float64 keeps the sim's attack and move multipliers equal to `buffMultiplier(stacks)` exactly (the server suite compares with `toBe`), and quantizing means changing `encodeMult`/`decodeMult` and the field type together. Until R4a removes the stacks fields, a read through `asMultOf`/`speedMultOf`/`modsOf` also re-folds if the stacks changed behind `recomputeMods`'s back (tests write them directly; production writes them only in `grantStacks`, so there it always passes).
- **Combat netcode.** Projectiles are not in the synced state: they are plain objects in `world.projectiles`. A projectile is announced once, in the `fxs` batch of the step that loosed it, and never updated. Clients fly it from `(x, y, vx, vy, t)`, and a `projEnd` fx says where and why it stopped. A client that joins or reconnects mid-flight is sent the projectiles then flying as a batch of its own (`FxChannel.inFlight`, queued behind its full state by core). Melee samples the attacker and every target at the attacker's render time (`rewindT`: the client's `t` on a low-level `attack`; a locked attack, which is all the game client makes, has none and rewinds one tick, and the server aims it from the present: the target lock). A projectile leaves from the shooter's rewound (drawn) position, and the `aim` angles that low-level attacks and the shield use are measured from where the client draws its own player: since the local fighter is predicted, that is the PREDICTED position, which is where the server will have it when the aim lands (closer to the server's present than the old delayed one). Locked attacks stay server-aimed from the present; `attack`/`release` users (the harness, mobs) keep the rewound origin and `t`. Keep those three consistent.
- **Wire format.** All fx of a step go out as ONE `fxs` message (`shared/src/fxCodec.ts`, `rooms/FxChannel.ts`): integer tuples, fighters named by index into the append-only `RaidState.roster`, projectile launches in the same batch (`FxBatch.p`). Players still in the lobby are not rostered (no fx names one, and an entry is for good). A mob is rostered when it is placed. `unpackFx(batch, room.state.roster, onDrop?)` needs the client's copy of the roster: without it every id-bearing fx is dropped, and `onDrop` is how a skipped tuple is noticed (the client warns once in dev builds; the e2e run asserts nothing was dropped). The client holds `fxs` batches from the join until the scene starts (`net/fxInbox.ts`). The code tables are wire format: grow them at the end, never reorder (the newest fx kind is `status`, 17: `[17, id, status, ms, by|null]`, a status instance newly applied; after `castEnd` 16, `castLand` 15 and `cast` 14 for the ability casts, and `cancel` 13, a player's own order cancelled its lock's attack; abilities and status kinds travel as their index in `ABILITY_IDS` and `STATUS_KINDS`, so those lists only grow at the end). A `hit` fx carries an optional fifth element, the ability code, for damage an ability dealt (its weapon is null); a reader that predates it ignores it, a bad code drops the tuple. `castLand` carries `x2, y2` together, only for a blink's landing. Adding a field to an `FxEvent` means adding it to its tuple and to `packages/shared/test/fxCodec.test.ts`. Synced numbers are narrow on the wire (float32 positions and hp, uint32 timers); the server keeps doubles.
- **The map is never synced.** Only `seed` is in state; both sides call `generateMap(seed)` (must stay deterministic: use `rng.ts`, never `Math.random`, in shared). Loot contents are rolled server-side with a non-public RNG. While `state.gatesLocked`, movement, line of fire and loot line of sight use `collisionMap(world)` (`withGates(world.map)`), never `world.map`. `coliseumSpots` hands out mapgen's coliseum inner spawns.
- **Map contract for the roguelike plan** (`shared/map.ts`, `mapgen.ts`; ROGUELIKE_PLAN 3.2). `GameMap` also carries `attempt` (the generator attempt `generateMap` accepted: later phases publish (seed, attempt) so both sides run exactly one; 0 for a hand-built map), `camps: CampDef[]` (zone, centre, clearing radius `r`, 3-5 `spots`, `eliteSpot`, the reward `chest` tile, `area`, `radius`), `territoryGrid` (0 = none, else 1 + the camp's index in `camps`), `spawnPool` (candidate starts tagged by zone), and `FactionRegionDef.pole`/`area`. `generateMap(seed)` keeps its signature (it still loops attempts until one passes); the plan's `generateMap(seed, attempt)` comes with R2. Until then a wedge adapter at the end of `buildMap` (`wedgeCamp`) fills the fields from the old data, draws no random number and changes no tile: `camps` in `REGION_FACTIONS` order then camp index with the same ids as `regions[].mobCamps` (which stays as a view, as do `spawns`), `chest` = the clearing floor tile nearest the camp centre that is not a spot (ties: lowest row, then column), `eliteSpot` 0 for an elite camp else -1, `radius` = `MOB_LEASH_RADIUS` (the old leash), `area` 0, `territoryGrid` all 0, `spawnPool` = `spawns` tagged by `regionGrid`, `pole` = `anchor`. Nothing in the sim or client reads any of it yet. `shared/test/mapLegacyHash.test.ts` pins the pre-R0 output of seeds 0..199 by hashing only the pre-R0 fields, so added fields pass and a changed layout fails; R2 replaces the sector (wedge) code and the adapter with the zone generator's own camps and that test with its own certification, on purpose.
- **`world.rewardRandom` is a private stream** for reward and roster rolls (camp rosters, chest options, "?" kinds, plan deals; nothing draws from it yet). `createWorld` seeds it (sfc32, a 128-bit state) from `rewardSalt`, four words `RaidRoom` takes from `crypto.randomBytes` (never the public seed, which every client holds; a 32-bit state could be brute-forced once rolls are revealed). A number is also accepted and expanded, for tests. It is separate from `world.random` so that drawing rewards never shifts the loot rolls or the sequence tests script (`createWorld` takes exactly one draw from `random`, for `orderSalt`, and none for this), and separate from `orderSalt` because that salt also keys `tieRank`, whose outcomes a client can stage and read (Known TODOs): a stream derived from it could be brute-forced. Without a `rewardSalt` (tests, the harness) it is derived from `orderSalt` by a tagged hash, so it matches neither `actionOrder` nor `tieRank`: fine for a test world, never for a live room. Anything hidden (rosters, "?" flags, chest rolls) comes from here and stays server-side or in private messages.
- **Clients render in the past, except the local fighter.** Remote entities render in the past via `SnapshotBuffer` (`shared/interp.ts`) at a time `RenderClock` gives (`EntityInterpolator.renderTime`; `new EntityInterpolator({ adaptive: false })` is the old fixed `INTERP_DELAY_MS` 100 behind a `ServerClock` that snaps back on a late patch, kept for A/B and as a fallback). `RenderClock` judges every patch by `r = (server time of the previous patch) − (its arrival)`, the most render time may be ahead of local time for the segment to be complete, and holds render time at the 98th-percentile-low `r` of the last 4 s less 10 ms: the delay (`PATCH_MS` + how far behind the median `r`) follows the network between `MIN_INTERP_DELAY_MS` 70 and `MAX_INTERP_DELAY_MS` 150, grows at up to 20% of real time (render slows to 80%), falls at 1% (up to 5% when far above what is asked), and render time never runs backwards (only a 250 ms jump re-anchors it). The `ServerClock` under it (`now()`, the order stamps, the HUD's deadlines) has no late snap there (`lateSnapMs = Infinity`): lateness is the delay's job, and the clock can wobble without moving the picture. Everything drawn at render time (fx, deaths, hit-stop juice) follows the delay; `INTERP_DELAY_MS` is the delay a client starts with and what the harness and the bots assume a player sees. In a dev build `window.__raid.interp` gives `{ delay, target }`. Measured with `bench/netProbe.ts`/`netTraceEval.ts` (see Known TODOs, Netcode). The LOCAL fighter is predicted (`net/localMotion.ts`, presentation only: nothing it computes is ever sent, the server stays authoritative): an order walks a model at once along the same shared A* path, `drawn = sim + visual`, and each patch pulls the model back in line (`S(T)` against the model `delay` earlier, `delay` measured from `moveSeq`; small errors go into a decaying `visual` offset, never faster than the `CORRECT_SPEED_*` caps). It cannot drift or hang: an order the server never applies (lost while reconnecting) is forgotten after `ORDER_EXPIRE_MS` and does not hold the comparison off; samples off by more than `DIVERGE_ERR` for `DIVERGE_PATCHES` in a row with nothing in flight and the server not heading where the model walks (a revive, a halt, a walk it did not order) drop the model's walk; an error past `SNAP_DISTANCE` (even with an order pending, beyond what that order's walk explains) or an offset past `VISUAL_SNAP_DISTANCE` snaps to the server and plans the destination again from there; the teleport and the local death fx `cut()` it (the next sample snaps, however short the jump); the scene resets it while `room.reconnection.isReconnecting`; a click is clamped to the world as `parsePoint` clamps it. Dead, in the lobby, after the run ends, and until a teleport is drawn it is drawn from the snapshots, except that while its death or the teleport's cut is still ahead of what is drawn it stays where it was last drawn (`localDrawSource`). After a `target` it follows the server's chase (the newest sample carried one tick by its velocity): the lock is the server's. The model enters follow when a patch shows the lock (`PlayerState.attackTarget`; not while a move or stop of ours is still in flight, which would end it) or at once on a click it expects to be accepted (`expectLock`, for the responsiveness), and leaves when the lock empties; a lock that never shows within `ORDER_EXPIRE_MS` was refused, and the walk it interrupted is planned again. The scene feeds it the buff and chill speed (a Frost mob chills like a Frost player), the kill bursts and the axe's root (`net/localPrediction.ts`), and what the abilities do to it: a stun or root and a cast's own root from the `status`/`cast`/`castEnd` fx (the synced `effects` bits stand in only when no fx told of one, as after a join), Last Stand's haste added on top as the server adds it, and a blink. A Blaze Step is predicted: `castSlot` runs the shared `blinkLanding` on the predicted position, tells the prediction (`noteCast`, which calls `LocalMotion.blink`: the model and the drawn fighter jump at once, the walk and lock in hand stop being predicted, the order carries its jump so the comparison does not read the lead as a divergence) and sends the `cast` with a `seq`; the patch that acks it also shows a changed `displaceSeq`, which `LocalMotion` reads as its OWN blink (the error to the server's landing is absorbed like any other, or snaps past `SNAP_DISTANCE`: a refused blink is echoed in `moveSeq` with no `displaceSeq` change, so the whole jump is the error and the prediction is pulled back to the server), while a changed `displaceSeq` with no blink of ours behind it is a forced displacement (the model, its history and the drawn fighter all shift by the jump, with no snap test, and a walk in hand is planned again from there). `EntityInterpolator` treats a changed `displaceSeq` as a cut for that fighter, so a remote blink is not slid into. Slow magnitudes are not predicted (only a bit is synced); anything unmodelled is the server's correction. Remote fighters and fx stay in render time, so what is drawn at the local fighter (hits on it, its telegraph) plays at its predicted position: accepted.
- **Rendering is separate from logic.** Phaser scenes only read interpolated state and send inputs. Projection lives in `client/src/render/projection.ts` (screenY = worldY · Y_SCALE, height drawn upward, depth = worldY).
- **The picture is a viewport, not the window.** `view/viewport.ts` fixes the world height every player sees (`REF_VIEW_H` projected px; wider windows show more width, capped at 21:9 with bars; below 4:3 the width stays at the 4:3 minimum), the canvas is rendered at the device density (capped at 2x and a 4K pixel budget, `settings.hiDpi` off = 1x) and the camera zoom is canvas px per projected world px. Never assume camera zoom 1 or 1 canvas px = 1 CSS px: read a pointer's world point through the camera (`screenToWorld`, `pointer.updateWorldPoint`), set a scroll with `scrollForTopLeft` or `centerOn`, and scale a Phaser camera shake by `1 / zoom²` (`ScreenJuice`). The DOM overlay `#ui` is laid out at `--ui-w` x `--ui-h` and CSS-scaled, so overlay code uses those variables and `data-ui-short`/`data-ui-narrow` instead of `vw`/`vh`/size media queries, and `getBoundingClientRect()` for anything that meets the pointer.
- **The hub is client-only.** `HubScene` has no room and no server. Its layout and walking rules are pure (`hub/hubLayout.ts`), and a station only calls back into the menu (`onStation`). What it shows comes from the REST profile.
- **Training is a mode, not a fork.** `client.create(TRAINING_ROOM_NAME)` makes a private one-seat room of the same `RaidRoom` class. The server registers two handlers (`defineRoom(RaidRoom, { mode: "arena" })` under `ROOM_NAME`, `{ mode: "training" }` under `TRAINING_ROOM_NAME`). Colyseus merges handler options over the client's, so a client cannot choose the mode. A training world has `SimConfig.training` + `dummies`: a plain dummy, a shield dummy and a rack of every weapon next to the spawn, started the moment its player joins. It has no regional mobs, patience timer, teleport, sudden death, result, GV or stats. Three locks keep it from recording anything: `trainingSettle` replaces `suddenDeath`/`settle` (anyone down is revived), `RaidRoom.settle` and `bankVoided` return early in training (a down *between* ticks still emits `resolved`, which the Room ignores), and leaving is `abandonPlayer`, never MIA. A dropped or leaving client frees the profile at once (`onDrop` holds no seat in training). A player with no accepted input for `trainingIdleSeconds` (300) is let go: only an input `enqueueClientMessage` accepts refreshes `lastInputAt`. Every training branch sits behind `world.config.training` / `RaidRoom.training`; an arena world never reaches it.
- **GV banks at resolve.** The sim only accumulates run GV and reports it in `resolved` results. The Room banks it (`recordRun`, or `bankGv` for a run voided by shutdown). Run gear never persists.
- **Persistence is `ProfileStore`.** Mutations are synchronous in memory (nothing awaits between a check and its change), writes are coalesced and atomic (temp file, fsync, rename, directory fsync) with retry and backoff, and `flush()` runs on shutdown. A v1 file migrates on load. A file that cannot be parsed stops the server and is moved aside, never overwritten.
- **The shop is server-only.** Purchases and equips are `POST /api/profile/:name/purchase|equip` with the profile token. The client sends only a cosmetic id (and a slot). `ProfileStore.purchase/equip` check the token, the catalog price, ownership and the balance in one synchronous step, so a double spend is impossible. Spending lowers `gv` only, never `gvLifetime` or `gvByMonth` (the leaderboard ranks GV earned). Achievements are evaluated inside `recordRun`. An id lands in `achievements` once, and its reward cosmetics are granted in the same step. Win achievements and the per-faction/weapon counters count only `winQualified` wins (the win-bonus gate: `!winBonusWithheld`), so a walkover against a throwaway callsign earns nothing. Kill and bounty achievements are not gated (their rewards are unpriced; an owner decision). The leaderboard ranking is cached per month (dropped when GV is credited in it), and `you` on `GET /api/leaderboard` is sent only with that profile's own token. Equipped cosmetics reach other players as one synced `PlayerState.look` word, fixed at join.

## Conventions
- Colyseus 0.18 APIs (not 0.15/0.16 tutorials): `defineServer/defineRoom` from `@colyseus/core`, `Room<{ state: X }>`, `this.onMessage` (or `messages = { ... }`), `setTimestep` (`setSimulationInterval` is its deprecated name), `client.sessionId` (no `client.id`), a static `onAuth` for matchmake-time checks, client `@colyseus/sdk`. `RaidRoom` sets `patchRate = 0` after `setTimestep` and sends each patch itself after the step. The scene reads `room.state` every frame; there are no per-field callbacks.
- Schema uses the decorator-free `schema({ ... }, "Name")` + `t.*` builders. Give primitives `.default(...)`. No decorators anywhere.
- Only the server imports `@raid/shared/schema` at runtime; the client uses `import type` from it (it decodes by reflection).
- Tunables live in `shared/src/constants.ts`, the catalogs (`weapons.ts`, `factions.ts`, the combos in `buffs.ts`, `cosmetics.ts`) and the signature numbers in `signatures.ts`. Mob scale, leash, buff curves and the reward curve are in `constants.ts`. Loot weights are in `server/src/sim/lootTables.ts`. Units: world units (1 tile = `TILE` = 32), seconds for durations unless a name ends in `Ms`, server time in ms.
- Weapon numbers live in `shared/src/weapons.ts`: the v3 faction × weapon formula (a weapon is a % boost on the faction's rate; `attackInterval`, `damagePerHit`, `backlashPerSwing`). It must keep matching `testing/realtime.py`: `python3 testing/weapon_reference.py` prints the reference tables, pasted into `shared/test/weapons.test.ts` and `server/src/harness/parity.ts` when the design numbers change. `DUEL_PACE` (2) multiplies every faction damage number (not hp; Sentenced's mark ramp by k²) through `pacedFaction`. Sim combat reads the paced sheet through `factionOf` (`sim/combatant.ts`), never the raw one.
- Design rules the sheet left open are recorded in `docs/GAME_DESIGN.md` 9.4. Change them there and in the tests together.
- No `Math.random` in shared code. No enums or decorators (keeps tsx/Vite/TS7 happy).
- Keep comments sparse; explain *why*, not *what*.

Identity and persistence
- No rate limits beyond two narrow ones. Matchmaking verifies the profile token before creating a room or reserving a seat (the static `RaidRoom.onAuth`), and refuses a profile that is already active or opened a still-unjoined room in the last 5 s. A target order out of sight costs at most one path search per `TARGET_REPATH_MS`. In-match orders are otherwise unlimited (up to `MAX_ACTIONS_PER_TICK`): a scripted client sending `stop` then `target` every tick starts and cancels a windup each tick, which broadcasts about 40 small fx a second (one windup and one `cancel`) to the room. It's bounded and cheaper than move spam (an A* search per tick), but both want a per-player order budget. Profile creation is free: any client can `GET /api/profile/<new name>` as often as it likes, `/api` answers every origin (`Access-Control-Allow-Origin: *`), and each claim adds a profile and a file rewrite. The shop and equip endpoints have no limit either. Training rooms have only the one-active-room guard per profile, and a running room broadcasts a patch at 20 Hz until its player leaves or idles out, so many throwaway profiles can hold many rooms.
- Profiles are weakly authenticated: a random token in `localStorage`, stored in plain text in the profile file, no passwords, recovery or expiry, and no TLS. Clearing site data forfeits the profile.
- GV banks when a player's run resolves. A graceful shutdown (SIGTERM/SIGINT, uncaught exception) pays the GV earned so far (`bankVoided`). A hard kill (SIGKILL, power loss, OOM) mid-run loses it. A purchase is answered once it is in memory, before the file write lands: a hard kill in that window undoes the purchase together with its GV debit, never one without the other. Writes are batched (at most one per second; `close()` and `flush()` write at once), so the window is up to about 1 s. Under `npm run dev`, Ctrl+C reaches the server twice (terminal and tsx), and the second SIGINT exits mid-shutdown, so the last second of changes can be lost in dev.
- The profile file has a single-writer lock (`<file>.lock` holding the PID; a dead PID is taken over, and an exit hook frees it). In a container, a hard-killed server restarted with the same PID (PID 1) sees its own PID as live and refuses to start; delete the lock by hand there.
- GV can be farmed with free callsigns: the win bonus needs 3+ starters and damage on 2+ different opponents (`WIN_BONUS_MIN_*`), but two throwaway callsigns that get killed still pay kills and the bonus. Bounties are uncapped but come from player kills only (an owner decision), so a partner can only cash a bounty that real kills built. Mob GV is capped at `GV_MOB_CAP` per run.
- GV earned after a player's result went out is dropped (`awardGv`). A projectile outlives its owner and its hit still lands; a kill by a shooter who left or whose result is out is credited by name only (`killedBy`), with no GV and no bounty.
- Mob kills do not feed achievements (owner question). "Bounty claimed" counts runs that paid bounty GV (`progress.bountyRuns`), not individual claims. There is no end-of-month trophy job: the leaderboard keeps each month and nothing is awarded when one closes.
- A player who joins without picking a faction (old clients, bots without `--faction`) gets the round-robin default by join order (`defaultFaction`). A failed join or a lobby leave still uses up a slot.
